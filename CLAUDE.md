# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Circles is a prototype for a federated, neighborhood-scale coordination tool — members, circles (the city, its neighborhoods, and the councils, collectives, and co-ops inside them — one universal, nestable concept), events, and a lightweight direct-democracy governance layer (any circle's meetings, confirmed by a majority of its members), on top of a design system carried over from "The Commons Institute" (ink-on-white, Helvetica/Georgia, zero border-radius, hairline rules).

It's a Next.js (App Router, TypeScript) app backed by a real, self-hosted Postgres database (via a data-access layer, `lib/db/`, using Drizzle ORM — see Data access layer) — `lib/data.ts` is now seed-script input rather than something any app code reads directly, and all runtime state lives in `components/providers/app-state-provider.tsx`, mounted in `app/(app)/layout.tsx`. Auth is real too (Better Auth's email-otp plugin, no password — see Authentication), gating everything except the welcome page at `/`; the one thing still missing is a real email provider. The app was originally prototyped as a single ~3900-line file, then split into `lib/` and `components/`, then moved off a single-component view-state switch onto real routes; none of the earlier single-file structure exists anymore, so treat the current tree as the spec.

## Setup & commands

- `npm run dev` — local dev server
- `npm run build` — production build (also the fastest way to catch broken imports/syntax across the app)
- `npm run lint` — ESLint

There is no test runner yet — deliberately deferred until the app grows past prototype stage.

## Architecture

### Routing and shared app state
`/` is the unauthenticated welcome page (email + one-time-code login — see Authentication below); every other route lives under the `app/(app)/` route group (a URL-invisible folder — `app/(app)/home/page.tsx` still serves `/home`), which requires a session: `/home`, `/circles`, `/circles/[id]`, `/circles/[id]/manage`, `/events`, `/events/new`, `/events/[id]`, `/events/[id]/edit`, `/profile/edit`, `/game`. Every circle — neighborhood or not, however deep it sits in the tree — lives under `/circles/[id]`, keyed by its own stable id rather than its position in the hierarchy (see Circles below). Routes can't share React state via props the way a single root component could — `components/providers/app-state-provider.tsx` holds everything that used to be `useState` in that root component (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, and their mutators) and is mounted once in `app/(app)/layout.tsx`, seeded from props that layout fetches server-side via `lib/db/`; every route beneath it reads the state via `useAppState()`.

Mutators on `AppStateProvider` are pure state + toast now — they never navigate. Where the old single-view app followed a mutation with a view change (e.g. jump to the newly created event), that's the calling route's job, since only the route has the router; `createEvent` returns the created event so the caller can `router.push` its URL. Each mutator also calls the matching `lib/db/` write, alongside (not instead of) its own `setState` — see Data access layer below. Compute the value a mutator writes to the DAL synchronously from the state already in scope, never by reading a `let` that a `setState` updater assigned: React doesn't run a functional updater inline, so that value is still its initial one on the next line (this silently dropped every DB write from `toggleRsvp`/`toggleVote`/`toggleRoleSlot` once). `lib/hooks.ts`'s `useAppNav()` centralizes the small set of "go somewhere" helpers (`openEvent`, `openCircle`, and a legacy-key `setView` for components still written against the old view-name API) so the URL shapes live in one place instead of being hand-typed across components. `openCircle` always routes to `/circles/[id]` — which of two views renders there is decided inside that route by the circle's `type` (a neighborhood renders as a folder view), not by the URL — see Circles below.

Back/cancel buttons use whichever is actually correct for that button: `router.back()` where the point is literally "return to wherever I came from" (e.g. the circle page), or an explicit `router.push()` to a known parent route where the destination is fixed regardless of entry point (e.g. a cancelled event form always returns to `/events`). Real routing made some of these more correct than the original: opening an event from Home's dashboard now returns to Home instead of always dumping into the full Events list.

The member-profile modal is deliberately not a route — it's opened identically from a dozen different pages (circles, attendee lists, member lists, role slots) and looks the same regardless of source. `components/providers/profile-modal-provider.tsx` holds it, mounted once in `app/(app)/layout.tsx`, and closes itself whenever the pathname changes (adjusted during render, not a `useEffect` — see the comment in that file) so it can't linger over content after a browser back/forward that bypasses its own close button.

### Data access layer
`lib/db/` (`members.ts`, `circles.ts`, `events.ts`, `resources.ts`) is the seam between the app and its data source — every function is `async` (`getMembers`, `getMemberById`, `getMemberByEmail`, `updateMember`, `getCircles`, `getCircleById`, `getCirclesByMember`, `updateCircle`, `getEventsForMember`, `createEvent`, `setRsvp`, ...) and is backed by a real, self-hosted Postgres database via Drizzle ORM. `lib/db/schema.ts` holds every Drizzle table definition (`members`, `circles`/`circle_members`/`circle_resources`, `events`/`event_rsvps`/`event_votes`/`roles`/`role_members`, plus Better Auth's own `user`/`session`/`account`/`verification` tables — see Authentication) and `lib/db/client.ts` opens the one real connection (`drizzle(process.env.DATABASE_URL)`). **Wrapping rule:** no file outside `lib/db/` (and `lib/better-auth.ts`, for the auth tables) may import `drizzle-orm` or `lib/db/schema.ts` directly — every other file reaches data through the plain async functions these files export, so the app is never tightly coupled to Drizzle itself. The DAL reassembles join tables into the arrays the app types expect (`Circle.members`, `Event.rsvps`/`votes`/`roles`) and normalizes Postgres's `HH:MM:SS` `time` back to the app's `HH:MM`.

Local dev runs Postgres via `docker-compose.yml` (`docker compose up -d`); schema changes go through `drizzle-kit` (`npm run db:generate` to diff `lib/db/schema.ts` into a new SQL file under `drizzle/`, `npm run db:migrate` to apply it). `scripts/seed.ts` (`npm run db:seed`) inserts `lib/data.ts`'s fixtures into a freshly-migrated database — `lib/data.ts` is seed-script input only; no app code imports it. The live beta is seeded separately: `npm run db:seed:beta` (`scripts/seed-beta.ts`) reads a **gitignored** `seed/beta.json` — one city, one neighborhood, one council inside it, and the people (all residents; those marked `inCouncil` are on the council) — because it holds real names and emails and must never be committed; `seed/beta.example.json` documents the shape with fake data. It also creates each person's login (a Better Auth user for their email — sign-up is off, so this is the only way to sign in) and refuses to run against a database that already has members. Both scripts share `scripts/seed-core.ts`.

`app/(app)/layout.tsx` is the one place a Server Component fetches through the DAL and hands the result to a Client Component as props: it calls `getEventsForMember(currentUserId)`/`getCircles()`/`getMembers()` and passes them into `AppStateProvider` as `initialEvents`/`initialCircles`/`initialMembers` (plus the signed-in member as `initialProfile`), which seed its `useState` calls. Components read the live roster and circles through `lib/hooks.ts` (`useMembers()`, `useMemberById()`, `useCircles()`, `useCirclesById()`), never from static data. `AppStateProvider` is a Client Component, though, and a real Postgres driver can't run in a browser bundle — so its mutators don't call `lib/db/` directly. They call `lib/db/actions.ts` instead: thin `"use server"` wrappers around the same DAL writes. Event and resource writes are authorized against the session and return `{ ok, value | error }` (Next sanitizes thrown messages in production, so a `UserFacingError` — the base of `EventError`/`ResourceError`, in `lib/db/errors.ts` — is caught in `asMember` and returned as data); the event actions are intent-specific (`createEventAction`, `updateEventDetailsAction`, `setRsvpAction`, `setVoteAction` — for meetings and proposals alike — `toggleRoleSlotAction`), never a general patch, because the server computes `rsvps`/`votes`/`roles` from the session member rather than trusting client-supplied arrays. `updateCircleAction`/`updateMemberAction` are still unauthenticated fire-and-forget calls (`.catch(console.error)`, no rollback) — real authorization/retry handling for those is future work. The event mutators are optimistic like the rest, but reconcile through `syncEvent` in `AppStateProvider`: they adopt the server's event on success and roll back with an error toast on refusal; `createEvent`/`updateEventDetails` instead await the server and return a result so the form can show a refusal inline.

### Circles and the Circles browser
Everything that scopes something is a **circle**. The city ("Providence") is the root circle; neighborhoods, councils, collectives, and co-ops are circles inside it, and circles nest. Every circle has a `parentId` (the root's is `null` — exactly one row, enforced by a unique partial index) and a `type`: `neighborhood | council | collective | cooperative | other`. Only `neighborhood` has behavior (a member's *home* circle; see below); the rest are display/filter labels (`CIRCLE_TYPE_LABEL` in `lib/circles.util.ts`). Membership is always explicit — a `circle_members` row — for every type, neighborhoods included; there are no derived rosters. `circle_members` carries its circle's `type` through a composite FK to `circles(id, type)`, which lets a partial unique index limit each member to **one neighborhood circle** (their `Member.homeCircleId`) with no trigger. Membership in a sub-circle is independent of its parent.

`lib/circles.util.ts`'s pure helpers are the seam everything else reads the tree through: `indexCircles` (id → circle lookup, `CirclesById`), `isCircleMember`, `circleChildren`, `circleNeighborhood` (the circle itself if it's a neighborhood, else its nearest neighborhood ancestor — `null` means citywide; used for the place chip and "local to my neighborhood" checks), `circleAncestors` (root-to-leaf, for breadcrumbs), `circleDescendantIds` (whole subtree, for search), `circlesForMember`, `sharesCircleWith` (gates avatar photos), and the event-audience trio `isCircleAudience`/`circlesForAudience`/`audienceLabel` (see Events belong to a circle below) — `isCircleMember` stays *explicit* membership on purpose, so everyone isn't implicitly in the root for rosters, resources or `sharesCircleWith`. Circles are **public**: any signed-in member can see any circle's page and roster (only an event's visibility is restricted — see Events belong to a circle below). A member may belong to no neighborhood (`homeCircleId` is nullable), so the UI tolerates that.

Browsing is one **Circles** browser at `/circles`, split across views since the city root and a neighborhood folder show meaningfully different things: `components/circles/circles-root.page.tsx`'s `CirclesRootPage` (`/circles` with no id) shows every circle directly under the root — neighborhoods and citywide groups — as folders, with no people grid; `components/circles/neighborhood.page.tsx`'s `NeighborhoodPage` (`/circles/[id]` for a `neighborhood`-type circle) shows its direct children as folders (`CircleCard`) and its members as files (`components/circles/member-card.tsx`'s `MemberCard`), with breadcrumbs and a search that flattens its whole subtree; every other circle renders `circle.page.tsx`'s `CirclePage` (which also has a "Sub-circles" section), with its manage form one level deeper at `/circles/[id]/manage` (`manage-circle.page.tsx`'s `ManageCirclePage`). Both browse views share `components/shared/folder-grid.tsx`'s `FolderGrid` (also reused by Home's "My circles" speed dial). Keying by the circle's own stable id means reparenting one (its Scope field on the manage page — neighborhoods or the city root are the offered parents for now) never changes its URL. `useAppNav()`'s `openCircle` constructs the URL — always route through it rather than hand-typing `/circles/${id}`. Folders split into a **Councils** grid (`type === "council"`) above an **Organizations** grid (everything else) inside a neighborhood.

`CircleCard`'s type eyebrow is controlled separately from its scope chip via `showKindEyebrow` (default: on for everything but a neighborhood), and its scope chip via `showScopeChip` (default on): both hide on every card while browsing *inside* a folder (`NeighborhoodPage`, `CirclePage`'s Sub-circles), since every card there structurally shares the folder's own neighborhood; they show at the Circles root and in Home's speed dial, which are flat, mixed-scope lists. `MemberCard`'s neighborhood chip follows the same `showScopeChip` reasoning. `NeighborhoodPage` shows a small teal home icon next to its title when it's the viewer's own home neighborhood (`circle.id === profile.homeCircleId`).

### Circle resources
A circle can attach **resources** — links (a shared drive, a doc), each shown with a folder or file icon the person adding it picks — that only that circle's **members** can see. They render as the first section (above About) of `CirclePage` (`components/circles/resources-section.tsx`) only when the viewer is a member; a non-member sees nothing, not even a placeholder. They apply to circles that have a detail page, so **not** neighborhoods (whose folder view has no such section, and the server refuses to add one). Any member of the circle can add, edit, or remove a resource, each saving immediately in its own modal rather than as part of the Manage form. A resource is `{ title, url, icon: "folder" | "file" }`, shown in the order added; links must be `http(s)` and open in a new tab (`lib/resources.util.ts`'s `validateResourceInput` is shared by the form for instant feedback and by the server as the real check).

Because circles themselves are public — the whole `circles` array is sent to every signed-in member — resources are deliberately **not** a field on `Circle`: they live in their own table and their own AppState slice, and the privacy boundary is enforced on the server, not in the UI. `lib/db/resources.ts` is the only place it lives: `getResourcesForMember(memberId)` returns only resources of circles that member belongs to (`app/(app)/layout.tsx` calls it with the session's member, so a non-member's browser never receives a circle's resources), and every write there re-checks membership and re-validates input, throwing a `ResourceError`. It takes the member id as an argument and never touches the session itself, so it can be exercised directly; `lib/db/actions.ts`'s `createResourceAction`/`updateResourceAction`/`deleteResourceAction` supply that id from `getCurrentUserId()` (never a client-supplied one) and return `{ ok, value | error }` result objects rather than throwing, since Next sanitizes a thrown error's message in production. These are the app's first server-side authorization; `updateCircleAction`/`updateEventAction`/`updateMemberAction` still trust the caller. Unlike every other mutator, `AppStateProvider`'s `addResource`/`updateResource`/`removeResource` are **await-then-update**, not optimistic: the server can refuse and generates the id, so state changes only after it accepts. New circle types or "wiki"-style pages that want resources should render `ResourcesSection` the same way (members only) rather than reading `resources` for non-members.

### Authentication
Real auth now — Better Auth's email-otp plugin, still passwordless: the welcome page (`app/page.tsx`, outside the `(app)` group, no session required) collects an email and a one-time code. Its "Demo accounts" button lists members' emails, fetched by that server component (the page sits outside `AppStateProvider`) and dropped entirely in a production build so real addresses never ship to an unauthenticated visitor. `lib/better-auth.ts` is the only file that imports `better-auth` itself (matching the DAL's wrapping rule above) — it builds the `betterAuth({...})` instance with the Drizzle adapter (pointed at `lib/db/schema.ts`'s `user`/`session`/`account`/`verification` tables), `emailAndPassword: { enabled: false }` (this app has never had a password), and the `emailOTP` plugin configured with `disableSignUp: true` — a member without a matching seeded email should get the same "we don't recognize that email yet" rejection the old mock gave, not a new account. There's still no real email provider: `sendVerificationOTP` doesn't send anything, and `requestLoginCode()` (`lib/auth.ts`) reads the code straight back out via `auth.api.getVerificationOTP()` (a Better Auth endpoint marked server-only — never exposed over HTTP) so the welcome page can keep showing it inline as an explicit "dev mode" hint.

`lib/auth.ts` still holds the three Server Actions the welcome page calls (`requestLoginCode`, `verifyLoginCode`, `logout` — same names/signatures as the mock version, so no call site changed), now calling `auth.api.sendVerificationOTP`/`getVerificationOTP`/`signInEmailOTP`/`signOut` instead of an in-memory pending-code `Map` and a plain cookie. Session cookies are Better Auth's own (`better-auth.session_token`), written via the `nextCookies()` plugin (must be last in the plugins array) — it forwards `Set-Cookie` headers from an `auth.api.*` call made inside a Server Action through `next/headers`'s `cookies()` automatically, which is what lets `lib/auth.ts` call `auth.api.*` directly with no client-side `authClient` and no mounted catch-all route handler. `lib/session.ts`'s `getCurrentUserId()` calls `auth.api.getSession()`, then looks the session's user back up by email via `getMemberByEmail()` to get this app's own `Member.id` — Better Auth's own user id is deliberately not linked to a member by foreign key (see `lib/db/schema.ts`'s comment on the `user` table); email is the one field both systems already agree on. `getCurrentUserId()` stays a separate file from `lib/auth.ts` on purpose — mixing a plain `next/headers`-using helper into a Server Actions file broke importing those actions from the Client Component welcome page, since Next tried to bundle the whole module for the client.

`proxy.ts` at the project root (not `middleware.ts` — Next 16 renamed the convention, and the exported function must be named `proxy`) is the primary route gate, and can't hold a real DB connection itself (middleware runs on the Edge runtime, incompatible with Drizzle's Node-only Postgres driver) — so it uses `better-auth/cookies`' `getSessionCookie()`, a presence-only check (decodes the cookie, doesn't hit the DB) that's safe there. `/` is explicitly excluded in the function body to avoid a redirect loop. `app/(app)/layout.tsx` calls `getCurrentUserId()` (a real, DB-validated check) and redirects defensively on top of proxy's cheap one — same division of labor the mock auth already had, not new.

The email + one-time-code shape maps closely onto how Better Auth's own `email-otp` plugin works, which is exactly why swapping to it didn't require redesigning the login flow — `requestLoginCode`/`verifyLoginCode`/`logout`'s signatures never changed. The one thing still missing before this is real: an actual email provider, since `sendVerificationOTP` is a no-op today.

### Data model
Three concepts, all in `lib/types.ts`: `Member`, `Circle`, and `Event`. `lib/data.ts`'s `MEMBERS`/`CIRCLES`/`EVENTS` are the seed dataset only (read through `lib/db/` at runtime). Every event belongs to exactly one circle (`circleId`) and always has an `organizerId` — the member who created it and the only person who can edit it (`isEventOrganizer`). `circleId` is who the event is shown to (and who would be notified of it); it is *not* the host. An event is hosted either by its organizer or, when `hostCircleId` is set, by a circle — which need not be the one it's shown to (the Finance Council can host an event shown to The 903). A circle-hosted event starts as a proposal (`proposed`) — see Events belong to a circle below. `currentUserId` is a real, dynamic value resolved at login (see Authentication) and threaded through as a prop from `AppStateProvider` downward. Components go through `AppStateProvider`'s state (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, via `useAppState()` or the `lib/hooks.ts` wrappers) for everything, static or not.

### Governance is the trickiest business logic
Two things put an event to a vote, and in both a circle's own members are the voters: a **meeting** (`kind: "meeting"`, see `EVENT_KINDS` in `lib/governance.util.ts`) and a **circle-hosted proposal** (see Events belong to a circle below). Any circle can hold a meeting: it's an event whose circle is the one being asked to decide, proposed by a member, and confirmed once its votes reach a majority of that circle's own members — `voteThreshold(e, circlesById)` computes this live (`majority(members.length)`, i.e. `Math.floor(n / 2) + 1`, shared with the server's approval check; the exact fraction is still a placeholder pending a real decision, isolated to this one function on purpose). Anyone who can see a meeting is by construction in its circle's audience, so there's no separate eligibility gating on voting or the agenda. A meeting can't be held in the root circle (its roster is implicit, so there's no majority to compute), carry signup slots, or be circle-hosted (its circle *is* the voter). A meeting's confirmation is recomputed from its live votes; a proposal's approval is **latched** by the server (`events.approved_at`) and stays even if votes are later withdrawn. `lib/governance.util.ts` (`kindOf`, `isConfirmed`, `voteCount`, `voteThreshold`, `majority`, `scopeLabel`, `scopeNoun`, `isEventOrganizer`, `isMeeting`, `isCircleHosted`, `isProposal`, `isVoting` — a vote is what the event is waiting on right now, so it gets the orange row/banner — `isGoverned` — it has been through a vote at all, for the Status filter — and `eventTypeLabel`) encodes these rules as pure functions shared between the event list and detail views — extend that module rather than duplicating logic per component. They take the live `circlesById` lookup (`useCirclesById()`) as an explicit argument rather than reading static data, so they always reflect the current circle rosters. A federation-wide council flow (event kind `council`, proposals, ratification, neighborhood endorsements) existed and was removed as unused; it would return as a meeting hosted by the root circle with its child circles' endorsements.


### RSVP/vote state is duplicated by design
`rsvpState`/`voteState` (`{ [eventId]: true }`, current user only) exist alongside each event's own `rsvps`/`votes` arrays and are updated together in lockstep (see `toggleRsvp`, `toggleVote` in `AppStateProvider`). This lets "am I going?" render without scanning arrays while keeping counts/rosters correct everywhere else. Keep both updates atomic if these handlers change.

### Role-slotted events and time-based cancellation
Some events define `roles` (shift lead, librarian, etc.) with `min`/`max` instead of a plain RSVP list. Whether the shift is cancelled is *derived from the clock*, not stored: `lib/roles.util.js`'s `shiftNeedsSlots` (neutral, more than an hour out) flips to `shiftCancelled` inside the one-hour cancellation window (`inCancelWindow`) if a required role is still unfilled, and to `shiftEnded` after the end time. Don't cache these values — they must be recomputed on render.

### Events belong to a circle
An event's circle decides who can see it: only that circle's own members — not its parent or child circles — plus, for the root (city) circle, everyone, since everyone is implicitly in the city (`isCircleAudience` in `lib/circles.util.ts`; the implicit-root rule applies to events only). Enforcement is server-side: `getEventsForMember` in `lib/db/events.ts` only ever returns events in the member's circles or the root, so anything else is never sent to their browser (its `/events/[id]` 404s and it's absent from every list), and every write goes through a DAL function that takes the session's `memberId`: `createEvent` (requires the circle's audience, forces the organizer, generates the id and the starting rsvps/votes itself), `updateEventDetails` (organizer only; never changes circle, kind or organizer, and keeps signed-up slot members by role key), `setRsvp`, `setVote` and `toggleRoleSlot` (audience only; slot max and one-slot-per-person enforced). A member outside an event's audience gets the same "doesn't exist" error as for a missing event. An event's circle and host circle are locked after creation.

**Circle-hosted events.** The event form's "Hosted by" is a dropdown of the person and the (non-root) circles they belong to that are the chosen Circle itself or inside it (`isWithinCircle` in `lib/circles.util.ts`, re-checked by `createEvent` on the server) — so PVD Things can't host an event shown to The 903, while the Finance Council can — and changing the Circle drops a host that no longer fits; choosing a circle turns the form orange ("Propose event") and creates a proposal: only the host circle's members can see it (`getEventsForMember` and `canSee` in `lib/db/events.ts` are the SQL and per-row forms of the same rule — keep them in step) and only they can vote, each vote an approval only (not an RSVP, unlike a meeting). RSVPs and slot signups are refused until it's approved. The vote that reaches `majority(host circle size)` — decided on the server, under a row lock so concurrent votes can't each miss the others — sets `approved_at`; the proposer's own vote counts, so a one-member circle approves immediately. Once approved it becomes visible to `circleId`'s audience as well as staying visible to the host circle's members, reads as an ordinary event again (host shown as the circle, its organizer named), and can no longer be voted on. A proposal that's never approved just lapses after its date. The organizer alone edits it, including while it's a proposal; editing deliberately does **not** reset votes already cast — they stand. A meeting is unaffected: it stays a separate kind hosted by its own circle for its own members. `insertEvent` is the raw trusted insert only the seed scripts use. In the event form a "Circle" dropdown (the member's circles plus the city, home neighborhood first; meetings exclude the city) is who it's shown to, and slots are available on any ordinary event. `validateEventDraft` in `lib/events.util.ts` is the one pure check shared by the form and the DAL.


### Shared design tokens and components
The design system lives in one place now: the `@theme` block in `app/globals.css` (Tailwind v4 CSS-first config) — colors, fonts, and the type scale as CSS custom properties Tailwind utility classes read from. This used to be duplicated in a parallel `lib/theme.js` of JS constants for components still using inline `style={{...}}`; once the last such component was converted, `lib/theme.js` was deleted rather than left as dead weight — see Coding style below for how that migration worked. `components/shared/` holds the generic pieces reused across pages (`Eyebrow`, `PageHeader`, `TabbedPanel`, `SearchWithFilter`, `Tag`, `Chip`); `components/events/` has the event-specific reusable pieces (`DateTile`, `VoteButton`, `RsvpButton`) — reuse these rather than re-implementing per page. `components/shared/index.tsx` is a barrel re-exporting everything in the folder, so `import { Button, Label } from "@/components/shared"` works alongside (not instead of) importing a single file directly (`@/components/shared/button`) — both are valid, existing call sites weren't migrated to the barrel.

Toasts go through a `ToastProvider`/`useToast()` context (`components/shared/toast.jsx`) mounted in the true root `app/layout.jsx` — outside and above `app/(app)/layout.jsx`'s `AppStateProvider`, on purpose: it's the one provider both the unauthenticated welcome page and the authenticated app need, so the welcome page's login form gets `useToast()` for free. Components fire toasts via the hook rather than managing their own transient UI state.

## Code organization

Files are grouped by domain, not by component type: `components/shared/`, `components/circles/`, `components/events/`, `components/home/`, `components/profile/`, `components/game/`, `components/welcome/` — one component per file, with the file's kebab-case name matching its PascalCase export (`event.page.jsx` exports `EventPage`; see Coding style below for the `.page.jsx` suffix). `components/providers/` holds the two app-wide context providers (`app-state-provider.jsx`, `profile-modal-provider.jsx`) — they're components (they render JSX), just not ones any single domain owns. `components/shared/app-shell.jsx` is the nav wrapper (`TopBar` + `BottomNav`) rendered once in `app/(app)/layout.jsx` around every authenticated route; the button-press interaction CSS it used to carry in an inline `<style>` tag now lives in `app/globals.css` instead, since the unauthenticated welcome page needs those same classes and sits outside the tree `AppShell` wraps. `lib/` holds everything that isn't a component: `data.ts` (seed data, not imported by app code), `governance.util.ts` / `roles.util.ts` / `format.util.ts` / `circles.util.ts` / `events.util.ts` / `members.util.ts` (pure helper functions), `hooks.ts` (`useMembers`, `useCircles`, `useIsMobile`, `useAppNav`, ...), `auth.ts` / `session.ts` / `better-auth.ts` (auth — see Authentication), and the `lib/db/` subfolder (the data access layer — see that section) — these stay `.js` since they hold no JSX. When adding a new component, put it in the folder for the domain it belongs to; when adding cross-domain UI (used by 2+ domains), it belongs in `components/shared/`.

`app/` has three things at its root: `layout.jsx` (minimal — just `ToastProvider`), `page.jsx` (the unauthenticated welcome/login route — a thin wrapper rendering `components/welcome/welcome.page.jsx`'s `WelcomePage`, the same route-pages-wire/`components/`-render split used everywhere else), and the `(app)/` route group holding everything else plus its own `layout.jsx`. Within `(app)/`, each route mirrors the route list above one-to-one — each `page.jsx` is a thin client component that pulls data from `useAppState()`/`useProfileModal()` and wires navigation via `useAppNav()`/`useRouter()`, then hands everything to the actual UI component from `components/`. Keep that split: route pages own data-fetching-and-wiring, `components/` own rendering, so a component never has to know whether it's reached via routing or (hypothetically) something else. `proxy.js` sits at the project root, a sibling of `app/`, not inside it — that's a Next.js convention, not a choice.

## Coding style

- **Tailwind (v4) for styling, using the theme tokens — not inline `style={{...}}` objects, and not CSS Modules.** This is a reversal of an earlier decision: inline styles were deliberate while the app was a single 3900-line file being split apart (adding a build step then would have widened that migration's scope), but now that the split is done, Tailwind is in. The migration off inline styles + `lib/theme.js` is essentially complete — `lib/theme.js` itself has been deleted now that nothing imports it — except for a handful of components under the deprioritized federation-council flow (see Governance is the trickiest business logic below) that haven't been touched yet; that's expected, not a bug to "fix" as a drive-by. `components/shared/eyebrow.tsx` and `components/shared/tag.tsx` are reference examples of the converted style (utility classes, `bg-ink`/`text-soft`/`font-sans`/`text-eyebrow`/`tracking-wide` etc. from the `@theme` tokens in `app/globals.css`, arbitrary-value or fractional-spacing classes like `px-2.75`/`tracking-[0.04em]` where a design value doesn't land on a named Tailwind step). When writing a new component, use Tailwind. **This is how the migration actually happened, element by element**: whenever you touch an existing element for some other reason (adding an icon, fixing a style, anything), convert that specific element to Tailwind classes and remove its `style` object as part of the edit, rather than adding to the inline style just because the rest of the file still is. Elements in the same file you didn't otherwise need to touch stay as they are — that's still not a drive-by fix, only what you actually edited is. A handful of components still keep one genuinely dynamic per-instance inline `style` (e.g. a computed progress-bar `width`, `FloatingActionButton`'s `bottom` offset, `FolderGrid`'s `gridTemplateColumns`) — Tailwind can't express a runtime-computed value as a static class, so these are deliberate, not leftovers.
- **Prefer a shared component over re-declaring the same style/behavior inline at each call site, once a pattern is genuinely established across the app.** `components/shared/button.tsx`'s `Button` is the reference example: before it existed, every "Save"/"Cancel"/"+ Add X" button in the app re-typed its own `style={{...}}` object for the same filled/invert-on-press or outlined/`ink-press` look (see the button-pattern inventory this replaced — filled primary, outlined secondary, outlined danger, a compact size). `Button` takes `variant` (`primary`/`secondary`/`danger`), `accent` (`ink`/`flame`/`teal`, primary only), `size` (`default`/`compact`), and passes through `disabled`/`onClick`/etc. — a leading icon is just a child rendered before the label text (`<Button><PlusIcon .../>Add hours</Button>`), not a separate prop, since the underlying markup already puts children in that order. It is deliberately **not** used for icon-only controls (a row's `✕` remove button, a modal's dismiss `✕`) — those stay bespoke, since `Button` always renders a visible text label. This doesn't override the general "don't add abstractions beyond what's needed" rule — a one-off control specific to a single page still stays inline — but when you notice yourself copying the same button (or similar repeated UI) styling into a third or fourth file, that's the signal to extract it into `components/shared/` rather than keep duplicating it, the same way `Eyebrow`/`Tag`/`Chip` already work.
- **Inline text links get an underline** — this is what distinguishes "this bold text is clickable" from plain emphasis (e.g. `components/circles/circle.page.tsx`'s website link, or the "Last edited by {name}" button in the same file). This applies specifically to bare text sitting inline in body content, not to nav chrome (top bar tabs, the "Providence" brand mark, `BottomNav`) or anything already boxed/bordered as a button, pill, or card (e.g. the mailto pill in `profile-modal.tsx`) — those already read as clickable from their shape and position, so underlining them too would be redundant.
- Prefer a theme token over a raw value or one-off arbitrary class whenever one already covers it (e.g. `text-flame` over `text-[#e1530b]`, `text-eyebrow` over `text-xs` when it's actually an eyebrow) — the whole point of porting the tokens was to stop repeating the same hex codes and sizes across files. If a new value is genuinely needed in more than one place, add it to the `@theme` block rather than hardcoding it at each call site.
- **`clsx` for conditional/combined class names** (e.g. `components/shared/tag.tsx`'s filled/unfilled state) rather than hand-built template-literal string concatenation — chosen over `classnames` for being the smaller of the two with an equivalent API. Don't reach for `tailwind-merge` alongside it unless a real class-conflict-resolution need shows up (e.g. a component needing to override a token class a caller passed in); it solves a different problem than `clsx` and isn't installed.
- Comments are rare and rationale-only (explaining *why*, e.g. the note above `CANCEL_WINDOW_MS`) — the existing file is a good model for this; don't add comments narrating *what* the code does.
- **TypeScript (`.ts`/`.tsx`), not plain JavaScript.** This is a reversal of an earlier decision, the same way the Tailwind migration above reversed the inline-styles-while-splitting-the-file call: plain JS was fine for a prototype with no types worth enforcing yet, but the codebase outgrew that once real domain shapes (`Event`, `Org`, `Member`, `Role`, ...) were being passed through a dozen layers by hand. `tsconfig.json` runs with `strict: true` and `noUncheckedIndexedAccess: true` from the start, not staged in later — the codebase's existing defensive style (guards everywhere already) made that low-friction. `lib/types.ts` is the single source of truth for the domain model (`Member`, `Org`, `Event`, `Role`, `Host`, `CouncilProposal`, `ProposalDetails`, `EventKindKey`, ...) — import shapes from there rather than re-declaring a structurally-equivalent inline type at each call site. `Event` is one flat interface with its governance-only fields (`orgId`, `votes`, `scope`, `sponsor`, `endorsements`, `roles`, `membersOnly`) optional, not a discriminated union on `kind` — every real call site already guards these defensively, and a true union would force exhaustive narrowing rework across every existing `e.kind === "meeting"` check for no real safety gain here. Where governance logic reads several of those fields together, `lib/governance.util.ts`'s `isMeeting`/`isCouncil` type guards give real narrowing without touching call sites that don't need it. One known TS sharp edge worth knowing before you hit it: a `let` reassigned inside a `.map()`/`.filter()` callback does not narrow correctly when read afterward in the outer scope (TS keeps the pre-callback flow type there), and separately, narrowing a property (`e.sponsor &&`) does not survive into a nested closure (an `onClick`, etc.) — both need the value hoisted into its own `const` at the point where the narrowing is actually valid (see `app-state-provider.tsx`'s `ratifyCouncilProposal` and `event-masthead.tsx` for worked examples) rather than a bare `!` slapped on where the error surfaces.
- **All source filenames are kebab-case** (`org-card.tsx`, `app-state-provider.tsx`, `date-tile.tsx`), including files that export a React component. This applies to the filename only — the exported component/function identifiers inside stay normal JS/React naming (`export function EventPage`, `PascalCase` for components, `camelCase` for everything else), since JSX requires a capitalized identifier to treat something as a component.
- **`.tsx` for anything under `app/` or `components/`, `.ts` for `lib/`.** The split is by location, not by whether a given file happens to contain a JSX tag — everything that's part of the component tree is `.tsx`; plain data/logic modules are `.ts`. Imports never include the extension, so this is purely a naming convention, not something Next.js's resolver depends on.
- **A file's *role* is encoded as a dotted suffix before that extension, for the two roles common enough to be worth marking:** `.page.tsx` for a component that's the full top-level view for exactly one route (`circle.page.tsx` exports `CirclePage`, one of two views `app/(app)/circles/[id]/page.tsx` can render — see Circles above; also `manage-circle.page.tsx`, `event.page.tsx`, `edit-myself.page.tsx`, `home.page.tsx`, `circles-root.page.tsx` and `neighborhood.page.tsx` (the Circles browser's other views, rendered at `/circles` and `/circles/[id]` for a neighborhood respectively), `event-form.page.tsx`, `name-game.page.tsx`, `events-list.page.tsx`, `welcome.page.tsx`), and `.util.ts` for a `lib/` module whose entire export surface is pure helper functions (`governance.util.ts`, `roles.util.ts`, `format.util.ts`, `circles.util.ts`, `events.util.ts`, `members.util.ts`). The suffix replaces an existing `-page`/`-form`-type word in the base name rather than stacking on top of it (`manage-org-page.tsx` → `manage-org.page.tsx`, not `manage-org-page.page.tsx`). Not everything under `components/` or `lib/` gets a role suffix — only these two well-defined categories do: reusable/chrome components, providers, and one-off pieces (`circle-card.tsx`, `stat-card.tsx`, `app-state-provider.tsx`) stay plain kebab-case, and so do `lib/` modules that aren't collections of *pure* helper functions — `hooks.ts` is React hooks, `data.ts` is seed data, `types.ts` is the domain-model type module, and `lib/db/*.ts` / `lib/auth.ts` / `lib/session.ts` all have side effects (a database connection, cookies), which is exactly what disqualifies them despite being "helper functions" in a loose sense. When a new file clearly fits one of the two roles, name it that way from the start; don't invent additional suffixes (`.hook.ts`, `.provider.tsx`, etc.) without deciding that expansion explicitly first.
