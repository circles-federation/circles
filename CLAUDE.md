# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Convene is a prototype for a federated, neighborhood-scale coordination tool — members, organizations (co-ops/collectives), events, and a lightweight direct-democracy governance layer (neighborhood assemblies and a federation council), on top of a design system carried over from "The Commons Institute" (ink-on-white, Helvetica/Georgia, zero border-radius, hairline rules).

It's a Next.js (App Router, JavaScript) app with no backend — `lib/data.js` is the entire dataset, and all other state lives in `components/providers/app-state-provider.jsx`, mounted once in `app/layout.jsx`. The app was originally prototyped as a single ~3900-line file, then split into `lib/` and `components/`, then moved off a single-component view-state switch onto real routes; none of the earlier single-file structure exists anymore, so treat the current tree as the spec.

## Setup & commands

- `npm run dev` — local dev server
- `npm run build` — production build (also the fastest way to catch broken imports/syntax across the app)
- `npm run lint` — ESLint

There is no test runner yet — deliberately deferred until the app grows past prototype stage.

## Architecture

### Routing and shared app state
Real Next.js routes: `/home`, `/federation`, `/people`, `/organizations`, `/organizations/[id]`, `/organizations/[id]/manage`, `/events`, `/events/new`, `/events/[id]`, `/events/[id]/propose`, `/profile/edit`, `/game`. `/` just `redirect()`s to `/home`. There's still no backend, so routes can't share React state via props the way a single root component could — `components/providers/app-state-provider.jsx` holds everything that used to be `useState` in that root component (`events`, `orgs`, `councilProposals`, `rsvpState`, `voteState`, `profile`, and their mutators) and is mounted once in `app/layout.jsx`; every route reads it via `useAppState()`.

Mutators on `AppStateProvider` are pure state + toast now — they never navigate. Where the old single-view app followed a mutation with a view change (e.g. jump to the newly created event), that's the calling route's job, since only the route has the router; `createEvent` and `proposeEndorsingAssembly` return the created event so the caller can `router.push` its URL. `lib/hooks.js`'s `useAppNav()` centralizes the small set of "go somewhere" helpers (`openEvent`, `openOrg`, `openNeighbors`, `openLocalOrgs`, and a legacy-key `setView` for components still written against the old view-name API) so the URL shapes live in one place instead of being hand-typed across components.

Back/cancel buttons use whichever is actually correct for that button: `router.back()` where the point is literally "return to wherever I came from" (e.g. the organization page), or an explicit `router.push()` to a known parent route where the destination is fixed regardless of entry point (e.g. a cancelled event form always returns to `/events`). Real routing made some of these more correct than the original: opening an event from Home's dashboard now returns to Home instead of always dumping into the full Events list.

The member-profile modal is deliberately not a route — it's opened identically from a dozen different pages (directory, attendee lists, member lists, role slots) and looks the same regardless of source. `components/providers/profile-modal-provider.jsx` holds it, mounted once in the layout, and closes itself whenever the pathname changes (adjusted during render, not a `useEffect` — see the comment in that file) so it can't linger over content after a browser back/forward that bypasses its own close button.

`/events/[id]/propose` is one route serving two governance flows — a confirmed assembly proposing a federation council, or a council getting an endorsing assembly proposed in the viewer's neighborhood. Which applies is fully determined by the event's own `kind`, so the mode isn't part of the URL.

`/people` and `/organizations` read `?hood=`/`?level=` as an optional initial filter (e.g. Home's "Neighbors" card links to `/people?hood=The 903`). Both wrap their `useSearchParams()` call in a `<Suspense>` boundary in their own `page.jsx` — Next.js requires this for static prerendering. Follow the same pattern if another route needs `useSearchParams()`.

### Data model
Three flat arrays in `lib/data.js` — `MEMBERS`, `ORGS`, `EVENTS` — are the entire dataset (no backend). `ORGS_BY_MEMBER` is a derived lookup built once at module load. `CURRENT_USER_ID` and `HOME_HOOD` fix which member and neighborhood the whole UI is viewed as. Components treat `lib/data.js` as read-only and go through `AppStateProvider`'s state (`events`, `orgs`, `rsvpState`, `voteState`, `profile`, via `useAppState()`) for anything that changes at runtime.

### Governance is the trickiest business logic
Events are either ordinary or "governance" (`assembly` or `council`, see `EVENT_KINDS` in `lib/data.js`). Assemblies are scoped to one neighborhood and confirm by resident vote count reaching a threshold; councils are federation-wide and confirm once a majority of neighborhoods *endorse* them (each neighborhood endorses by passing its own assembly vote). A council is proposed via `councilProposals` (state on `AppStateProvider`) and only becomes a real event once its sponsoring assembly ratifies it (`ratifyCouncilProposal`) — until then it doesn't appear anywhere events are listed. `lib/governance.util.js` (`kindOf`, `isConfirmed`, `councilConfirmed`, `canVote`, `canReadDetails`, `neighborhoodMajority`, `isExclusive`, `isHostOrgMember`) encodes these rules as pure functions shared between the event list and detail views — extend that module rather than duplicating logic per component.

### RSVP/vote state is duplicated by design
`rsvpState`/`voteState` (`{ [eventId]: true }`, current user only) exist alongside each event's own `rsvps`/`votes` arrays and are updated together in lockstep (see `toggleRsvp`, `toggleVote` in `AppStateProvider`). This lets "am I going?" render without scanning arrays while keeping counts/rosters correct everywhere else. Keep both updates atomic if these handlers change.

### Role-slotted events and time-based cancellation
Some events define `roles` (shift lead, librarian, etc.) with `min`/`max` instead of a plain RSVP list. Whether the shift is cancelled is *derived from the clock*, not stored: `lib/roles.util.js`'s `shiftNeedsSlots` (neutral, more than an hour out) flips to `shiftCancelled` inside the one-hour cancellation window (`inCancelWindow`) if a required role is still unfilled, and to `shiftEnded` after the end time. Don't cache these values — they must be recomputed on render.

### Members-only ("exclusive") events
An event hosted by an org with `membersOnly: true` is visible to everyone but only RSVP-able (and notification-eligible) by that org's members — `isExclusive` / `isHostOrgMember` in `lib/governance.util.js` gate this, independently of the governance rules above.

### Shared design tokens and chrome
The design system exists in two parallel representations that must be kept in sync by hand: `lib/theme.js` (JS constants — `INK`, `PAPER`, `SOFT`, `FAINT`, `FLAME`, `LEAF`, `TEAL`, `PLUM`, `sans`, `serif`, the `TYPE` scale) for components still using inline `style={{...}}`, and the `@theme` block in `app/globals.css` (Tailwind v4 CSS-first config) for components written with Tailwind utility classes. Both must list the exact same colors/fonts/sizes — see Coding style below for which one a given component should use. `components/chrome/` holds the generic pieces reused across pages (`Eyebrow`, `PageHeader`, `TabbedPanel`, `SearchWithFilter`, `Tag`, `Chip`, `form-fields`); `components/events/` has the event-specific reusable pieces (`DateTile`, `VoteButton`, `RsvpButton`) — reuse these rather than re-implementing per page.

Toasts go through a `ToastProvider`/`useToast()` context (`components/chrome/toast.jsx`) mounted once in `app/layout.jsx` (outermost, above `AppStateProvider`, since state mutations need to fire toasts) — components fire toasts via the hook rather than managing their own transient UI state.

## Code organization

Files are grouped by domain, not by component type: `components/chrome/`, `components/directory/`, `components/orgs/`, `components/events/`, `components/home/`, `components/profile/`, `components/game/` — one component per file, with the file's kebab-case name matching its PascalCase export (`event.page.jsx` exports `EventPage`; see Coding style below for the `.page.jsx` suffix). `components/providers/` holds the two app-wide context providers (`app-state-provider.jsx`, `profile-modal-provider.jsx`) — they're components (they render JSX), just not ones any single domain owns. `components/chrome/app-shell.jsx` is the persistent nav wrapper rendered once in `app/layout.jsx` around every route. `lib/` holds everything that isn't a component: `theme.js` (design tokens), `data.js` (seed data + lookups), `governance.util.js` / `roles.util.js` / `format.util.js` (pure helper functions), `hooks.js` (`useIsMobile`, `useAppNav`) — these stay `.js` since they hold no JSX. When adding a new component, put it in the folder for the domain it belongs to; when adding cross-domain UI (used by 2+ domains), it belongs in `components/chrome/`.

`app/` mirrors the route list above one-to-one — each `page.jsx` is a thin client component that pulls data from `useAppState()`/`useProfileModal()` and wires navigation via `useAppNav()`/`useRouter()`, then hands everything to the actual UI component from `components/`. Keep that split: route pages own data-fetching-and-wiring, `components/` own rendering, so a component never has to know whether it's reached via routing or (hypothetically) something else.

## Coding style

- **Tailwind (v4) for styling, using the theme tokens — not inline `style={{...}}` objects, and not CSS Modules.** This is a reversal of an earlier decision: inline styles were deliberate while the app was a single 3900-line file being split apart (adding a build step then would have widened that migration's scope), but now that the split is done, Tailwind is in. Most existing components still use inline styles + `lib/theme.js` and haven't been migrated yet — that's expected, not a bug to "fix" as a drive-by. `components/chrome/eyebrow.jsx` and `components/chrome/tag.jsx` are the reference examples of the converted style (utility classes, `bg-ink`/`text-soft`/`font-sans`/`text-eyebrow`/`tracking-wide` etc. from the `@theme` tokens in `app/globals.css`, arbitrary-value or fractional-spacing classes like `px-2.75`/`tracking-[0.04em]` where a design value doesn't land on a named Tailwind step). Match whichever pattern the file you're editing already uses; when writing a new component, use Tailwind.
- Prefer a theme token over a raw value or one-off arbitrary class whenever one already covers it (e.g. `text-flame` over `text-[#e1530b]`, `text-eyebrow` over `text-xs` when it's actually an eyebrow) — the whole point of porting the tokens was to stop repeating the same hex codes and sizes across files. If a new value is genuinely needed in more than one place, add it to the `@theme` block (and to `lib/theme.js` if inline-style code still needs it too) rather than hardcoding it at each call site.
- **`clsx` for conditional/combined class names** (e.g. `components/chrome/tag.jsx`'s filled/unfilled state) rather than hand-built template-literal string concatenation — chosen over `classnames` for being the smaller of the two with an equivalent API. Don't reach for `tailwind-merge` alongside it unless a real class-conflict-resolution need shows up (e.g. a component needing to override a token class a caller passed in); it solves a different problem than `clsx` and isn't installed.
- Comments are rare and rationale-only (explaining *why*, e.g. the note above `CANCEL_WINDOW_MS`) — the existing file is a good model for this; don't add comments narrating *what* the code does.
- Plain JavaScript, not TypeScript.
- **All source filenames are kebab-case** (`org-card.jsx`, `app-state-provider.jsx`, `form-fields.jsx`), including files that export a React component. This applies to the filename only — the exported component/function identifiers inside stay normal JS/React naming (`export function EventPage`, `PascalCase` for components, `camelCase` for everything else), since JSX requires a capitalized identifier to treat something as a component.
- **`.jsx` for anything under `app/` or `components/`, `.js` for `lib/`.** The split is by location, not by whether a given file happens to contain a JSX tag — everything that's part of the component tree is `.jsx`; plain data/logic modules are `.js`. Imports never include the extension, so this is purely a naming convention, not something Next.js's resolver depends on.
- **A file's *role* is encoded as a dotted suffix before that extension, for the two roles common enough to be worth marking:** `.page.jsx` for a component that's the full top-level view for exactly one route (`org.page.jsx` exports `OrgPage`, rendered by `app/organizations/[id]/page.jsx`; also `manage-org.page.jsx`, `event.page.jsx`, `edit-myself.page.jsx`, `home.page.jsx`, `directory.page.jsx`, `new-event-form.page.jsx`, `governance-proposal-form.page.jsx`, `name-game.page.jsx`, `events-list.page.jsx`, `org-directory.page.jsx`, `federation-home.page.jsx`), and `.util.js` for a `lib/` module whose entire export surface is pure helper functions (`governance.util.js`, `roles.util.js`, `format.util.js`). The suffix replaces an existing `-page`/`-form`-type word in the base name rather than stacking on top of it (`manage-org-page.jsx` → `manage-org.page.jsx`, not `manage-org-page.page.jsx`). Not everything under `components/` or `lib/` gets a role suffix — only these two well-defined categories do: reusable/chrome components, providers, and one-off pieces (`org-card.jsx`, `stat-card.jsx`, `app-state-provider.jsx`) stay plain kebab-case, and so do `lib/` modules that aren't collections of helper functions (`hooks.js` is React hooks, `data.js` is seed data, `theme.js` is design tokens, `feature-flags.js` is a flag constant). When a new file clearly fits one of the two roles, name it that way from the start; don't invent additional suffixes (`.hook.js`, `.provider.jsx`, etc.) without deciding that expansion explicitly first.
