# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Circles is a prototype for a federated, neighborhood-scale coordination tool — members, circles (the city, its neighborhoods, and the councils, collectives, and co-ops inside them — one universal, nestable concept), events, and a lightweight direct-democracy governance layer (any circle's meetings and the events it hosts, decided by its members' consent), on top of a design system carried over from "The Commons Institute" (ink-on-white, Helvetica/Georgia, zero border-radius apart from round icon buttons and the pill-shaped circle chip, hairline rules).

It's a Next.js (App Router, TypeScript) app backed by a real, self-hosted Postgres database (via a data-access layer, `lib/db/`, using Drizzle ORM — see Data access layer) — `lib/data.ts` is now seed-script input rather than something any app code reads directly, and all runtime state lives in `components/providers/app-state-provider.tsx`, mounted in `app/(app)/layout.tsx`. Auth is real too (Better Auth's email-otp plugin, no password — see Authentication), gating everything except the welcome page at `/`; login codes are emailed through `lib/email/` (SMTP — see Email). The app was originally prototyped as a single ~3900-line file, then split into `lib/` and `components/`, then moved off a single-component view-state switch onto real routes; none of the earlier single-file structure exists anymore, so treat the current tree as the spec.

## Setup & commands

- `npm run dev` — local dev server
- `npm run build` — production build (also the fastest way to catch broken imports/syntax across the app)
- `npm run lint` — ESLint

There is no test runner yet — deliberately deferred until the app grows past prototype stage.

## Architecture

### Routing and shared app state
`/` is the unauthenticated welcome page (email + one-time-code login — see Authentication below), `/apply` the unauthenticated application to join, `/terms` and `/privacy` its public beta terms and privacy notes (see Applications below), and `/e/[token]` and `/e/stop/[id]`, an event someone has shared and a guest's way to stop its emails (see Sharing an event below); every other route lives under the `app/(app)/` route group (a URL-invisible folder — `app/(app)/home/page.tsx` still serves `/home`), which requires a session: `/home`, `/circles`, `/circles/new`, `/circles/[id]`, `/circles/[id]/manage`, `/circles/[id]/manage/details`, `/circles/[id]/manage/roles`, `/circles/[id]/manage/wiki`, `/circles/[id]/bulletin/new` (a neighborhood's is New post: see Neighborhood bulletin), `/circles/[id]/bulletin/[resourceId]`, `/circles/[id]/tasks/new`, `/circles/[id]/tasks/[taskId]`, `/circles/[id]/invite`, `/invitations/[id]`, `/proposals/[id]`, `/events`, `/events/new`, `/events/[id]`, `/events/[id]/edit`, `/profile/[id]`, `/profile/edit`, `/settings`, `/settings/notifications`, `/settings/availability`, `/game`, and for system admins `/admin/review`, `/admin/applications/[id]` and `/admin/photos/[memberId]` (`/admin/applications` redirects to `/admin/review`). Every circle — neighborhood or not, however deep it sits in the tree — lives under `/circles/[id]`, keyed by its own stable id rather than its position in the hierarchy (see Circles below). Routes can't share React state via props the way a single root component could — `components/providers/app-state-provider.tsx` holds everything that used to be `useState` in that root component (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, and their mutators) and is mounted once in `app/(app)/layout.tsx`, seeded from props that layout fetches server-side via `lib/db/`; every route beneath it reads the state via `useAppState()`.

Mutators on `AppStateProvider` are pure state + toast now — they never navigate. Where the old single-view app followed a mutation with a view change (e.g. jump to the newly created event), that's the calling route's job, since only the route has the router; `createEvent` returns the created event so the caller can `router.push` its URL. Each mutator also calls the matching `lib/db/` write, alongside (not instead of) its own `setState` — see Data access layer below. Compute the value a mutator writes to the DAL synchronously from the state already in scope, never by reading a `let` that a `setState` updater assigned: React doesn't run a functional updater inline, so that value is still its initial one on the next line (this silently dropped every DB write from `toggleRsvp`/`toggleVote`/`toggleRoleSlot` once). `lib/hooks.ts`'s `useAppNav()` centralizes the small set of "go somewhere" helpers (`openEvent`, `openCircle`, and a legacy-key `setView` for components still written against the old view-name API) so the URL shapes live in one place instead of being hand-typed across components. `openCircle` always routes to `/circles/[id]` — which of two views renders there is decided inside that route by the circle's `type` (a neighborhood renders as a folder view), not by the URL — see Circles below.

**Back lives in the top bar, not on the page.** Like Flutter's automatic app-bar back button, `TopBar` (`components/shared/top-bar.tsx`) shows a ghost arrow button on every route except the three tab roots (`/home`, `/circles`, `/events`); pages don't render their own. Its title is always the current page's (`pageTitle`: the tab name at a root, a circle's or event's own name on its page, "New event", "Manage circle" and so on), on desktop as well as mobile, so the Circles root, neighborhood folders and the Events list carry no title of their own. It has no shadow or edge: it fades from solid white behind its title and buttons to transparent at its foot, so the page shows clear up to the title row as it scrolls under. The bar is laid out the same on every screen size: the title on the left and the page's action on the right. On desktop the tabs sit in the centre, centred on the bar itself, with the title stopping short of them; on mobile they're in `BottomNav` instead. The action is an icon button, the icon in a filled circle (`IconButtonCircle` in `top-bar.tsx`). A primary one, the page's main job such as Save, is blue (`--color-action`), except a Save that proposes a change for its circle's consent (Manage circle's Details and Roles, the event form's Propose event and Propose meeting for a new circle-hosted event or a meeting that needs consent, New circle's Propose circle for a Circle in a neighborhood, and a neighborhood's Propose post), which is orange (`--color-flame`) with the proposals' hand icon (`variant: "propose"`); a secondary one, such as Manage or Edit, is ink. A link-style action comes from `TopBar`'s `pageAction()`: a circle's Manage for its members (a cog) and your own profile's Edit (a pencil). Where a page has several things to offer, the action is a menu instead (`TopBarMenu`, `components/shared/top-bar-menu.tsx`, the same raised circle, which stays pressed in while its menu is open; see Home for how it behaves): Home's is your photo (`ProfileMenu`: My profile, Settings); an event's is the page's own (`useTopBarMenu`, built like `useTopBarAction`, for items that run the page's code): Edit for whoever manages it, Share and Stop sharing, and Add to calendar (shown greyed out until you've RSVPed: a menu item can be `disabled`); and elsewhere it's an ellipsis on ink (`pageMenu` in `top-bar.tsx`), the one place to look for what a page offers: on the Events list, New event and New meeting (`/events/new?kind=meeting`, the form starting on its Meeting tab as switching to it would; the form keeps its own Event/Meeting switch, since a circle page's Events tab opens it too), and on the Circles browser New circle (a ring, `RingIcon`) at the root and on a neighborhood, which adds Post on bulletin (a +) for a member of a Circle in it and, on your own neighborhood once someone else lives there, Learn names (a teal play). A page can instead put an action of its own there, one that runs its code rather than linking somewhere, with `useTopBarAction` (`components/providers/top-bar-action-provider.tsx`, mounted in `app/(app)/layout.tsx`), which takes precedence over `pageAction()`. Each form's Save is one: the Manage circle pages' and Edit profile's checks stay disabled until something changes, and the event form's submit (Create, Propose or Save changes) until the event is valid, with a validation error, at the foot of the form, scrolled into view. The action lives only in the top bar, never also on the page: there are no masthead Manage or Edit buttons and no Save or Cancel buttons at the foot of a form, and leaving a form is the top bar's Back. A page's other main action, what a tab offers to do (add to the bulletin, invite, host an event), is its **floating action button**: the page says what it is with `useFloatingAction` (`components/providers/floating-action-provider.tsx`, mounted in `app/(app)/layout.tsx`, built like `useTopBarAction`), and the chrome draws `FloatingActionButton` (`components/shared/floating-action-button.tsx`: round, frosted-glass white, an ink rule, a soft shadow) where it belongs — `AppShell` above the right end of `BottomNav` on a phone (dropping to where the nav was while it's away, with room left at the end of the page to scroll clear of it), `SimpleTabs` at the right end of the page's tab row wider, the small size beside the tabs it changes with, so that's plain to see (a page using one wider needs a tab row; a page without one will need a place decided for it). Pages never place one themselves; the welcome page, outside the app, is the one exception. Which tab is highlighted (the top bar's tabs on desktop, `BottomNav` on a phone) is one rule for both, `activeTab` in `lib/nav.util.ts`: a page you browse to belongs to its tab (every circle page, every event page, and the name game, played from your neighborhood's page, and Home with the pages only it leads to: profiles), while a page for doing something belongs to none, however it was reached, from the top bar's action or a button in the page (Settings, Edit profile, a new circle, a new or edited event, a circle's Manage, Invite and bulletin forms, an invitation, a proposal, an admin's review pages). On such a page `BottomNav` slides down off the screen and fades (and back on leaving), like a native app's pushed screen, which is left by the top bar's Back: it stays mounted for the transition, `inert` while it's away, and `AppShell` drops the nav's bottom padding with it. A new route needs a place in it. It goes back through `useGoBack()` (`components/providers/back-handler-provider.tsx`). That calls `router.back()` when there's an in-app page to go back to, and otherwise (the page was opened directly, from a link or a reload) pushes one URL segment up (`parentRoute`), so it never leaves the app for whatever site linked here. It also does that when `router.back()` turns out to go nowhere (no `popstate` within `BACK_FALLBACK_MS`), as when the app's navigation count says there's a page behind this one but the tab's history has none: a page opened from a push notification, or a form opened directly whose submit replaced its URL. A proposal, an invitation or a profile goes up to Home. A page that goes back once it's done uses the same hook rather than `router.back()`, as the Manage circle pages do after saving. A page that needs to intercept leaving — the event form, the Manage circle pages and Edit myself, which ask before discarding unsaved changes — registers a handler with `useBackHandler` (`components/providers/back-handler-provider.tsx`, mounted in `app/(app)/layout.tsx`), passing `null` while there's nothing to lose so Back behaves normally. Where a form is left once its changes are discarded (its route's `onCancel`/`onBack`) is still each route's own choice: `router.back()` where the point is "return to wherever I came from", or an explicit `router.push()` to a known parent (a discarded new-event form always returns to `/events`). Back also returns to where the page was scrolled; for that, anything the person opened that makes a page longer (`EventFeed`'s past events and how many are loaded) is kept on the browser history entry with `useHistoryState` (`lib/hooks.ts`), so it's still open on Back, while a fresh visit starts closed.

**A hidden email really is hidden.** Edit myself's Visible/Hidden choice is `members.email_public` (`Profile.emailPublic`, saved by `updateMember` like the rest of the profile). `getMembersForViewer` in `lib/db/members.ts`, which AppState is seeded and refreshed with, leaves the email off everyone who's hidden theirs except the viewer themself, so it never reaches anyone else's browser; the profile page's "Get in touch" then simply has nothing to show.

**Pronouns.** On Edit myself, one of the common three with a tap (`PRONOUN_OPTIONS` in `lib/members.util.ts`: he/him, she/her, they/them; tapping the chosen one again clears it), which fills the field under them, or anything typed into that field; an option is selected only while the field holds exactly it. Either way it's the one free-text field (`members.pronouns`, up to `PRONOUNS_MAX`, which `updateMember` checks too), saved as written, optional, shown beside the name on the profile.

**Occupation.** Free text on Edit myself (`members.role`, `Member.role`, up to `OCCUPATION_MAX`, checked by `updateMember` too), optional, shown under their name, in grey serif sentence case, on cards and (a size up) on the profile. Not to be confused with a circle role.

**Skills and interests.** Free-text tags on Edit myself (`EditableTags`, `components/profile/editable-tags.tsx`). As one's typed, what other members have already added of that kind is suggested under the field (skills from skills, interests from interests), so the same thing is called the same thing and can be counted together: `tagSuggestions` in `lib/members.util.ts` (case aside, those starting with what's typed first, then the most used), and adding one that exists in another case takes its most common spelling (`canonicalTag`). It's worked out in the browser from the members AppState already holds (every member's skills and interests reach every signed-in member), so there's no server call; the field is a combobox (arrow keys and Enter, a tap, Escape). A tap blurs the field before its click lands, on iOS especially, so a press on the list doesn't close it (`picking`), and the pick puts focus back so the keyboard stays up; the list is capped to the room between the field and the bottom of the visual viewport (above an on-screen keyboard), never less than two rows, and scrolls in itself beyond that. Circle offers and needs use the same component without suggestions.

**Born in the…** A member may say which decade they were born in (`members.birth_decade`, `Member.birthDecade`, stored as the decade's first year), never a birthdate. Edit myself offers the decades in `BIRTH_DECADES` (`lib/members.util.ts`, which `updateMember` checks against too) plus "Rather not say", which saves `null` (an undefined field wouldn't survive the trip to the Server Action, hence `ProfilePatch`). The profile shows it under "Born in the" as a big, tilted sticker, labelled by `birthDecadeLabel`: "'90s", but "2000s" and "2010s" in full, since "'00s" would read as the 1900s.

**Languages.** A member lists the languages they speak, each with a level from 1 (beginner) to 5 (native) (`members.languages`, jsonb, `MemberLanguage[]`), edited on Edit myself (`LanguagesEditor`) and shown on their profile. The level is drawn as five unnumbered segments (`LanguageLevelBar`, tappable in the editor), with the level's word for screen readers. `lib/languages.util.ts` holds the rules, shared by the form and `updateMember`: the pickable codes (`LANGUAGE_CODES`, including Cape Verdean Creole, Haitian Creole, Khmer, Hmong, Lao and ASL), up to 10, no repeats. A language shows in its own name ("Español", "ខ្មែរ") with its English name under it. Both names are kept in a table in `lib/languages.util.ts` (`LANGUAGES`), not asked of the runtime's `Intl.DisplayNames`: its data differs between Node and each browser (Chrome has no name for ASL and few languages' own names), so the server-rendered picker never matched the browser's, a hydration error. A new language needs both names added there. No flags, on purpose: a flag stands for a country, not a language.

**Home's prompts.** Home's one-time prompts are dealt as a **deck** (`PromptDeck`, `components/home/prompt-deck.tsx`), built by `HomePrompts` (`components/home/home-prompts.tsx`) as a list of `Prompt`s (an id, icon, title, body and buttons), in order: **Install the app**, always on top while it isn't installed and the browser can install it (`useInstallPrompt`, `components/home/install-app-prompt.tsx`; see Installable app), then turning on push, then, for a profile still as applying left it (`isProfileBlank` in `lib/members.util.ts`: no pronouns, occupation, bio, skills, interests, languages or decade), **Tell your neighbors about yourself**, with Edit profile (which isn't an answer: the card goes once something's filled in) and Not now, then, while availability has never been set (`Profile.availability` null; `[]` is an answer) and they're in a circle that holds meetings, **Say when you can meet**, with Set times (to `/settings/availability`, likewise not an answer) and Not now. A new prompt is one more entry in that list. Only the top card can be acted on; up to two sheets of paper peek out under it while more are waiting, its corner counts "1 of 2" through the deck as Home opened with it, and answering one (it leaves the list) pulls it off, opaque, to the side (`animate-deal-out`) and deals the next up into place (`animate-deal-in`); with reduced motion it just changes. Nothing shows until this device's push status is known, so the deck doesn't reshuffle as it loads. Not now is remembered in this browser's storage (`lib/home-prompts.ts`), per member for the profile and availability prompts (`useNotNow`), so another device may ask once more. In the installed app `<main>` doesn't scroll sideways (`overflow-x-hidden`), so a card leaving the screen can't make it.

A member's profile is a page, `/profile/[id]` (`components/profile/member-profile.page.tsx`), opened from anywhere a member is shown (circles, attendee lists, member lists, role slots) through `useAppNav().openMember`. It's laid out like a circle page, with their home neighborhood as the masthead chip and "Member of" as a `FolderGrid` of `CircleCard`s. On your own, the top bar's action is the Edit pencil to `/profile/edit`, which goes back (`useGoBack`) to wherever it was opened from. It replaced a global profile modal.

### Data access layer
`lib/db/` (`members.ts`, `circles.ts`, `circle-roles.ts`, `availability.ts`, `events.ts`, `resources.ts`, `notifications.ts`, `applications.ts`, `invitations.ts`, `proposals.ts`, and for sharing an event `event-shares.ts`, `guest-rsvps.ts`, `guest-notifications.ts`) is the seam between the app and its data source — every function is `async` (`getMembers`, `getMemberById`, `getMemberByEmail`, `updateMember`, `getCircles`, `getCircleById`, `getCirclesByMember`, `updateCircle`, `getEventsForMember`, `createEvent`, `setRsvp`, ...) and is backed by a real, self-hosted Postgres database via Drizzle ORM. `lib/db/schema.ts` holds every Drizzle table definition (`members`/`member_photos`, `circles`/`circle_members`/`circle_roles`/`circle_resources`, `events`/`event_series`/`event_agenda_items`/`event_rsvps`/`event_votes`/`roles`/`role_members`, `event_notifications`, plus Better Auth's own `user`/`session`/`account`/`verification` tables — see Authentication) and `lib/db/client.ts` opens the one real connection (`drizzle(process.env.DATABASE_URL)`). **Wrapping rule:** no file outside `lib/db/` (and `lib/better-auth.ts`, for the auth tables) may import `drizzle-orm` or `lib/db/schema.ts` directly — every other file reaches data through the plain async functions these files export, so the app is never tightly coupled to Drizzle itself. The DAL reassembles join tables into the arrays the app types expect (`Circle.members`, `Event.rsvps`/`votes`/`roles`) and normalizes Postgres's `HH:MM:SS` `time` back to the app's `HH:MM`.

Local dev runs Postgres, plus Mailpit for outgoing email (see Email), via `docker-compose.yml` (`docker compose up -d`); schema changes go through `drizzle-kit` (`npm run db:generate` to diff `lib/db/schema.ts` into a new SQL file under `drizzle/`, `npm run db:migrate` to apply it). `scripts/seed.ts` (`npm run db:seed`) inserts `lib/data.ts`'s fixtures into a freshly-migrated database — `lib/data.ts` is seed-script input only; no app code imports it. The live beta is seeded separately: `npm run db:seed:beta` (`scripts/seed-beta.ts`) reads a **gitignored** `seed/beta.json` — one city, one neighborhood, one council inside it (a `circle`-type circle; the file's keys still say `council`), and the people (all residents; those marked `inCouncil` are on the council) — because it holds real names and emails and must never be committed; `seed/beta.example.json` documents the shape with fake data. It also creates each person's login (a Better Auth user for their email — sign-up is off, so this is the only way to sign in) and refuses to run against a database that already has members. Beyond the seed, the only way a login is created is an approved application (see Applications). Both scripts share `scripts/seed-core.ts`.

`app/(app)/layout.tsx` is the one place a Server Component fetches through the DAL and hands the result to a Client Component as props: it calls `getEventsForMember(currentUserId)`/`getCircles()`/`getMembers()` and passes them into `AppStateProvider` as `initialEvents`/`initialCircles`/`initialMembers` (plus the signed-in member as `initialProfile`), which seed its `useState` calls. Components read the live roster and circles through `lib/hooks.ts` (`useMembers()`, `useMemberById()`, `useCircles()`, `useCirclesById()`), never from static data. `AppStateProvider` is a Client Component, though, and a real Postgres driver can't run in a browser bundle — so its mutators don't call `lib/db/` directly. They call `lib/db/actions.ts` instead: thin `"use server"` wrappers around the same DAL writes. Event and resource writes are authorized against the session and return `{ ok, value | error }` (Next sanitizes thrown messages in production, so a `UserFacingError` — the base of `EventError`/`ResourceError`, in `lib/db/errors.ts` — is caught in `asMember` and returned as data); the event actions are intent-specific (`createEventAction`, `updateEventDetailsAction`, `setRsvpAction`, `setVoteAction` — for meetings and proposals alike — `toggleRoleSlotAction`), never a general patch, because the server computes `rsvps`/`votes`/`roles` from the session member rather than trusting client-supplied arrays. `updateCircleAction`/`updateMemberAction` are authorized too, each the narrowest rule that closes it: `updateCircleAction` requires the session member to belong to the circle (`updateCircle` in `lib/db/circles.ts`, throwing a `CircleError`; it also silently drops a `members`/`roles` key from the patch, since neither is editable through this generic path — `roles` has its own action, and there's no membership-editing UI yet) — `/circles/[id]/manage` and its pages 404 for a non-member (`useManagedCircle` in `lib/hooks.ts`), the same way `/events/[id]/edit` 404s for a non-organizer, so the button that's already hidden for them isn't reachable by URL either. `updateMemberAction` takes no id from the client at all — it always writes the session member's own row, so there's no id to check. Both stay fire-and-forget (`.then((r) => { if (!r.ok) console.error(r.error); })`, no rollback) — retry/rollback handling for these two is still future work, but a refusal is no longer silent. The event mutators are optimistic like the rest, but reconcile through `syncEvent` in `AppStateProvider`: they adopt the server's event on success and roll back with an error toast on refusal; `createEvent`/`updateEventDetails` instead await the server and return a result so the form can show a refusal inline.

### Circles and the Circles browser
Everything that scopes something is a **circle**. The city ("Providence") is the root circle; neighborhoods, councils, collectives, and co-ops are circles inside it, and circles nest. Every circle has a `parentId` (the root's is `null` — exactly one row, enforced by a unique partial index) and a `type`: `neighborhood | circle | collective | cooperative | other | group`. A council (the Finance Council, a beta neighborhood's council) is a plain `circle`: there used to be a `council` type, and migration `0015` renamed that enum value to `circle`, converting every existing council. Two types have behavior: `neighborhood` (a member's *home* circle; see below) and `group` (see Groups below); the rest are display/filter labels (`CIRCLE_TYPE_LABEL` in `lib/circles.util.ts`). Membership is always explicit — a `circle_members` row — for every type, neighborhoods included; there are no derived rosters. `circle_members` carries its circle's `type` through a composite FK to `circles(id, type)`, which lets a partial unique index limit each member to **one neighborhood circle** (their `Member.homeCircleId`) with no trigger. Membership in a sub-circle is independent of its parent.

`lib/circles.util.ts`'s pure helpers are the seam everything else reads the tree through: `indexCircles` (id → circle lookup, `CirclesById`), `isCircleMember`, `circleChildren`, `circleNeighborhood` (the circle itself if it's a neighborhood, else its nearest neighborhood ancestor — `null` means citywide; used for the place chip and "local to my neighborhood" checks), `circleDescendantIds` (whole subtree, for search), `circlesForMember`, `sharesCircleWith` (gates avatar photos), and the event-audience trio `isCircleAudience`/`circlesForAudience`/`audienceLabel` (see Events belong to a circle below) — `isCircleMember` stays *explicit* membership on purpose, so everyone isn't implicitly in the root for rosters, resources or `sharesCircleWith`. Circles are **public**, except groups: any signed-in member can see any other circle's page and roster (only an event's visibility is restricted — see Events belong to a circle below). A member may belong to no neighborhood (`homeCircleId` is nullable), so the UI tolerates that.

Browsing is one **Circles** browser at `/circles`, split across views since the city root and a neighborhood folder show meaningfully different things: `components/circles/circles-root.page.tsx`'s `CirclesRootPage` (`/circles` with no id) shows every circle directly under the root — neighborhoods and citywide groups — as folders, with no people grid; `components/circles/neighborhood.page.tsx`'s `NeighborhoodPage` (`/circles/[id]` for a `neighborhood`-type circle) shows its direct children as folders (`CircleCard`) and its members as files (`components/circles/member-card.tsx`'s `MemberCard`) and a search that flattens its whole subtree; every other circle renders `circle.page.tsx`'s `CirclePage` (which also has a "Sub-circles" section), with its management one level deeper at `/circles/[id]/manage` (see Managing a circle below). Both browse views share `components/shared/folder-grid.tsx`'s `FolderGrid`. Keying by the circle's own stable id means reparenting one (its Parent Circle field on the manage page — neighborhoods or the city root are the offered parents for now) never changes its URL. `useAppNav()`'s `openCircle` constructs the URL — always route through it rather than hand-typing `/circles/${id}`. Folders split into a **Circles** grid (`type === "circle"`), a **Groups** grid (see Groups below) and an **Organizations** grid (collectives, cooperatives and everything else), in that order, inside a neighborhood, and the Type filter's options are Circles, Groups, Organizations and People. At the city level it's Neighborhoods, Groups, then Organizations (where plain circles go too). A chip at the top of a masthead (a circle's parent, a profile's neighborhood, a proposal's or event's circle) goes in `MastheadChip` (`components/shared/chip.tsx`), which caps it at part of the row (60%; the event masthead 45%, beside its time) so a long name ends in "…", with the full name as its tooltip, rather than running off the screen. `CirclePage` shows its parent as a clickable chip in its masthead, opposite the type eyebrow: the shared `Chip` (made a button by its `onClick` prop; every chip leads with a ring icon, since every chip names a circle), colored like any place chip, so teal when the parent is your home neighborhood and ink for the city. `NeighborhoodPage` has no masthead, so it still opens with a **Part of** grid holding one card, its parent (`components/circles/parent-circle.tsx`'s `ParentCircle`), hidden while searching or filtering. The city root has no `/circles/[id]` page of its own — `openCircle` sends it to `/circles`.

`CircleCard`'s type eyebrow is controlled separately from its neighborhood chip via `showKindEyebrow` (default: on for everything but a neighborhood), and its neighborhood chip via `showNeighborhoodChip` (default on): both hide on every card while browsing *inside* a folder (`NeighborhoodPage`, `CirclePage`'s Sub-circles), since every card there structurally shares the folder's own neighborhood; they show at the Circles root, a flat list that mixes neighborhoods. `MemberCard`'s neighborhood chip follows the same `showNeighborhoodChip` reasoning. The top bar shows a small teal home icon next to the title when the page is the viewer's own home neighborhood (`/circles/${profile.homeCircleId}`).

### Creating a circle
Any member can create a circle: New circle in the top bar's menu on the Circles root and on a neighborhood's page opens **New circle** (`/circles/new`, `create-circle.page.tsx`), with its Parent Circle starting as where it was pressed (`?parent=<neighborhood>`, or the city at the root) and changeable. A circle's own page has Manage there instead. The form asks only for the **type**, with an info box describing each kind (`CIRCLE_TYPE_DESCRIPTION` in `lib/circles.util.ts`, the chosen one picked out), the **name**, an optional **tagline**, for a Circle its **domain and aims** (required; see Consent proposals), and the **parent**; the rest of the page is filled in from Manage circle afterwards. Create stays disabled until every required field has a value, which says enough on its own, so the form shows no messages (`checkNewCircle` can say which field a problem is about, for a form that needs it). The creatable types are `CREATABLE_CIRCLE_TYPES`: Circle, Collective, Cooperative and Group — not a neighborhood, whose type carries behavior a new one isn't set up for, nor Other, since a new circle should say what it is (existing ones keep it: Manage circle offers Other only to a circle that's already Other, and `updateCircle` refuses changing anything else to it). Parents are `parentCircleOptions` (the neighborhoods, then the city), offered by `ParentCircleSelect` (`components/circles/parent-circle-select.tsx`), the Parent Circle field both Create circle and Manage circle use: grouped under Neighborhoods and Citywide, with the city as "Providence (the whole city)", since a bare name doesn't say which it is. `validateNewCircle` is the one check, for the form (Create stays disabled until it passes) and `createCircle` in `lib/db/circles.ts`, which makes the creator its first member and its id the name's slug (`-2`, `-3`… if taken; `new` is reserved, being the form's own route). `AppStateProvider.createCircle` is await-then-update, and the form replaces itself with the new circle's page. **A Circle (type `circle`) inside a neighborhood isn't created but proposed to that neighborhood**, since it can post to the neighborhood's bulletin (see Neighborhood bulletin): `createCircleAction` sends it to `proposeNewCircle` in `lib/db/proposals.ts` (a `new_circle` proposal on the neighborhood, `changes` holding the form), the form's top bar action becomes the orange Propose circle, which asks first, and the route goes on to the proposal. Residents are asked in their daily digest; when it passes, `startCircle` makes it with its proposer as first member (`insertCircle` in `lib/db/circles.ts`, the transaction-taking half of `createCircle`) and records it as the proposal's `subjectCircleId`, so its page offers "Go to" it. A neighborhood whose only resident is the proposer starts it at once. Every other kind, and a citywide Circle, is created at once as before. Circles that existed before this keep posting without being asked.

### Managing a circle
A member manages a circle from the cog on its page: **Manage circle** (`/circles/[id]/manage`, `manage-circle.page.tsx`) is a menu like Settings, of `MenuRow`s each opening a page of its own, with Leave at the foot (see Leaving a circle). **Details** (`/manage/details`, `circle-details.page.tsx`): its name, tagline, type, parent, and a Circle's domain and aims, all proposed for consent. **Roles** (`/manage/roles`, `circle-roles.page.tsx`; only where `circleHasRoles`): see Circle roles, also proposed. **Wiki** (`/manage/wiki`, `circle-wiki.page.tsx`; not for a group): everything the circle page's Wiki tab shows, saved directly, with the member recorded as last editor. Each page has its own Save in the top bar and asks before discarding unsaved changes; once saved (or proposed by a circle of one) it goes back to the menu, and proposing goes on to the proposal. The routes share `useManagedCircle` (the circle, the members-only 404 and its open proposal), and Roles and Wiki 404 for a circle without them.

### Groups
A **group** (`type: "group"`) is a circle with fewer features, and private. `lib/circles.util.ts` holds the rules as predicates, so check those rather than the type: `isGroup`, `circleHasWiki` (no Wiki tab, no quick facts, and no Wiki row on its Manage circle menu), `circleHasTasks` (no Tasks tab or backlog) and `circleCanHoldMeetings` (it can't hold a meeting); `circleHasRoles` is false for one too. It keeps a bulletin, members and invitations. It **can host events, decided by consent** (see Meetings and circle-hosted events, by consent, below), and members may also post their own ordinary events *shown to* it; either way only its members see them. **Only its members know it exists:** `getCirclesForMember` in `lib/db/circles.ts` sends every circle except a group the member isn't in, roster included, so to anyone else its page 404s and it's absent from every list. That's why an invitation carries its circle's name and tagline (`CircleInvitation.circleName`/`circleTagline`), so the person invited to a group can read it before they can see it. `createEvent` refuses a group as a meeting's circle, or as host of an event shown anywhere but the group itself (`hostCanShowTo`: a group event shown to its neighborhood would reveal the group), and `updateCircle` refuses turning a circle into a group or a group into anything else, since either would hide or reveal it; the Manage page offers neither. Groups have their own **Groups** grid when browsing (see the Circles browser above). The demo data has one, Providence Anarchists (Felix and Gus). A group is created like any other circle, from Create circle (see Creating a circle).

### Meetings and circle-hosted events, by consent
A **meeting**, and an event a **circle hosts** (any circle, a group included), is decided by its circle's members **by consent**, through the same proposals as a change to a circle (see Consent proposals) — the circle that decides is the host, or a meeting's own circle. The one exception: **anyone holding a role in a meeting's circle** (a built-in one or the circle's own; `roleHeldIn` in `lib/db/events.ts`, `approvingRole` in `lib/circle-roles.util.ts` for the form) schedules it outright, recorded in `approved_by_role`. A role-holder's *event* for the circle still needs consent. Creating any other meeting, or a circle-hosted event, saves it unapproved (`approved_at` null, `Event.proposed`, with no votes) and opens a consent proposal for it in the same transaction (`createConsentEvent` → `openEventProposal` in `lib/db/proposals.ts`): a `circle_proposals` row of kind `event` with `event_id` set, `changes` empty and `lines` describing it (`describeEventProposal`: title, kind, when, repeats, where, roles, agenda, details), so `isEventProposal`/`proposalTitle` ("Schedule …") read it even after the event's gone. The circle is told by the proposal's "opened" notice, not an event notice. Members answer it like any proposal (Like / Accept / Object, 3 days, silence is consent); a circle of one passes it at once. **Consenting is also an RSVP**: the proposer is marked going by proposing, and each member who likes or accepts it by answering (`rsvpConsenters` in `lib/db/proposals.ts`, in the same transaction); silence counts as consent but not as an RSVP, so a member who never answers isn't going. Not for an event with signup roles, where people take a role once it's scheduled. Consenters go only to the date they consented to: a series' later dates start with no one. The proposal page and the event form say so. While it's undecided its page offers no Add to calendar, and the calendar route refuses it, since it may never be held. **Passing** approves it (`approveHostedEvent` in `lib/db/events.ts`), and its `approved` email, with its details, tells the circle; at the deadline no one is skipped. **An objection** discards the event (`discardEvent`; the proposal's `event_id` goes to null, its record stays), as does **withdrawing** it: cancelling it while it's undecided (any member; the proposal page's Withdraw) closes the proposal as `withdrawn`. One still undecided when its event's start time comes is **withdrawn automatically** (`withdrawLapsedEventProposals` in `lib/db/proposals.ts`, run by the notification poller before due proposals are passed, and checked again by `pass` in case a last answer comes in between): closed as `withdrawn` with `circle_proposals.lapsed` set, so its page says it was withdrawn automatically because its start time came first, and its event discarded. No one is notified. While it's undecided (`awaitingConsent`: `Event.proposed`) only the deciding circle's members can see it (`canSee`/`getEventsForMember`), it's in no list (`EventFeed` leaves it out), it can't be RSVP'd to by hand (only by consenting) or edited (what's proposed is what's consented to), and its page shows its proposal's banner and an orange "Proposed" masthead. Once decided it's attended by RSVP like any event, meetings included, and reads like one. Any number of event proposals can be open at once, alongside a change to the circle: `circle_proposals_one_open` covers only changes (`kind = 'change'`), and only those lock Manage circle. The actions behind creating one, answering one and withdrawing one hand back the whole app state for `AppStateProvider` to adopt, since each moves both an event and a proposal. The form's Propose asks first (a `ConfirmModal` with `tone="flame"`), saying it needs the consent of the circle that hosts it (or whose meeting it is), since sending it tells that circle at once. Creating one goes to its proposal's page rather than the event's. **There's no voting any more**: majority votes were the interim rule, and `scripts/convert-to-consent.ts` (`npm run convert-to-consent`, `convertMajorityToConsent`) moved every upcoming meeting or circle-hosted event still waiting on its votes to an open consent proposal, its votes counted as consents; one that had its majority stayed scheduled. `event_votes` keeps the old votes as history; nothing writes to it.

### Who manages an event
An event hosted by a person is theirs alone to edit or cancel. One a **circle holds** — it hosts it, or it's the circle's meeting — can be edited or cancelled by **any member of that circle**: `assertCanManage` in `lib/db/events.ts` (`updateEventDetails`, `cancelEvent`) and `canManageEvent` in `lib/governance.util.ts` (Edit in the event page's menu, the edit page) are the same rule. Update and cancellation emails skip whoever made the change, so the organizer hears when someone else does.

### Circle invitations
A member of a circle can **invite** anyone on Circles who isn't in it — any circle with a page, so not a neighborhood (whose members are its residents) or the city. On the Members tab, the page's floating action button is Invite (a person-plus, members only) that opens `InvitePicker` (`components/circles/invite-picker.tsx`): everyone not in the circle, searchable, their home neighborhood first, each invited with a tap and sent at once. Like the bulletin form, it's a dialog on desktop (`InviteModal`) and a page on a phone (`/circles/[id]/invite`, `InvitePage`), chosen at the tap by `isPhoneWidth()`. An invitation (`circle_invitations`, one per member per circle, `CircleInvitation`) shows on the invitee's Home, and under the circle's Members grid as **Invited**; each opens `/invitations/[id]` (`InvitationPage`). There the invitee has **Accept** as the top bar's action (they join the circle and the invitation goes; the action returns their whole app state, which `AppStateProvider` adopts, since joining opens up the circle's events and bulletin) and Decline at the foot; a member of the circle has Delete. Both ask first. `lib/db/invitations.ts` is where it's enforced: only a member invites or deletes, only the invitee accepts or declines, and `getInvitationsForMember` sends a member only their own invitations and those of their circles — the AppState `invitations` slice. Mutators are await-then-update. The invitee is told once, by email (`invitationEmail`, if they have an address) and by push (`invitationPush`), right after `createInvitationAction` responds (`after()`, `tellInvitee`), linking to the invitation; unlike event notifications it isn't queued, so a failed send isn't retried — the invitation is on their Home either way.

### Leaving a circle
A member leaves deliberately from the foot of the **Manage circle** menu: a red **Leave {name}** button, kept apart from the rest since it's one-way, behind a confirmation that says what it means for them — they lose its bulletin and the events shown only to its members, any roles they hold there are left empty, and if they're its last member it's archived. `leaveCircle` in `lib/db/circles.ts` (through `leaveCircleAction`, which hands back the whole app state for `AppStateProvider.leaveCircle` to adopt, as accepting an invitation does) removes the membership and clears their roles, rather than letting them come back on rejoining. A neighborhood (their home) and the city can't be left this way. Their proposals, and events they organize for it, stand. The **last member out archives the circle** (`circles.archived_at`): it's kept, but `getCirclesForMember` sends it to no one, so its page 404s and it's in no list, and its pending invitations are deleted; reviving or deleting archived circles is future work. It's decided under a lock on the circle. Afterwards the route replaces Manage circle with the circle's page (now as a non-member), or the Circles browser if it was archived.

### Circle roles
Members can hold **roles** inside a circle — Secretary, Leader, Facilitator, a Circle's Delegate, or any the circle adds — in every circle *except* a neighborhood, a group or the city root (`circleHasRoles` in `lib/circle-roles.util.ts`, the module that holds every rule below as pure functions). They're optional throughout. The **built-in** roles (`BUILTIN_CIRCLE_ROLES`; for a given circle, `builtinRolesFor(type)`) are always listed for an eligible circle, empty until someone is chosen, and can be assigned and cleared but never removed or renamed. The fourth, the **Delegate**, who represents a circle in its parent circle, belongs only to a circle accountable to its parent (`circleIsAccountable`: type `circle`), not a collective or co-op: no other circle can name a role of its own Delegate (`validateCircleRoles`), and a Circle that becomes one of those loses its Delegate (`assembleCircleRoles` takes the type, as `writeCircleRoles` does). Whether a role is built-in is decided by its name and the circle's type; a circle may add its own (up to 20, names up to 40 characters, unique case-insensitively). A role has **at most one holder, and a member can hold several roles** — one row per role, one member picker each. Circles are public, so `Circle.roles` (every built-in first, then the circle's own, each with its `memberId` or null) travels with the circle to every signed-in member, and the roles show on the circle page for anyone.

**Where they show:** on a member's card in that circle's Members grid, as an outlined badge (one per role, in the circle's own order) under their occupation. The card always shows their occupation (`Member.role`) and never their neighborhood — everyone in the grid belongs to this circle, so the chip would be redundant (the same reasoning as `MemberCard`'s `showNeighborhoodChip`); a member with no role simply has no badge. Nowhere else — a role belongs to one circle, so the profile page, the neighborhood folder view and event pages don't show them.

**Managing them:** Manage circle's **Roles** page (`/circles/[id]/manage/roles`, `circle-roles.page.tsx`) has a Roles table, one row per role with a member picker over that circle's members, plus "Add role" for the circle's own (which can be renamed or removed). Each built-in role has a description under its name (`BUILTIN_ROLE_DESCRIPTION` in `lib/circle-roles.util.ts`, after Sociocracy for All's circle roles: a role is about paying attention, not power). Keep that copy short: one line per role, one line of intro. It's shown only to members of the circle, and who holds which role is the circle's to decide **by consent**: saving a change to the roles proposes it (see Consent proposals), and only a passed proposal writes them, through `writeCircleRoles` in `lib/db/circle-roles.ts` — there's no other way to change them, and `updateCircle` ignores a `roles` key. A proposal carries each role's name and holder, in order: whether a role is built-in is decided by its name, a built-in left out is just kept empty, a holder must be a member of the circle (`validateCircleRoles`, shared with the form), and a holder who's since left the circle is left out when it's written. The demo Finance Council has Priya as Secretary, Felix as Leader and Mira as Facilitator; the beta seed takes an optional `councilRoles` list per person.

### Consent proposals
Some changes to a circle are its members' to decide **by consent**, as Sociocracy for All defines it: a decision is made unless someone has a reasoned objection. They are its **name, tagline, type, parent and roles**, and a Circle's **domain and aims** (`CONSENT_FIELDS`); the rest of its page (about, offers, needs, facts, hours, how to join…) stays freely editable.

**Domain and aims.** Sociocracy defines a circle by its **domain** (the area it has the authority to decide in) and its **aims** (what it's there to achieve), so a circle of type `circle` must have both: `circles.domain` (text) and `circles.aims` (text[], up to `MAX_CIRCLE_AIMS`), on `Circle` as `domain`/`aims`. They're edited on Manage circle's Details page, shown only while the type is Circle, and proposed like the rest of that page; `updateCircle` drops them from a direct edit. On Manage circle's Details and Roles pages a problem with what's proposed shows **under its own field**, which is scrolled to and focused, and goes as soon as that field's edited: `checkChanges`/`checkCircleBasics` return the field with the message (`validateChanges`/`missingCircleBasics` are the same as just the message, for the server), and a refusal from the server, which doesn't say which field, shows at the top of the page (`useConsentError` and `ConsentNotice` in `components/circles/consent-form.tsx`). `missingCircleBasics` (`lib/proposals.util.ts`) refuses a proposal about what defines a Circle — its type, domain or aims — that would leave it without a domain or at least one aim; any other proposal (its roles, a rename) goes ahead regardless, so a Circle that hasn't defined itself yet isn't stopped from deciding anything else. Manage circle's Details asks for them all the same, checking the whole form rather than only what changed, so they're filled in the next time its details are edited. Checked by the form and `createProposal`, but not again when one passes, so an agreed change can't fail on it. New circle asks for them too, for a Circle, so a new one starts with both. Both forms use one component for them, `CircleBasicsFields` (`components/circles/circle-basics-fields.tsx`), and the limits live in `lib/circles.util.ts`. They're shown nowhere else yet. On Manage circle's Details and Roles pages, a change to any of those is **proposed**, not saved: their Save is the orange Propose button with the hand icon, which is what says so (the pages carry no copy about consent), and the route goes on to the proposal's page (`useProposeCircleChanges` in `lib/hooks.ts`; a circle of one decides it at once). Details and roles are proposed separately, one page each. `updateCircle` refuses a direct change to any of them.

**Kinds, and who decides.** A proposal has a `kind` (`ProposalKind`): a `change` to a circle, an `event` (see Meetings and circle-hosted events), a `post` to the neighborhood's bulletin (see Neighborhood bulletin) or a `new_circle` (see Creating a circle); `isEventProposal` and `proposalTitle` read it, never the lines. Its `circleId` is whose members decide it. A change that would make a circle in a neighborhood a Circle, or move a Circle into a neighborhood from elsewhere (`neighborhoodConsentFor` in `lib/proposals.util.ts`), is decided by that neighborhood's residents together with the circle's own members: the row's `circleId` is the neighborhood and `subjectCircleId` the circle it changes (`decidersOf`), its own members are told by email and push and the rest of the residents in their digest, and only its proposer and the circle's members hear how it ended (`toldOfOutcome`). Manage circle's Details asks first for such a change (a flame `ConfirmModal`), since it reaches the whole neighborhood. One open change per circle counts these too (the `circle_proposals_one_open` index is on `coalesce(subject_circle_id, circle_id)` for `change`s only), and `getProposalsForMember` sends a member the proposals of their circles, those about their circles and their own.

A proposal (`circle_proposals`, `CircleProposal`, `lib/db/proposals.ts`) holds only what actually changes (`changedFields`), checked by the same rules Manage circle always used (`validateChanges` in `lib/proposals.util.ts`, which the form also runs), and its `lines` — each change as label, before and after, written when it's proposed so it reads the same however things are renamed later. Its proposer consents by proposing. It's open for **3 days** (`PROPOSAL_WINDOW_MS`); **one per circle at a time** (a partial unique index), and Manage circle's Details and Roles lock while one's open: their menu rows say "Locked while a proposal is open", and each page opens with a grey notice saying so and why (a circle decides one change at a time) around the open proposal's banner (`ConsentNotice`), its fields disabled and its add and remove controls gone. Each member answers on `/proposals/[id]` (`proposal.page.tsx`) with one of three buttons: green **Like this** (thumb up), yellow **Accept this** (a check, `--color-accept`) — both consent, differing in enthusiasm rather than reservations — or red **Object** (thumb down), which asks why (required). They can change their answer while it's open; the page shows every member's answer, as a round would. **One objection closes it** as objected (it can be proposed again, changed to meet it); it **passes** as soon as every member has consented, or at the deadline if no one objected — silence counts as consent (`closeDueProposals`, run by the notification poller). Passing makes the changes (`applyProposal`, which re-checks them against the circle as it now is and records the proposer as last editor). Every write locks the proposal's row.

Members are told by email and push (`proposal_notifications`, leased and retried like the other queues; `proposalEmail`, `proposalPush`): **opened** (everyone but the proposer), **objected** (everyone but the objector, with the reason) and **passed** (everyone but whoever's answer passed it). Proposals are for the circle's members only: `getProposalsForMember` sends open ones and those decided in the last 30 days (AppState `proposals`), and to anyone else one doesn't exist. An open one shows as an orange banner on its circle's page, a neighborhood's included (above its folders, while not searching or filtering) (`ProposalBanner`, which inverts to orange while pressed: `flame-press`, and carries no attention dot), and each one waiting on your answer is a row in Home's **Needs you** (see Home), and your own open ones a quieter row after them, since they wait on others — the way back to an undecided meeting, which is in no event list. Meetings and circle-hosted events are decided through the same proposals (see Meetings and circle-hosted events, by consent).

### Circle resources
A circle can attach **resources** — links (a shared drive, a doc), each shown with the icon of the kind the person adding it picks: a folder (yellow), a file (blue), a video (purple), a survey (green, a clipboard with a check: a form to fill in) or an announcement (red, a megaphone) — that only that circle's **members** can see. They render on `CirclePage`'s Bulletin tab (`components/circles/bulletin-section.tsx`). `CirclePage` always shows a tab row: **Bulletin** (members only, and where a member lands), **Wiki** (its quick facts first, then About, what they offer and need, sub-circles, its website, address and contact as coloured squares (see Website, address and contact), its open hours on their own, and how to join; where a non-member lands; Manage circle's Wiki page edits them in the same order), **Members** and **Events**. The Members and Events tabs carry no eyebrow of their own, since the tab names them. A non-member gets no Bulletin tab, and no hint one exists. Their Events tab shows only what they can see, meaning events the circle hosts for a circle they belong to, since events shown to a circle reach only its own members; its empty state says so. They apply to circles that have a detail page, so **not** neighborhoods (whose folder view has no such section, and the server refuses to add one). Adding an item is the page's floating action button (a +) while the Bulletin tab is active, so `CirclePage` owns whether the add dialog is open and passes it to `BulletinSection` (`adding`/`onAdd`/`onAddingDone`). The tab decides the button: the Members tab's is Invite (a person-plus) and the Events tab's a + opening the new event form (`/events/new?host=<id>`, via `useAppNav().newEvent`) hosted by and shown to that circle, both for members only; the Wiki tab has none. An empty board also offers adding an item as a dashed blank card, with a line on what to post; once anything is pinned only the + remains. The bulletin shows them as a board of cards (`BulletinCard` in `bulletin-section.tsx`), as many columns as fit: each card is ruled along its top in its kind's color, a link card is a link all over (its title's link stretched across it, inverting while pressed), and an announcement spans more of the board with its whole message. Any member of the circle can add, edit, or remove one, each saving immediately in its own form rather than as part of the Manage form. On desktop that form is a dialog (`ResourceFormModal`); on a phone it's a page (`ResourceFormPage`, at `/circles/[id]/bulletin/new` and `/circles/[id]/bulletin/[resourceId]`), with Save in the top bar, no Cancel (Back leaves, asking first if anything changed), and Remove at its foot. Both shells share `useResourceForm` and `ResourceFields` (`components/circles/resource-form.tsx`), whose kind is chosen with `ResourceKindPicker` (`resource-kind-picker.tsx`): a field-styled button opening a listbox that shows each kind with its icon in its colour and a line on what it's for, since a native select can't (arrow keys, Enter, Escape, which closes only the list inside a dialog), and which one opens is decided at the tap by `isPhoneWidth()` (`lib/viewport.ts`). Anything else that should be a dialog on desktop and a page on a phone follows the same pattern; confirmations and alerts stay dialogs everywhere. A card's only control is its edit pencil; removing lives in the edit dialog, behind a confirmation. A control inside a pressable card is marked `data-press-ignore`, so pressing it doesn't press the card (see `PressFeedback`). A resource is `{ title, icon: "folder" | "file" | "video" | "announcement" | "survey", url?, message? }`: a folder, file, video or survey is a link (`url`), with an optional message about it shown on its card between the title and the link, and an announcement is a message typed out for members (`message`) with no link, shown in full in the list rather than opened, and signed with who posted it and the date ("— Name on 2/24/2026"). The poster is `created_by`, set by `createResource` from the session and never changed by an edit; items from before it was recorded (or whose poster was deleted) have none and show just the date. An announcement has a message and never a link, and every other kind a link, which the form (it asks what you're adding first, then for a link and an optional message, or a message), `validateResourceInput`, `lib/db/resources.ts` (which clears an announcement's link, and saves an empty message as none) and the table's own `circle_resources_link_or_message` check all hold to (so does a neighborhood post's); only an announcement emails anyone, whatever message a link carries, shown newest first (editing one doesn't move it); links must be `http(s)` and open in a new tab (`lib/resources.util.ts`'s `validateResourceInput` is shared by the form for instant feedback and by the server as the real check).

Because circles themselves are public — the whole `circles` array is sent to every signed-in member — resources are deliberately **not** a field on `Circle`: they live in their own table and their own AppState slice, and the privacy boundary is enforced on the server, not in the UI. `lib/db/resources.ts` is the only place it lives: `getResourcesForMember(memberId)` returns only resources of circles that member belongs to (`app/(app)/layout.tsx` calls it with the session's member, so a non-member's browser never receives a circle's resources), and every write there re-checks membership and re-validates input, throwing a `ResourceError`. It takes the member id as an argument and never touches the session itself, so it can be exercised directly; `lib/db/actions.ts`'s `createResourceAction`/`updateResourceAction`/`deleteResourceAction` supply that id from `getCurrentUserId()` (never a client-supplied one) and return `{ ok, value | error }` result objects rather than throwing, since Next sanitizes a thrown error's message in production. Resources were the app's first server-side authorization; the event actions and `updateCircleAction`/`updateMemberAction` (see above) now all check the caller too. Unlike every other mutator, `AppStateProvider`'s `addResource`/`updateResource`/`removeResource` are **await-then-update**, not optimistic: the server can refuse and generates the id, so state changes only after it accepts. New circle types or "wiki"-style pages that want resources should render `BulletinSection` the same way (members only) rather than reading `resources` for non-members.

**Announcement emails.** Posting an announcement tells the circle's other members (not the poster), by email and by push (`announcementPush`: its title and as much of the message as fits), each channel queued and drained on its own as for events, always on its own rather than in the digest: a bulletin exists only on a circle with a page, never on a neighborhood or the city, the audiences big enough for the digest. It's queued in the same transaction as the post (`createResource` → `enqueueAnnouncementNotifications` in `lib/db/notifications.ts`), in its own queue table, `announcement_notifications`, which leases and retries rows exactly as `event_notifications` does. That table cascades from `circle_resources`, so an announcement removed before it's sent never goes out. `createResourceAction` drains it with `after()` (`deliverAnnouncementNotifications` in `lib/notify.ts`), with the 15-second poller as the safety net. The email (`announcementEmail`) carries the whole message, signed like the bulletin card, and is rendered when it's sent, so an edit made first is what goes out. Links, edits and removals tell no one.

**Website, address and contact.** On a circle's Wiki tab the website is a blue square with a globe (`--color-action`) opening the site in a new tab, and the address a green square with a map (`--color-leaf`) opening it (`VisitLink` in `circle.page.tsx`; from the desktop breakpoint the domain or the address sits beside its square, all one link) in the visitor's maps app: Apple Maps on an iPhone or iPad and in Safari on a Mac, a `geo:` link on Android (its default maps app), Google Maps on the web otherwise, a Mac in another browser included (`mapsPlatform`/`mapsUrl` in `lib/maps.util.ts`, read on the client, so the server renders the Google link). Each has an accessible name starting with its visible label ("Website: …", "Address: …") and a tooltip, since on a phone it carries no text. A website that isn't a link-able address (an Instagram handle, say) shows as typed, with no square, and Manage circle's Wiki says so under the field as it's typed. Beside them, its Get in touch: an email address as a sky-blue square with an envelope (`--color-email`, lighter than the website's blue, a `mailto:` link) or a phone number as a red one with a phone (`--color-phone`, a `tel:` link), told apart by `circleContact` in `lib/circles.util.ts` (a number needs 7 to 15 digits and only phone punctuation, and isn't a date); anything else shows as typed, and the Wiki editor says so. How to join follows as an ordinary section.

### Circle tasks
Every circle with a page (not a neighborhood or the city), except a group, has a **backlog** (`circleHasTasks`), its members' alone: a **Tasks** tab beside the Bulletin (members only, with no hint to anyone else), and **My tasks** on Home, listing what's assigned to you across your circles that isn't done or on the back burner, each naming its circle. A task (`circle_tasks`, `CircleTask`) has a title, an optional description, a **status** (To do, In progress or Done), a **priority**, shown as traffic lights (🔴 Critical, 🟠 High, 🟡 Medium, nothing for Normal, the everyday one, and 💤 the back burner; `TASK_PRIORITIES` in `lib/tasks.util.ts`, so the column reads as a scale at a glance; its keys are older than its names, so `normal` is Medium and `none` is Normal; the form's Normal button says its name), an optional due date, and an optional assignee, one of the circle's members. The **back burner isn't a status**: it's a to-do of priority 💤 (`someday`; `onBackBurner`), listed after what's live and before what's done. `lib/tasks.util.ts` holds the rules the form, the lists and the server share (`validateTask`, `sortTasks` and `dueCell` for the tables, `dueLabel` for the assignment notice). **Any member can add, change, assign, move or delete any of its tasks, saved straight away**: day-to-day work, not something decided by consent. `lib/db/tasks.ts` is where that's held to: `getTasksForMember` sends a member only their circles' tasks (AppState `tasks`), and every write checks they're a member of the task's circle and validates it again, locking the task's row while it reads and writes it (so a concurrent save can't be undone, or misreport who it was just given to). The table's round button changes the status alone (`setTaskStatus`, through `setTaskStatusAction`), never the whole task from a copy that may be out of date, and ticking a task it just marked done puts it back as it was (In progress stays In progress), not always To do. A refused save shows in the form; a refused tick, which has nowhere else to say so, in a toast. Whether a circle has tasks at all is `circleHasTasks` (`lib/circles.util.ts`): `circleHasPage`, the rule invitations and leaving share, and not a group; the server refuses a group's tasks and never sends any. A task deleted (or gone on a refresh) while its page is open sends the page back rather than to a 404. A member who leaves a circle no longer holds its tasks (`unassignFromCircle`, in `leaveCircle`). Tasks show as **one table** (`TaskTable`, `components/circles/task-table.tsx`, ), whatever their status: what's live first, then the back burner, then what's done, each part in the order chosen. Its header row is ink (`on-ink`, so keyboard focus is paper there) and its rows alternate white and grey. Columns: a round button that marks each done or not, then Task, Status, the priority's mark under a heading with no label, since the marks say what it is, Due (`dueCell`: "Today", "Tomorrow", "Fri, Oct 24", an overdue date in red) and Assigned to. A phone keeps Task, the priority and Due (no weekday), with "In progress" under the title. Home's My tasks lists them as rows instead (see Home). Each part is in one order, soonest due first and undated last, then the most pressing, then by name (`sortTasks`); the table doesn't sort by its headings. A row opens its task. The form follows the bulletin's: a dialog on desktop (`TaskFormModal`) from the tab's + or a tap, a page on a phone, and from Home or a notification on any screen (`TaskFormPage`, at `/circles/[id]/tasks/new` and `/circles/[id]/tasks/[taskId]`), sharing `useTaskForm`/`TaskFields`. `AppStateProvider`'s `addTask`/`updateTask`/`removeTask` are await-then-update. **Giving a task to someone else tells them**, once, by email (`taskAssignedEmail`, if email's on) and push (`taskAssignedPush`), right after the response (`after()`, `tellAssignee`), like an invitation, using who the save gave it to and who saved it, and skipping it if the task has been given to someone else since; nothing else about a task notifies anyone.

### Neighborhood bulletin
A neighborhood has a bulletin of its own, on its page (`NeighborhoodBulletin`, above Part of, hidden while searching or filtering), where the **Circles inside it** (type `circle`, however deep; `postingCirclesFor` in `lib/circles.util.ts`) post for **everyone who lives there**. Posts are the same kinds as a circle bulletin's, a link or an announcement, shown on the same `BulletinCard` with "From {circle}". `lib/db/neighborhood-posts.ts` is where it's enforced: `getNeighborhoodPostsForMember` sends a member only the published posts of their own neighborhood and those their own circles made (AppState `neighborhoodPosts`), so no one else's browser ever gets them, and the page shows nothing at all to a non-resident. **Each post is consented to by its circle first**: a member proposes it from the bulletin's Propose a post (`/circles/[neighborhoodId]/bulletin/new`, `NeighborhoodPostPage`, a page on every screen like the event form, with From, which circle it's posted as, always chosen from none to start even for someone in only one, then the bulletin's own `ResourceFields`, and the orange Propose post, which asks first), which saves it unpublished (`neighborhood_posts.published_at` null) and opens a `post` proposal for that circle (`openPostProposal`) in one transaction; a circle of one posts it at once (the top bar's Post). Passing publishes it (`publishPost`); an objection or a withdrawal (the proposal page's Withdraw) deletes it, the proposal keeping what it said. Once up it isn't edited, since that's what was consented to; any member of the posting circle can take it down (the card's trash, `removeNeighborhoodPost`). A published post tells residents only in their **daily digest** (no email of its own, no push), as a section above the events.

The digest carries a neighborhood's news through its own queue, `neighborhood_notifications` (one row per post or proposal per resident, email only, `enqueueNeighborhoodNotifications`), which `claimDigests` takes together with each member's event lines so they still get one email (`digestEmail` in `lib/email/templates.util.ts`: the neighborhood's bulletin, then what it's asked to decide, then the events). A post taken down goes from the queue with it, and a proposal decided by the time the digest goes is left out.

### Settings
Home's top bar photo opens **Settings** (see Home) (`/settings`, `components/settings/settings.page.tsx`), a menu like iOS's Settings: each part is a `MenuRow` (`components/shared/menu-row.tsx`, the boxed row with a chevron) opening a page of its own — **Edit profile** (`/profile/edit`, which Home no longer links to; opened directly, its Back goes to Settings), **Notifications** and **Meeting availability** (see Meeting availability) — with **Log out** at the foot (asking first; it turns push off for this device, then signs out). No tab is highlighted on a Settings page and the bottom nav slides away, and Back from one goes up a level (`parentRoute`).

**Notifications** (`/settings/notifications`, `notification-settings.page.tsx`) has two switches: **email**, the member's own everywhere (`members.notify_email`, `Profile.notifications.email`, on by default), and **push**, for this device alone, as on a phone (its browser's push subscription; see Installable app). There's also a member-wide `notify_push` (`Profile.notifications.push`, on by default) that still gates every push, but it isn't shown: two push switches read as the same thing. Kept in case per-kind preferences bring it back; meanwhile turning this device's push on also sets it on. The Settings menu's summary under Notifications reads both (email for the member, push for this device). Switches are the shared `Switch`. Like any form here nothing changes until the top bar's Save (disabled until something does), and Back asks before discarding. Save does this device first, since a browser only asks for permission to push in answer to a tap, then the member's switches (`saveNotificationSettingsAction` → `setNotificationSettings`; `AppStateProvider.saveNotificationSettings` is await-then-update). Where this device can't have a switch the row says why: blocked in the device's settings, an iPhone browser tab (install first), or a browser without push. Turning a channel off is respected when notifications are queued (`channelsFor`) and again when they're sent (an email row reads the address only if email's still on; `getSubscriptions` returns no devices if push is off), so it also stops what was already queued, as well as invitations and the digest's push nudge. Sign-in codes and application emails go regardless.

### Profile photos
A member can **replace** their photo on Edit myself (`components/profile/photo-picker.tsx`) but never remove it — no UI, action or DAL function deletes one. The browser crops it to a square and shrinks it to a 512px JPEG before upload. Save uploads it first, waiting for the result (`AppStateProvider.savePhoto` → `updateMemberPhotoAction` → `submitMemberPhoto` in `lib/db/photo-reviews.ts`, which checks the file's actual bytes are JPEG/PNG/WebP and that it's under 1 MB, `readPhoto`), so a refused photo keeps the form open.

**A new photo is reviewed first.** It goes to `member_pending_photos` (one row per member; sending another replaces it), not live, and a system admin approves or declines it as they do an application (see Applications), so until then everyone else keeps seeing the photo the member had. An admin's own goes live at once. Only the member knows it's waiting (`Profile.pendingPhotoVersion`, from `getOwnSettings`): where they look at themselves (their profile and Edit profile) `Avatar`'s `showPending` shows the new one under an "In review" band, the picker says it's waiting and that choosing another replaces it, and the save toast says it'll show once approved; their small avatars elsewhere show what others see. The photo route serves it (`?pending`, `pendingPhotoFor`) only to the member and admins (`getPendingPhoto`). An admin reviews it at `/admin/photos/[memberId]` (`photo-review.page.tsx`) beside the photo it would replace, which the route serves an admin (`?review`, `getCurrentPhotoForReview`) only while a new one is waiting. Approving moves it into `member_photos`; declining deletes it, with an optional note. A decision is for the version the admin saw (`approvePhoto`/`declinePhoto` take it, under a row lock), so one replaced since is refused rather than approved unseen. The member is told by email (if email's on; `photoDecisionEmail`) and push (`photoDecisionPush`), once, after the response (`after()`), like an invitation. Photos sit in Postgres (`member_photos`, bytea) in their own table, so `getMembers` reads only the upload time (`Member.photoVersion`), never the image data. `avatarFor` turns that into `/api/members/[id]/photo?v=…` and falls back to the pravatar placeholder until someone uploads one. That route serves the photo only to the member or to someone sharing a circle with them (`getMemberPhoto`), which is the same rule `Avatar` applies in the UI, so it can't be bypassed by URL. It's cached `private, immutable`, since each new upload gets a new URL.

### Installable app (PWA)
Circles can be installed from the browser as a standalone app. `app/manifest.ts` is the manifest. Its `start_url` is `/home`, so someone not signed in lands on the welcome page. `app/layout.tsx`'s `viewport` and `appleWebApp` cover iOS, which still reads its own meta tags rather than the manifest. Every icon (`public/icons/`, `app/apple-icon.png`, `app/icon.svg`) is generated from one SVG mark by `npm run icons` (`scripts/generate-icons.tsx`) and committed, so change the mark there, not the PNGs. `proxy.ts`'s matcher skips the manifest and icons, because browsers fetch them without cookies. Because of `viewportFit: "cover"`, the page draws under the home indicator and a landscape notch, so anything pinned to an edge pads itself with `env(safe-area-inset-*)`: `AppShell`, `TopBar`, `BottomNav`, toasts, and the floating action button (placed by `AppShell` from `--bottom-nav-gap`, which already includes it). A new fixed or sticky element needs the same, and full-height layouts use `min-h-dvh`, not `min-h-screen`. Installed on iOS 27, the system blurs whatever's under the status bar unless a fixed element with a solid background sits at the very top (at least 6px tall and 80% wide), whose colour it uses instead (`theme-color` and the status bar style meta tag no longer count), so the root layout pins a paper strip over the status bar in the installed app; the top bar can't do it, being neither fixed there nor solid. The on-screen keyboard should shorten the page, not slide it up (taking the top bar with it): the viewport's `interactiveWidget: "resizes-content"` (`app/layout.tsx`) does that on Android and Firefox, but Safari doesn't support it yet, so on iOS the installed app runs `AppShell`'s `useIosKeyboard`, Ionic's "scroll assist" pattern. Safari slides only when the field being focused would end up under the keyboard, so a tap on a field low in `<main>` is taken over before it focuses anything (its `touchend` is cancelled): temporary room is added under the page (`--keyboard-room`), `<main>` is scrolled to put the field just below the top bar, and only then is it focused (`preventScroll`), with the caret at the end. Pickers (selects, dates) aren't taken over, since iOS only opens one for a real tap. Once the keyboard is up the shell is `--app-height` tall, the visual viewport's height, so `<main>` ends at the keyboard; any slide that happened anyway is undone; both reset once the keyboard is gone. Delete the hook once Safari ships `interactive-widget`. Fields in a dialog (outside `<main>`) aren't covered. Home's prompt deck (see Home's prompts) offers installing too, wherever the browser can: Chromium browsers fire `beforeinstallprompt`, which `lib/install.ts` holds (an inline script in the root layout's `<head>` catches one that comes before any app code has loaded, since it can) so the card's Install brings up the browser's own prompt; the event is single-use, so it's let go either way, and `appinstalled` takes the card away. Browsers that can't install (Firefox, Safari on a Mac) get no card. iOS has no install API, so on an iPhone browser tab (not the installed app) the welcome page's `InstallPrompt` (`components/welcome/install-prompt.tsx`) offers an "Install the app" button whose dialog (`InstallStepsModal`, shared with Home's install card) walks through Share → Add to Home Screen. It sits on the welcome page because the installed app keeps its own cookies apart from Safari's, so it has to be signed into separately anyway. The service worker (`public/sw.js`, plain JS since `public/` isn't compiled) is there only for **push notifications**: it has no `fetch` handler on purpose, so it never caches a page or fights the reload-after-deploy check below, and offline support would be a separate decision. It shows every push it gets (iOS revokes a subscription whose pushes show nothing), badged in Android's status bar with `public/icons/badge-96.png`, the mark on a transparent square (Android draws a badge from its transparency alone, so the app icon would be a white square), generated by `npm run icons` with the rest and, on a tap, asks an open window to go to the notification's path (`AppShell`'s `useServiceWorker` routes there without a reload) or opens one. It's standard Web Push, so iOS and Android run the same code; iOS only allows it in the installed app (16.4+). `lib/push/index.ts` is the only file that imports `web-push` (the same wrapping rule as `lib/email/`), configured by `NEXT_PUBLIC_VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`. A device's subscription is a `push_subscriptions` row keyed by its endpoint (`lib/db/push.ts`, which refuses an endpoint that isn't a known push service, since the server POSTs to it); `lib/push-client.ts` is the browser's side, and `AppShell` re-saves an existing subscription on every open, so it follows whoever is signed in. A subscription is bound to the VAPID public key it was made with, so one made with a key the server no longer has is replaced on that open (`madeWithCurrentKey`/`replaceStaleSubscription`: push is already allowed, so it needs no tap; if the browser refuses, push is just off on that device). **Rotating the VAPID keys** therefore means: set both new keys (the public one is built into the browser code, so it takes a deploy), then delete every `push_subscriptions` row, since pushes to the old ones fail (a 403, which `pushToMember` deliberately doesn't treat as gone, lest a misconfigured key wipe every device); each device subscribes afresh as it next opens. `lib/notify.ts`'s `pushToMember` sends to all of a member's devices, forgets one the push service says is gone, and throws only if every device failed otherwise. Home also asks once per device (`PushPrompt`/`usePushPrompt`, `components/home/push-prompt.tsx`): a card of our own whose Turn on is what brings up the browser's prompt, since a browser asks only once and a refusal there can only be undone in the device's settings, while Not now leaves that unspent. It shows only where push could work and hasn't been decided (supported, not on, not blocked, not an iPhone browser tab) and until it's answered on this device, there or by changing push in Settings (`pushPromptAnswered`/`markPushPromptAnswered` in `lib/push-client.ts`, in `localStorage` through `lib/home-prompts.ts`, since push is per device too); turning it on also turns the member-wide `notify_push` back on. A device opts in on Settings → Notifications (see Settings), and signing out turns it off for that device (`unsubscribeThisDevice`, before `logout`). Every email a member gets about the app's goings-on has a push counterpart: event notifications and announcements (queued per channel, see Event notifications), invitations, and a detail-free nudge with the daily digest. Application decisions are email only, since an applicant has no account, and so no device, until they're approved. iOS's swipe-from-the-edge Back is turned off in the installed app (`useBlockEdgeSwipe` in `AppShell`), because it slides the whole screen, bars included. Bringing it back properly would need a gesture of our own that moves only the page.

Everything in `AppStateProvider` is loaded once, when the `(app)` layout renders, and pages render from it without fetching, so `refresh` in `AppStateProvider` reloads it all through `loadAppStateAction`. That happens on every return to the app, every 60 seconds while it's on screen, and when the connection comes back, with refreshes at least 15 seconds apart. So what someone else did shows up within about a minute, and at once on coming back. Coming back after at least a minute away also checks first whether the server has been deployed since this copy loaded: `lib/app-version.ts` compares the commit built into the browser code (`NEXT_PUBLIC_APP_VERSION`, set by `next.config.mjs`) with `/api/version`, and on a mismatch reloads the page, because the old copy's Server Actions no longer exist on the new server. It's only checked then, not on the timer, because a reload would throw away a form someone is partway through. Next's `deploymentId` is no help here, since nothing on a self-hosted server reads it. That's the same `getAppStateForMember` (`lib/db/app-state.ts`) the `(app)` layout seeds from, so keep the two using it. A refresh that starts within 10 seconds of a change made in this session is dropped, in case it read the database before that change landed. That's what the `tracked` wrapper around every mutator records, so a new mutator needs wrapping too.

### Applications
There's no sign-up: someone joins by **applying** at `/apply` (public — `proxy.ts` lets it through; linked from the welcome page; a guest who RSVPed to a shared event arrives with their details filled in and no code to enter, see Sharing an event), and a **system admin** — a worker of the foundation running the platform, `members.is_admin`, set with `npm run admin -- add|remove <email>` — decides. The form (`components/welcome/apply.page.tsx`) collects what a member needs: a photo (cropped square in the browser like a profile photo, `toSquareJpeg`), first and last name, email, and their neighborhood. `lib/applications.util.ts`'s `validateApplication` is shared by the form and the server. After the form comes an **agreement step**: the short beta terms and privacy notes (`components/legal/beta-terms.tsx`, `beta-privacy.tsx`, also public at `/terms` and `/privacy`), sent with "Agree and send". The server refuses an application without the current `BETA_AGREEMENT_VERSION` and records the version and time on it (`agreement_version`, `agreed_at`). The notes describe what the code actually does, so change them when who-sees-what changes, and bump the version whenever either says something new. The full privacy policy and terms of use are drafted outside the repo and will replace them once the app settles. An application (`applications` table) starts `unconfirmed`: `lib/apply.ts`'s public Server Actions email a code (hashed on the row, 30 minutes, 5 tries, one email per address per minute), and entering it moves it to `pending`, so an admin never reviews an address its applicant doesn't own. Starting again replaces an unconfirmed one; an address with one `pending`, or that already belongs to a member, is refused; unconfirmed ones are dropped after a day.

Admins see a count in Home's **Needs you** (`AppState.pendingReviews`: applications plus members' new photos, `countPendingReviews`; null for everyone else) and review both at `/admin/review` (`review.page.tsx`), applications opening `/admin/applications/[id]` and photos `/admin/photos/[memberId]` (see Profile photos) — the one set of `(app)` routes that are Server Components fetching through the DAL themselves, since neither goes into AppState, and that 404 for anyone but an admin; the photo is served only to admins by `/api/applications/[id]/photo`. **Approve** (the top bar's action) creates, in one transaction, the member (their id from the `members` identity column — the seed scripts insert fixture ids and then move the sequence past them), their photo, their neighborhood membership and their Better Auth `user` row, which is what lets them sign in; **Decline** takes an optional note. Both email the applicant (`approveApplicationAction`/`declineApplicationAction`; the decision stands if the email fails, and the admin is told), and both clear the photo from the application. A new member has blank pronouns, occupation and bio until they fill them in. Later, people will be able to join without a neighborhood and ask to join one, validated by a random selection of its members; `applications.neighborhood_id` would then become optional.

### Authentication
Real auth now — Better Auth's email-otp plugin, still passwordless: the welcome page (`app/page.tsx`, outside the `(app)` group, no session required) collects an email and a one-time code. Its "Demo accounts" button lists members' emails, fetched by that server component (the page sits outside `AppStateProvider`) and dropped entirely in a production build so real addresses never ship to an unauthenticated visitor. `lib/better-auth.ts` is the only file that imports `better-auth` itself (matching the DAL's wrapping rule above) — it builds the `betterAuth({...})` instance with the Drizzle adapter (pointed at `lib/db/schema.ts`'s `user`/`session`/`account`/`verification` tables), `emailAndPassword: { enabled: false }` (this app has never had a password), and the `emailOTP` plugin configured with `disableSignUp: true` — a member without a matching seeded email should get the same "we don't recognize that email yet" rejection the old mock gave, not a new account. Better Auth's own `sendVerificationOTP` hook is deliberately a no-op, because Better Auth runs it as a background task and swallows its errors (a failed send would look like success): `requestLoginCode()` (`lib/auth.ts`) creates the code, reads it back out via `auth.api.getVerificationOTP()` (a Better Auth endpoint marked server-only — never exposed over HTTP), and emails it itself, so a failed send is reported to the person. **The code is returned to the browser only when `NODE_ENV !== "production"`** (the welcome page's inline "dev mode" hint) — in production the email is the only proof of owning the address, so leaking it would let anyone sign in as any member. `requestLoginCode()` also allows one code per address per minute (an in-memory cooldown, per server process — move it to the database if this ever runs on more than one instance), since the address is a member's real inbox; a failed send doesn't start it. Wrong-code attempts are limited by Better Auth's own default (3 per code).

`lib/auth.ts` still holds the three Server Actions the welcome page calls (`requestLoginCode`, `verifyLoginCode`, `logout` — same names/signatures as the mock version, so no call site changed), now calling `auth.api.sendVerificationOTP`/`getVerificationOTP`/`signInEmailOTP`/`signOut` instead of an in-memory pending-code `Map` and a plain cookie. Session cookies are Better Auth's own (`better-auth.session_token`), written via the `nextCookies()` plugin (must be last in the plugins array) — it forwards `Set-Cookie` headers from an `auth.api.*` call made inside a Server Action through `next/headers`'s `cookies()` automatically, which is what lets `lib/auth.ts` call `auth.api.*` directly with no client-side `authClient` and no mounted catch-all route handler. `lib/session.ts`'s `getCurrentUserId()` calls `auth.api.getSession()`, then looks the session's user back up by email via `getMemberByEmail()` to get this app's own `Member.id` — Better Auth's own user id is deliberately not linked to a member by foreign key (see `lib/db/schema.ts`'s comment on the `user` table); email is the one field both systems already agree on. `getCurrentUserId()` stays a separate file from `lib/auth.ts` on purpose — mixing a plain `next/headers`-using helper into a Server Actions file broke importing those actions from the Client Component welcome page, since Next tried to bundle the whole module for the client.

`proxy.ts` at the project root (not `middleware.ts` — Next 16 renamed the convention, and the exported function must be named `proxy`) is the primary route gate, and can't hold a real DB connection itself (middleware runs on the Edge runtime, incompatible with Drizzle's Node-only Postgres driver) — so it uses `better-auth/cookies`' `getSessionCookie()`, a presence-only check (decodes the cookie, doesn't hit the DB) that's safe there. `/` is explicitly excluded in the function body to avoid a redirect loop. `app/(app)/layout.tsx` calls `getCurrentUserId()` (a real, DB-validated check) and redirects defensively on top of proxy's cheap one — same division of labor the mock auth already had, not new.

The email + one-time-code shape maps closely onto how Better Auth's own `email-otp` plugin works, which is exactly why swapping to it didn't require redesigning the login flow — `requestLoginCode`/`verifyLoginCode`/`logout`'s signatures never changed.

### Email
`lib/email/index.ts` is the only file that imports `nodemailer` (the same wrapping rule as the DAL and Better Auth): everything sends through `sendEmail({ to, subject, text, html? })`. It speaks plain SMTP, so any provider (Postmark, Resend, SES, ...) or a self-hosted server is a change of `SMTP_URL`, not of code — prefer an SMTP relay over self-hosting the outbound server, since deliverability (SPF/DKIM/DMARC, IP reputation) is the hard part, not the protocol. Config is `SMTP_URL` (e.g. `smtps://user:password@host:465`) and `EMAIL_FROM` (an address on a domain the relay is set up to send as); in development `.env.example` points at **Mailpit**, a mail catcher in `docker-compose.yml` that shows every message at http://localhost:8025 and delivers none. With them unset, development just logs the message, and production throws instead of silently dropping a login code. `lib/email/templates.util.ts` holds the messages as pure functions (`loginCodeEmail(code)`), plain text first with matching inline-styled HTML. Emails so far: login codes, application confirmation codes and decisions (see Applications), circle invitations (see Circle invitations), bulletin announcements (see Circle resources), and event notifications and the daily digest (see Event notifications below). Anything member-typed goes through the template's `esc()` before it reaches HTML.

### Event notifications
Members are told about an event when it's created, and when a meeting or circle-hosted event is decided by its circle's consent. Two things vary independently, and the queue records both (`event_notifications.kind` and `.digest`):

**What happened** (`kind`), and who's told, in `lib/db/notifications.ts`:
- **`new`** — an event a person hosts, or a meeting a role-holder scheduled outright: the members of the circle it's shown to (`circleId`). A role-holder's meeting says who scheduled it and asks for RSVPs.
- **`proposed`** — no longer queued: an undecided meeting or circle-hosted event is announced by its consent proposal's "opened" notice instead (see Consent proposals). The kind stays for the rows and templates already written.
- **`approved`** — a meeting or circle-hosted event was decided by its circle's consent (its proposal passed: `approveHostedEvent`, from `lib/db/proposals.ts`), and **everyone in the circle it's shown to** (for the city root, every member) is told, in the transaction that passes it, always by an email of its own (`immediate`), since it's what opens it up to them, but whoever's answer passed it (none at the deadline). Not sent for one that's already over.
- **`updated`** — the organizer changed an event's date, time or location (`updateEventDetails`). Everyone going (`goingTo` in `lib/db/events.ts`: RSVPs, a meeting's voters among them, and slot holders, read before the slots are rewritten) is told by an email of its own straight away (`enqueueUpdateNotifications`, in the editing transaction). Other edits (title, description, agenda, slots) tell no one. The row's `change` column keeps when and where it was before, and the email shows each changed detail with its old value struck through. A member with an unsent one keeps it, with the older "was", since that's what they last heard; a sent one is replaced, so a later edit is news again; and one whose event was put back as it was before it went out is marked sent without emailing (`eventChanges`). "This and later" on a series tells each person once, about the soonest date they're going to (`andLater`). A cancellation withdraws an unsent one along with everything else.
- **`reminder`** — the event starts within `REMINDER_HOURS` (24, in `lib/events.util.ts`). Everyone going, organizer included (RSVPs, a meeting's voters among them, and slot holders), gets an email of their own: when and where, their own slots, and any slots still short of their minimum, with a warning that an empty required slot calls the event off an hour before it starts. Nothing earns it in a transaction: the 15-second poller queues it (`enqueueReminders`) once the event comes within range, locking the event and stamping `events.reminded_at` so it's queued once. Who's going is read then, so someone who signs up later gets none. A cancelled event and a proposal are skipped, and so is a meeting still short of its votes, until it's approved. An event created already less than a day out is stamped at creation (`writeEvent`), since its people have only just heard of it. Moving an event's date or start (`updateEventDetails`) drops any unsent reminder (`withdrawReminders`). It also clears the stamp if the event is now more than a day out, so it's reminded again, or sets it if it's within a day, since the `updated` email just went out. A reminder still retrying once the event has begun is dropped unsent.
- **`short`** — a required slot is still short an hour before the start: its host (organizer, plus a host circle's role holders, or all its members if it has none assigned) is told by an email of its own straight away, so they can find cover before it's cancelled automatically at 15 minutes (see Role-slotted events). Dropped unsent if the slot is filled first, the event is moved, or it starts.
- **`cancelled`** — the organizer cancelled an event others were going to, or it was cancelled automatically for a short slot (then its host is told too) (see Cancelling an event under Events belong to a circle). Everyone going, meaning its RSVPs (a meeting's voters among them) and slot holders, is told, always by an email of its own straight away (`enqueueCancellationNotifications`, in the cancelling transaction). Anything not yet sent about the event is withdrawn first (`withdrawEventNotifications`), so no one hears "new event" after "cancelled".

**How it's delivered** (`digest`) depends on the size of the circle being told (`queueFor`): a circle with **no sub-circles** gets an email of its own, right away; one **with sub-circles** — a neighborhood, the city — gets a line in its members' **daily digest** instead, since an email per event would be too much for a big audience. This applies to `new`, `proposed`, and a *meeting's* `approved`. A circle-hosted event's `approved` is the exception: it's always its own email (`immediate`), because it's what opens the event to that audience at all.

In every case the person whose own action caused it (the creator; the member whose answer passed a proposal) is skipped, and nothing goes out for an event already in the past.

**Channels.** Everyone told is told on every channel they can be reached by (`channelsFor` in `lib/db/notifications.ts`): **email** if they have an address, and **push** if they've turned it on for a device (a `push_subscriptions` row). Each channel is its own queue row (`channel`, part of both queue tables' keys), claimed, retried and marked sent on its own, so a failed push never resends an email or the reverse; someone with neither can't be told. A digest line is email only (no push row is queued for it). `lib/notify.ts` drains the two channels side by side (`deliverEventNotifications` runs both, so a slow mail relay never holds up a push), with the same skip rules. A push says what its email says in the few words a lock screen shows (`lib/push/messages.util.ts`, the counterpart of `templates.util.ts`, sharing its date formatting through `fmtEventWhen` and `relativeDayWord`), opens the event, and is tagged by event, so a newer push about it replaces one still showing. An edit notifies only the people going, and only for a new date, time or place (`updated`, above). There are no per-member preferences or unsubscribe yet, which the beta will want before it emails real people at any volume.

**The daily digest.** `lib/notify.ts`'s `deliverDigests` sends one email per member listing what's been queued for them since the last send, grouped by the circle they belong to (a proposal by its host circle) and soonest first: new events and a role-holder's meetings (rows from before consent may still list a proposal to vote on or an approved meeting). A meeting that was proposed and then approved since the last digest is listed once, as approved. The heading says "N new events" while that's all it is, and "N updates" once it mixes in the rest. It goes out once a day at `DIGEST_HOUR` (0–23, default 8, in the server's local time — set `TZ` on a server that isn't in the community's timezone): rows are *due* once queued at or before the most recent send time, so something that happened after this morning's send waits for tomorrow's, and there's no "did today's run happen" record — due rows are marked sent as they go, so the next poll finds none, and a server that was down at send time simply sends when it comes back. Events already over by then are left out, and a digest with nothing left to say isn't sent. Once a member's digest email has gone, any device they've turned push on for gets a nudge with none of its detail ("Your daily digest is in your inbox", `digestPush`), best effort and never retried, since a late nudge would point at old news; it isn't queued, so there's no push without the email. One caveat: the digest claims each member's rows together, so two servers draining at once could split a member's rows across two emails; a single instance can't.

It's a Postgres-backed queue: `event_notifications` has one row per (event, member, kind, channel) — a member can be owed a proposal email and later an approval email for the same event, each by email and by push — inserted **in the same transaction as the change that earns it** (`insertEvent(event, { notifyMembers: true })`, which only `createEvent` passes — seeding never emails anyone — and `setVote`'s approval), so an event is never created without its emails queued or the reverse. `lib/notify.ts`'s `deliverEventNotifications()` drains it: `createEventAction` and an approving `setVoteAction` schedule it with Next's `after()` so it runs right after the response is sent (members hear about it within a second or two), and `instrumentation.ts` starts a 15-second poller at server boot — which also drives the digest — as the safety net for failures, leftovers from a restart, and other server instances. The database is what prevents double sends: rows are claimed with `FOR UPDATE SKIP LOCKED` and a row can't be claimed again until 5 minutes after its last attempt (which is also the retry backoff), up to 5 attempts, with the last error kept on the row. Each email is rendered at send time from the event's current data, so a proposal approved in the seconds before its email goes out (and not already dropped) is sent as an ordinary event rather than as a request for votes. The poller is started once at boot by `instrumentation.ts` and **doesn't hot-reload**: restart `npm run dev` after changing notification code, or the running server keeps sending with the old one. `lib/db/notifications.ts` decides *who* and never touches SMTP; `lib/notify.ts` sends and never decides who.

### Data model
Three concepts, all in `lib/types.ts`: `Member`, `Circle`, and `Event`. `lib/data.ts`'s `MEMBERS`/`CIRCLES`/`EVENTS` are the seed dataset only (read through `lib/db/` at runtime). Every event belongs to exactly one circle (`circleId`) and always has an `organizerId` — the member who created it and the only person who can edit it (`isEventOrganizer`). `circleId` is who the event is shown to (and who would be notified of it); it is *not* the host. An event is hosted either by its organizer or, when `hostCircleId` is set, by a circle — which need not be the one it's shown to (the Finance Council can host an event shown to The 903). A circle-hosted event starts as a proposal (`proposed`) — see Events belong to a circle below. `currentUserId` is a real, dynamic value resolved at login (see Authentication) and threaded through as a prop from `AppStateProvider` downward. Components go through `AppStateProvider`'s state (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, via `useAppState()` or the `lib/hooks.ts` wrappers) for everything, static or not.

### Governance is the trickiest business logic
Two things are decided by a circle's own members, **by consent**: a **meeting** (`kind: "meeting"`, see `EVENT_KINDS` in `lib/governance.util.ts`), held by its circle for its own members, and an event a **circle hosts** (see Meetings and circle-hosted events, by consent, above). A meeting can't be held in the root circle (its roster is implicit) or a group, carry signup slots, or be circle-hosted (its circle *is* the one deciding). **Wording:** "approve" is still the word for a decided meeting or circle-hosted event in the code (`isApproved`, `approveHostedEvent`, the `approved` notification kind), while what people read says it's *scheduled* once its circle *consents*; don't reintroduce "confirm" (the generic `ConfirmModal` is unrelated: it's a confirmation dialog). `lib/governance.util.ts` (`kindOf`, `isMeeting`, `isScheduledMeeting` — a role-holder's, with no consent asked — `isCircleHosted`, `isProposal`/`awaitingConsent` — undecided, so in no list — `isGoverned`, `isApproved`, `isEventOrganizer`, `canManageEvent`, and `majority`, kept only for the conversion) encodes these rules as pure functions shared between the event list and detail views — extend that module rather than duplicating logic per component. A federation-wide council flow (event kind `council`, proposals, ratification, neighborhood endorsements) existed and was removed as unused; it would return as a meeting hosted by the root circle with its child circles' endorsements.

### Meeting agendas
A meeting has an **agenda** instead of a description (`Event.agenda`; its `description` is stored as `""`). The agenda is an ordered list of items, called **topics** in everything people read ("Add topic", "Topic 2", "Give agenda topic 1 a title") though the code says `AgendaItem`. Each is marked with Sociocracy's R/E/D, meaning what the circle will do with it: **Report** (hear it), **Explore** (talk it through, no decision) or **Decide** (decide it, by consent). `lib/agenda.util.ts` holds the categories (letter, label, and the hint the form shows) and `validateAgenda`, which `validateEventDraft` runs for every meeting. A meeting needs at least one item, and an ordinary event can't have any. Items live in `event_agenda_items`, one row per item with its `position`. They are rewritten as a whole with the meeting (`writeAgenda` in `lib/db/events.ts`) and deleted with it (`ON DELETE CASCADE`).

On the event page (`components/events/agenda-section.tsx`), the agenda is a numbered board of cards shaped like the bulletin's (`BulletinCard`). Each card is ruled along its top in `--color-agenda`, a turquoise teal, and headed by its category's letter in a solid square (`AgendaBadge`) beside the category's name. The event form's Agenda row opens a view of its own that edits it with `AgendaEditor` (`agenda-editor.tsx`): a three-way R/E/D choice per item, a title, optional details, and reordering. Its top bar Done stays disabled until every topic in it has a title, a blank one included (fill it in or remove it). A meeting's notification email lists the agenda the same way, as cards in the HTML and "1. [D] Decide: …" lines in the text. Migration `0016` moved each meeting's old free-text agenda into a single Explore item titled "Agenda", for its organizer to split up.

### Meeting availability
A member says once when they can do meetings (`members.availability`, jsonb, `AvailabilityWindow[]`: some days, 0 = Sunday, and a start and end in minutes from midnight, wall-clock like an event's, never crossing midnight) and every meeting a circle of theirs plans is checked against it. **`null` is never set, and shows as Unknown; `[]` is set to nothing, and shows as Not available** — keep them apart. Two states only (available or not); preferred levels, per-circle schedules, one-off away dates and calendar import are future work. `lib/availability.util.ts` holds the rules the form, the page and the server share: `validateAvailability` (quarter hours, up to `MAX_AVAILABILITY_WINDOWS`, at least one day each), `normalizeAvailability` (the one stored form: each day's ranges joined, days with the same range grouped, in time order, so overlapping windows are fine to enter), the quick-pick `AVAILABILITY_PRESETS` and `availabilityFor`, which says whether someone can attend a date and time (one range must cover all of it) and, when they're free as it begins but not through the end, `freeUntil`.

It's edited at **Settings → Meeting availability** (`/settings/availability`, `availability-settings.page.tsx`): quick-pick chips that each add (or remove) a window, a read-only week preview, and the windows themselves, each a row of day chips with From and To time fields, like one of iOS's sleep schedules. Save is the top bar's, as on the other settings pages. It's the member's own, so it's on `Profile.availability` (via `getOwnSettings`) and never on `Member`; `AppStateProvider.saveAvailability` is await-then-update and adopts the server's normalized schedule, and `saveAvailabilityAction` always writes the session member's row.

**Where it shows:** the meeting form (`components/events/meeting-availability.tsx`, on the Meeting tab under the date and time, create and edit) lists the circle's members as Available, Not available (with "free until …") and Unknown, with a count. **No one's schedule is sent to a browser:** the form asks `meetingAvailabilityAction` about the one time chosen, and `getMeetingAvailability` in `lib/db/availability.ts` answers it only to a member of that circle, only for a circle that can hold a meeting (not the city, not a group), and a non-member of a group is told it doesn't exist. A meeting that runs past midnight isn't checked. The beta privacy notes say what members see; change them, and bump `BETA_AGREEMENT_VERSION`, if that changes. The demo seed gives members 1-5 schedules (`AVAILABILITY` in `lib/data.ts`) and leaves the rest Unknown.

### RSVP state is duplicated by design
`rsvpState` (`{ [eventId]: true }`, current user only) exists alongside each event's own `rsvps` array and the two are updated together in lockstep (see `toggleRsvp` in `AppStateProvider`). This lets "am I going?" render without scanning arrays while keeping counts and rosters correct everywhere else. Keep both updates atomic if this handler changes. (There used to be a matching `voteState` for meeting votes; voting is gone.)

### Add to calendar
Once someone's going to an upcoming event (`isAttending`: an RSVP or a slot), its page's menu offers **Add to calendar**, a link to `/api/events/[id]/calendar`. That route serves the event as an iCalendar file (`eventCalendarFile` in `lib/calendar.util.ts`), only to a member who may see it (`getVisibleEvent` in `lib/db/events.ts`), and inline as `text/calendar`, which is what makes a phone offer to add it. Event times are the community's wall-clock time with no zone of their own, so they're converted to UTC in `TZ` (falling back to `America/New_York`), the same variable the daily digest's hour is read in. It carries an alert an hour before the start (a `VALARM`), on top of the reminder email the day before. It's a one-off copy: later edits and cancellations don't reach it. A per-member calendar subscription that stays in sync would need a private, revocable feed URL, since calendar apps fetch without a session.

### Sharing an event
A member can send an event to someone with no account. **Share** in the event page's menu (`useEventSharing`, `components/events/event-sharing.tsx`; not offered for a meeting, an event awaiting consent, a cancelled one and one that's over, which the server refuses too) makes the member's own link, `/e/[token]`, and opens the phone's share sheet on a phone, copies it elsewhere. The link is a bearer secret: anyone holding it sees the event's public page and, while it's live, can RSVP. Events shown to a **group** can be shared; the page never names the group.

**Links** (`event_share_links`, `lib/db/event-shares.ts`): one live link per (event, sharer), so who invited whom is known. **Stopping** one sets `revoked_at` rather than deleting it, so guests who came by it still say who invited them; sharing again makes a new token. The sharer stops their own; whoever manages the event (`memberManagesEvent`, the same rule as editing or cancelling: its organizer, or any member of its host circle) can stop every link to it. Stop sharing, in the same menu once there's a link to stop, does either, asking first. A stopped link opens a 404 and takes no new RSVPs; **guests who already RSVPed stay on the list** and keep their emails.

**The public page** (`components/events/shared-event.page.tsx`) is built from `SharedEvent` (`lib/types.ts`), never `Event` or `Member`: no member ids, so nothing in it can link to a profile; photos are the same grey placeholder; people going are **first names only**. A signed-in member who can see the event is redirected to `/events/[id]`. The page is `noindex` with no referrer. Pasted into a message it **previews as the event**: `generateMetadata` in the page sets the title (the event's name) and description (who invited you, when, where; "Online" for a meeting link), and `opengraph-image.tsx` draws the picture from the same `SharedEvent`; a dead link gets only the wordmark. Messaging apps cache a preview by URL, and some (WhatsApp, Slack) fetch it on their own servers. It's the one place outside the app that shows an event, so `getSharedEvent` is where what a stranger sees is decided.

**Guest RSVPs** (`event_guest_rsvps`, `lib/db/guest-rsvps.ts`; public Server Actions in `lib/guest-rsvp.ts`): a guest gives a name and email, enters a code emailed to them (hashed, 30 minutes, 5 tries, one per address per minute), and is then on the list. Not a member and not a login. Only for a plain-RSVP event (not one with roles). An address that belongs to a member is told to sign in. Abuse limits live in the DAL, since the form is public and a code goes to whatever address is typed: per address, 50 per event per hour, and 10 per connection per hour (`takeCodeAllowance`, keyed by a hash of the IP). A confirmed RSVP is remembered in the `guest_rsvps` cookie (its id), which also lets the guest take it back from the page, after confirming. Members see guests in an event's Who's going as non-clickable first names (`Event.guests`), counted in "N going"; an event with a guest going is cancelled rather than deleted (`cancelOne`).

**Guest emails** (`guest_notifications`, `lib/db/guest-notifications.ts`, drained by `deliverEventNotifications`): a confirmation, and when the date, time or place changes or the event is cancelled, reusing the member emails (`guestEmail`). Email only. A group's name is replaced by "Circles". Each ends with a link to `/e/stop/[id]`, where buttons (opening the page changes nothing, since mail scanners open links) either stop the emails or delete the guest's details; the id in the link is the capability. A guest's name and email are deleted 30 days after their event, and an RSVP never confirmed after a day (`purgeGuestData`, hourly from the poller). The privacy notes say all this.

**Becoming a member:** the Apply button after RSVPing goes to `/apply?guest=<id>`, honored only if this browser's cookie holds that RSVP. The application is prefilled with the email locked, skips the code step and goes straight to review, recording who invited them and through which event (`applications.referred_by`, `referred_event_id`), which the review pages show. On approval their guest RSVPs for live, upcoming events shown to the city or their neighborhood become real RSVPs (`adoptGuestRsvps`); others stay guest RSVPs.

Home (`components/home/home.page.tsx`) opens with a greeting (`Greeting`: today's date over "Good morning, Mira", by the time of day, read from `useClock` so the server renders a plain hello), then **My circles**, the way into everything else, then the rest in the order people come back for things, its sections 40px apart and each gone when it has nothing to show: Starting soon, the prompt deck (see Home's prompts), **Needs you**, **Up next** and **My tasks**. It has no masthead: who you are is the top bar's action, your photo (`ProfileMenu`, `components/shared/profile-menu.tsx`, built on `TopBarMenu`), raised like the bar's other actions with a hairline ring inside it, which opens a small menu of My profile and Settings dropping from it like a context menu, the button pressed in (its shadow gone) while it's open; a tap outside, Escape or choosing an item closes it. Each section's heading is `HomeSection` (an eyebrow with its count, the attention dot when it's what lit the Home tab's, and a link to the whole of it on the right). **Needs you** (`needs-you.tsx`, reading `useNeedsYou` in `lib/hooks.ts`, which the Home tab's dot reads too) is one list of `LinkRow`s, each with an icon: an admin's reviews, proposals waiting on your answer (the orange hand), invitations (an envelope), then your own open proposals, quieter (a grey hand), titled "Your proposals" when they're all there is. **Up next** (`up-next.tsx`) is the soonest three of your events (`isMyEvent` in `lib/events.util.ts`: going, or organized, the same rule as the Events tab's Mine), each saying which: Hosting (organized for no circle), Going, or Organizing (for a circle, not going), or, while you're going to nothing, the next two in your circles (one date of a series) under "Coming up in your circles", each with its RSVP, which moves it up into yours; with **My events ›** to the Events tab filtered to yours (`/events?show=mine`, its Show filter's Mine, past ones included; the filter lives in the URL, so the Events tab's plain `/events` shows everything). **My tasks** (`my-tasks.tsx`) are rows rather than the Tasks tab's table, ticked with the same `useTaskTick`; one ticked done there stays, struck through, until Home is left, so it can be put back as it was. **My circles** (`my-circles.tsx`) is a shelf of cards scrolling sideways (208px, so a phone shows one and a half to two), each with a few members' faces and how many there are, your neighborhood first, so joining more never pushes the rest down.

### Starting soon
Home opens with a hero card (`components/home/starting-soon.tsx`) for an event you're going to (`isAttending`, or your own RSVP) from 15 minutes before it starts until it ends: an ink card linking to it, with the countdown ("In 12 min" under "Starting soon", then "Now" under "Happening now") on a tilted paper sticker in the same playful type as a profile's "Born in the" decade. One at a time, never a cancelled one: the next to start if one's coming up, otherwise the one under way that began last. It's computed on render from `useClock()` (`lib/hooks.ts`), which ticks every 15 seconds and is null on the server, so the card never mismatches during hydration; nothing about it is stored.

### Repeating events
When creating an event (circle-hosted or not — **not a meeting**, for now: `validateEventDraft` refuses one, and the form hides "Repeats" for a meeting), the form's "Repeats" can make it **weekly** or **monthly**, with an optional last date ("Until"). The pattern is read from the first date (`lib/recurrence.util.ts`, pure). Weekly repeats that weekday. Monthly repeats its place in the month ("the 2nd Tuesday"), not the day number; a first date on the 29th–31st means "the last" such weekday. Editing can't turn a one-off into a series or change the pattern.

**Storage: a series plus materialized dates.** `event_series` holds the pattern and a template (title, times, location, description, slot definitions, circle, host, organizer). Each date is an ordinary `events` row with `series_id` set, so RSVPs, votes, slots, visibility, cancelling and notifications all work per date with no special cases, and `Event.repeat` just says which series a date belongs to. Dates exist only `REPEAT_HORIZON_DAYS` ahead (4 weeks weekly, about 2 months monthly), so a weekly event doesn't flood the list. `extendSeries` in `lib/db/events.ts` adds them: when the series is created, when a circle-hosted one is approved, and from a 10-minute poller (`lib/series.ts`, started by `instrumentation.ts`, which also doesn't hot-reload). `generated_through` is how far a series has got, so a date that was deleted is never made again, and the series row is locked while it's extended. A new date starts like a created event: the organizer attends, with empty slots.

**Governance.** A circle-hosted series is consented to **once**: only its first date exists until its proposal passes, and passing it (`approveHostedEvent`) approves the series (`event_series.approved_at`) and adds the rest, already approved. While it's waiting it can't be edited (what's proposed is what's consented to). Meetings don't repeat yet; if they come back, the open question is whether a series is consented to once or date by date.

**Notifications.** The circle is told **once**, by the first date's usual `new`/`proposed`/`approved` notice, whose email and digest line say how it repeats. Later dates are added silently.

**This date or this and later.** The organizer's edit form offers either scope for a date of a live series (`SeriesScope` in `lib/events.util.ts`). "This and later" applies to every later date not already cancelled and to the template, and keeps each date's slot signups by slot name, but the day itself only moves one date at a time. Cancelling "this and later" runs the usual cancel on each date (deleted if no one else is going, otherwise marked cancelled) and ends the series the day before (`until`), so nothing more is added. Someone going to several of those dates gets **one** cancellation email, about the soonest, saying the rest are off too (`endedBefore`). Both return every event they changed, and `AppStateProvider` merges them in.

### Role-slotted events and automatic cancellation
Some events define `roles` (shift lead, librarian, etc.) with `min`/`max` instead of a plain RSVP list; a role with `min >= 1` is required. An event whose required slot is still short as it comes up goes through a lifecycle (`lib/roles.util.ts`): more than an hour before the start it's a neutral "needs slots" note (`shiftNeedsSlots`); within the hour (`SLOT_WARNING_MS`) it's **at risk** (`shiftAtRisk`, a yellow `ShiftStatusBanner` saying when it cancels — yellow, `--color-warning`, being a heads-up rather than the orange of a decision waiting on members), and its **host is told** — its organizer, and for a circle-hosted event the host circle's role holders (Leader, Secretary, Facilitator and its own roles; a holder who's left the circle doesn't count) if any are assigned, otherwise every member, who might know someone to cover it (`hostOf`, the `short` notification); and **15 minutes before** (`AUTO_CANCEL_MS`), if it's still short, it's **cancelled for real** — `cancelled_at` plus `cancelled_automatically`, final like an organizer's cancellation but never deleted — and everyone going and the host are told (`cancelled`, whose email, push and `CancelledBanner` say it was automatic and which slot was short). `checkUnfilledSlots` in `lib/db/events.ts` does both, from the 15-second notification poller, locking each event as it decides. Like `enqueueReminders`, it bounds its queries by `events.date` (indexed) before comparing start times, which no index covers, so each check reads a day or two of events however many there are. The 15-minute check is a one-time decision: an event whose slots are filled at that point has `auto_cancel` turned off, so someone dropping out afterwards only brings the warning back rather than calling it off at the last minute; and one created or moved to start within the hour starts with `auto_cancel` off (`Event.noAutoCancel`) — its host is warned, but it's never cancelled automatically. The host is warned once (`slots_warned_at`); moving the event clears that and withdraws an unsent warning. The at-risk and needs-slots states are derived from the clock on render (`ShiftStatusBanner` re-renders through `useClock`); only the cancellation is stored.

### Events belong to a circle
An event's circle decides who can see it: only that circle's own members — not its parent or child circles — plus, for the root (city) circle, everyone, since everyone is implicitly in the city (`isCircleAudience` in `lib/circles.util.ts`; the implicit-root rule applies to events only). Enforcement is server-side: `getEventsForMember` in `lib/db/events.ts` only ever returns events in the member's circles or the root, so anything else is never sent to their browser (its `/events/[id]` 404s and it's absent from every list), and every write goes through a DAL function that takes the session's `memberId`: `createEvent` (requires the circle's audience, forces the organizer, generates the id and the starting rsvps itself), `updateEventDetails` (its organizer, or any member of its host circle — see Who manages an event — and not once the event is over — `isPastEvent`, the day after its date, as for cancelling; the menu leaves Edit out and the edit page 404s to match; never changes circle, kind or organizer, and keeps signed-up slot members by role key), `setRsvp` and `toggleRoleSlot` (audience only; slot max and one-slot-per-person enforced; refused once the event has ended — `hasEnded` in `lib/events.util.ts`, from its end time, the next day's for one that runs past midnight — and on the page `useEventEnded` turns those controls off at the same moment, re-checked as `useClock` ticks, rather than only from the next day as `isPastEvent` does). A member outside an event's audience gets the same "doesn't exist" error as for a missing event. An event's circle and host circle are locked after creation.

**Cancelling an event.** Its organizer can cancel it from the edit form (`cancelEvent` in `lib/db/events.ts`, through `cancelEventAction`), but not once it's over. What happens depends on whether anyone else is going to it, meaning an RSVP or a slot. If someone is, the event is marked cancelled (`events.cancelled_at`, `Event.cancelled`), stays visible where it was with a Cancelled banner and badge, and each person going is emailed. If no one is, it's deleted, along with its RSVPs, votes, slots and notification rows. One still waiting on its circle's consent is withdrawn instead: its proposal is closed and the event discarded (see Meetings and circle-hosted events, by consent), even after its date, since it never happened. The proposal page shows a refused withdrawal under its Withdraw button. It's decided under a row lock, and it's final: every event write (`updateEventDetails`, `setRsvp`, `toggleRoleSlot`) refuses a cancelled event, and its edit page 404s.

**Roles, not slots.** What people read calls an event's signup positions **roles** ("Roles" on the event page and form, "a required role" in emails); the code still says slots (`SlotsEditor`, `shiftNeedsSlots`, `checkUnfilledSlots`, `toggleRoleSlot`) and its data `Event.roles`, and the docs below use either word. They're unrelated to a circle's roles (Secretary, Leader…).

**The event form's layout** is built for a phone: a Event/Meeting switch (new events only), then flat sections between hairlines — title; date, time and repeats, then location; description; who it's shown to and hosted by — with no box around the whole form. What would nest, **slots** (an ordinary event's) and a meeting's **agenda**, are each a `MenuRow` that swaps in a view of its own (`view` state in `event-form.page.tsx`, so the draft survives; `SlotsEditor` is a flat list, a slot per row), whose top bar action is Done, which keeps its changes, and whose Back returns to the form without them, as the view found them (`viewStart`), asking first if anything changed. There's no "Use slots" switch: an event has slots when any is named, and unnamed ones are dropped on leaving the view.

**Circle-hosted events.** The event form's "Hosted by" is a dropdown of the person and the (non-root) circles they belong to that are the chosen Circle itself or inside it (`isWithinCircle` in `lib/circles.util.ts`, re-checked by `createEvent` on the server) — so PVD Things can't host an event shown to The 903, while the Finance Council can — and changing the Circle drops a host that no longer fits; choosing a circle turns the form orange ("Propose event") and proposes it to that circle for its members' consent (see Meetings and circle-hosted events, by consent): only the host circle's members can see it (`getEventsForMember` and `canSee` in `lib/db/events.ts` are the SQL and per-row forms of the same rule — keep them in step), it's in no list, and RSVPs and slot signups are refused until it's scheduled. Once it is, it becomes visible to `circleId`'s audience as well as staying visible to the host circle's members, and reads as an ordinary event (host shown as the circle, its organizer named); any of the host circle's members can edit or cancel it (see Who manages an event). A group's events are shown only to the group. `insertEvent` is the raw trusted insert only the seed scripts use. In the event form a "Circle" dropdown (the member's circles plus the city, home neighborhood first; meetings exclude the city) is who it's shown to, and slots are available on any ordinary event. `validateEventDraft` in `lib/events.util.ts` is the one pure check shared by the form and the DAL; among other things it refuses a date before today, so nothing is created in, or edited into, the past (only the seed scripts' raw `insertEvent` skips it), and with `{ creating: true }` (the new-event form, and `createEvent` on the server) a start time that's already passed — not on an edit, so an organizer can still fix an event already under way today. The form's date field also has `min` set to today, so date pickers grey out earlier days; nothing does that for times, which only this check catches. A new event starts at the next quarter hour, for two hours (`defaultEventTimes`), and moving its start moves its end, keeping its length (`endAfterStartMoves`).


### Shared design tokens and components
The design system lives in one place now: the `@theme` block in `app/globals.css` (Tailwind v4 CSS-first config) — colors, fonts, and the type scale as CSS custom properties Tailwind utility classes read from. This used to be duplicated in a parallel `lib/theme.js` of JS constants for components still using inline `style={{...}}`; once the last such component was converted, `lib/theme.js` was deleted rather than left as dead weight — see Coding style below for how that migration worked. `components/shared/` holds the generic pieces reused across pages (`Eyebrow`, `TabbedPanel`, `SearchWithFilter`, `Tag`, `Chip`); `components/events/` has the event-specific reusable pieces (`DateTile`, `VoteButton`, `RsvpButton`) — reuse these rather than re-implementing per page. `components/shared/index.tsx` is a barrel re-exporting everything in the folder, so `import { Button, Label } from "@/components/shared"` works alongside (not instead of) importing a single file directly (`@/components/shared/button`) — both are valid, existing call sites weren't migrated to the barrel.

**Focus, tap areas and the smallest text.** Keyboard focus shows as a square 2px ink outline set 2px off the element, for the keyboard only (`:focus-visible` in `app/globals.css`'s base layer); fields show theirs with their own ink bottom rule instead, and on the ink bottom nav (`.on-ink`) it's paper. Don't switch it off with `outline-none` on anything but a field. Every control's tap area is at least 44×44px: a control drawn smaller (a tag's ×, a name, a chip, a switch, a tab, a compact button) gets the `hit` class, an invisible layer centred on it (in the components layer, so a positioning class still wins), and two controls flush against each other get a minimum size instead, so their areas don't overlap. No text is smaller than 11px (`text-label`); there's no smaller size in the theme. The one exception is the small date tile (`DateTile`), whose month and weekday stay at 9px and 8px: at 11px the tile grows too tall for a list on a phone, and the day number beside them carries the date.

**Fields are filled; buttons are outlined.** A text field, text area or select (`Input`, `TextArea`, `Select`) is filled with the `wash` grey and ruled along its bottom in `soft` grey, the rule thickening to 2px ink while it has focus (`FIELD` in `components/shared/input.tsx`); the resting rule is there so an empty field can still be told apart from the page, since the grey alone barely shows against white. A row holding bare inputs and controls of its own (an aim and its ×, a day and its hours) is styled as one field with `FIELD_ROW` and `ROW_INPUT`. A field that can't be changed looks it: white, a dashed faint outline, grey text, a not-allowed cursor, and no chevron on a select (`DISABLED_FIELD`, `FIELD_ROW_DISABLED`); a read-only one (Edit myself's email) looks the same. The search bar (`SearchWithFilter`) is one filled field with its filter funnel inside it. Buttons, chips, cards and toggles keep their ink outlines, which is what tells them apart from fields.

**Every clickable, bounded element without a shadow inverts when pressed** (a bordered or filled button, chip, card, square or choice), through `PressFeedback`'s classes in `app/globals.css`: a paper one turns ink (`ink-press`); a filled one turns paper with its colour in its text and outline (`btn-invert` with `btn-ink`, `btn-teal`, `btn-flame`, `btn-leaf`, `btn-danger`, or `btn-accept`, which keeps ink text since yellow can't be read on white); a link holding a filled square and text inverts just the square (`fill-press`); and an on/off chip uses `togglePress(on)` (`components/shared/press-feedback.tsx`), since `ink-press` alone leaves a selected (ink) one unchanged. Exceptions: anything with a shadow (the top bar's filled circles, the floating action button), list rows, tabs, switches, text links, and small icon-only controls inside a field.

**An empty list says so in one shape** (`EmptyState`, `components/shared/empty-state.tsx`): a soft serif sentence saying what will appear there, and, where there's something to do about it, the action that fills it as a compact outlined button linking to its page (Home's My circles: Browse circles; Up next: Browse events; the Events list: Create an event). An empty search says nothing matched, with no action. A small inline status ("None yet." under a tag field, a proposal's "No answer yet") isn't one.

**Outlines mean something to tap.** What's only read isn't boxed: a tag (`Tag`: a profile's skills and interests, a circle's offers and needs) is a grey chip in sentence case with no outline, and a section of a page is set off by hairlines and spacing, never a box. An outline stays where it frames a chart or a form (the availability preview, the roles table).

**An event page leads with when.** Under its eyebrow, a phone shows the date as a headline and the time beneath it; wider, where the date tile shows the date, the time line stands alone. The RSVP button only RSVPs ("RSVP", then "Going" with a check); how many are going is said beside it ("12 going", "12 went"), never inside it. The name game is Learn names in the top bar's menu on your own neighborhood's page, once someone else lives there; it belongs to the Circles tab, and leaving it goes back, or to your neighborhood when there's nothing behind it (`useGoBack` takes a page's own `up` for a parent its URL can't say). Opened with no one else there, it says so rather than starting.

Every dialog is built on `components/shared/modal.tsx`'s `Modal` (`ConfirmModal` and `AlertModal` included): a dimmed overlay and a borderless paper box with the same soft shadow as the bottom nav, closed by a tap outside, Escape, or its close button. Given a `title`, it has a header laid out like the top bar's — the close X on the left, then the title — so don't hand-build a dialog header. That X, the top bar's Back and the + at the end of a tab row are one component, `GhostIconButton` (`components/shared/ghost-icon-button.tsx`): an icon with no fill whose circle shows faintly while pressed.

Toasts go through a `ToastProvider`/`useToast()` context (`components/shared/toast.tsx`) mounted in the true root `app/layout.tsx` — outside and above `app/(app)/layout.tsx`'s `AppStateProvider`, on purpose: it's the one provider both the unauthenticated welcome page and the authenticated app need, so the welcome page's login form gets `useToast()` for free. Components fire toasts via the hook rather than managing their own transient UI state. A toast is floating chrome like a dialog: no outline, the bottom nav's soft shadow, its tone as a colored rule down the left, and a `GhostIconButton` to dismiss it. It sits just beneath the top bar, offset by the `--top-bar-height` the bar publishes (falling back to the notch inset on the welcome page, which has no bar).

## Code organization

Files are grouped by domain, not by component type: `components/shared/`, `components/circles/`, `components/events/`, `components/home/`, `components/profile/`, `components/game/`, `components/settings/`, `components/welcome/` — one component per file, with the file's kebab-case name matching its PascalCase export (`event.page.tsx` exports `EventPage`; see Coding style below for the `.page.tsx` suffix). `components/providers/` holds the app-wide context providers (`app-state-provider.tsx`, `back-handler-provider.tsx`, `top-bar-action-provider.tsx`) — they're components (they render JSX), just not ones any single domain owns. `components/shared/app-shell.tsx` is the nav wrapper (`TopBar` + `BottomNav`) rendered once in `app/(app)/layout.tsx` around every authenticated route; the button-press interaction CSS it used to carry in an inline `<style>` tag now lives in `app/globals.css` instead, since the unauthenticated welcome page needs those same classes and sits outside the tree `AppShell` wraps. `lib/` holds everything that isn't a component: `data.ts` (seed data, not imported by app code), `governance.util.ts` / `roles.util.ts` (an event's signup slots) / `recurrence.util.ts` (a repeating event's dates) / `format.util.ts` / `circles.util.ts` / `circle-roles.util.ts` (a member's roles in a circle) / `events.util.ts` / `members.util.ts` / `nav.util.ts` (pure helper functions), `hooks.ts` (`useMembers`, `useCircles`, `useAppNav`, ...), `auth.ts` / `session.ts` / `better-auth.ts` (auth — see Authentication), `email/` and `notify.ts` (outgoing email and the notification sender — see Email), `series.ts` (the poller that adds repeating events' dates), and the `lib/db/` subfolder (the data access layer — see that section) — these are `.ts` since they hold no JSX. When adding a new component, put it in the folder for the domain it belongs to; when adding cross-domain UI (used by 2+ domains), it belongs in `components/shared/`.

`app/` has three things at its root: `layout.tsx` (minimal — just `ToastProvider`), `page.tsx` (the unauthenticated welcome/login route — a thin wrapper rendering `components/welcome/welcome.page.tsx`'s `WelcomePage`, the same route-pages-wire/`components/`-render split used everywhere else), and the `(app)/` route group holding everything else plus its own `layout.tsx`. Within `(app)/`, each route mirrors the route list above one-to-one — each `page.tsx` is a thin client component that pulls data from `useAppState()` and wires navigation via `useAppNav()`/`useRouter()`, then hands everything to the actual UI component from `components/`. Keep that split: route pages own data-fetching-and-wiring, `components/` own rendering, so a component never has to know whether it's reached via routing or (hypothetically) something else. `proxy.ts` sits at the project root, a sibling of `app/`, not inside it — that's a Next.js convention, not a choice.

## Coding style

- **Tailwind (v4) for styling, using the theme tokens — not inline `style={{...}}` objects, and not CSS Modules.** This is a reversal of an earlier decision: inline styles were deliberate while the app was a single 3900-line file being split apart (adding a build step then would have widened that migration's scope), but now that the split is done, Tailwind is in. The migration off inline styles + `lib/theme.js` is complete — `lib/theme.js` itself has been deleted now that nothing imports it, and no component still uses a static inline `style`. `components/shared/eyebrow.tsx` and `components/shared/tag.tsx` are reference examples of the converted style (utility classes, `bg-ink`/`text-soft`/`font-sans`/`text-eyebrow`/`tracking-wide` etc. from the `@theme` tokens in `app/globals.css`, arbitrary values only where no token fits (a one-off size), never for a colour, a shadow, a duration or a letter-spacing). When writing a new component, use Tailwind. Don't add an inline `style` object for anything Tailwind can express. A handful of components still keep one genuinely dynamic per-instance inline `style` (e.g. a computed progress-bar `width`, `FloatingActionButton`'s `bottom` offset, `FolderGrid`'s `gridTemplateColumns`) — Tailwind can't express a runtime-computed value as a static class, so these are deliberate, not leftovers.
- **Prefer a shared component over re-declaring the same style/behavior inline at each call site, once a pattern is genuinely established across the app.** `components/shared/button.tsx`'s `Button` is the reference example: before it existed, every "Save"/"Cancel"/"+ Add X" button in the app re-typed its own `style={{...}}` object for the same filled/invert-on-press or outlined/`ink-press` look (see the button-pattern inventory this replaced — filled primary, outlined secondary, outlined danger, a compact size). `Button` takes `variant` (`primary`/`secondary`/`danger`), `accent` (`ink`/`flame`/`teal`, primary only), `size` (`default`/`compact`), and passes through `disabled`/`onClick`/etc. — a leading icon is just a child rendered before the label text (`<Button><PlusIcon .../>Add hours</Button>`), not a separate prop, since the underlying markup already puts children in that order. It is deliberately **not** used for icon-only controls (a row's `✕` remove button, a modal's dismiss `✕`) — those stay bespoke, since `Button` always renders a visible text label. This doesn't override the general "don't add abstractions beyond what's needed" rule — a one-off control specific to a single page still stays inline — but when you notice yourself copying the same button (or similar repeated UI) styling into a third or fourth file, that's the signal to extract it into `components/shared/` rather than keep duplicating it, the same way `Eyebrow`/`Tag`/`Chip` already work.
- **Inline text links get an underline** — this is what distinguishes "this bold text is clickable" from plain emphasis (e.g. `components/circles/circle.page.tsx`'s website link, or the "Last edited by {name}" button in the same file). This applies specifically to bare text sitting inline in body content, not to nav chrome (top bar tabs, `BottomNav`) or anything already boxed/bordered as a button, pill, or card (e.g. the mailto pill in `member-profile.page.tsx`) — those already read as clickable from their shape and position, so underlining them too would be redundant.
- **The design tokens are the rules** (all in `app/globals.css`):
  - **Colour by job**, never a hex value: the role map at the top of the `@theme` block (neutrals ink, body, soft, ghost, faint, wash, paper; the one action blue; the meanings flame, leaf, danger, warning; attention for the badge; and a colour per kind). Running text is `text-body`.
  - **Spacing on a 4px grid**: padding, margins and gaps from 8px up use whole Tailwind steps (`3` = 12px, `4` = 16px…), never `3.5` or `2.75`; below 8px, 2px steps (`0.5`, `1.5`) are fine for nudging type and icons.
  - **Elevation in two levels**: `shadow-float` (hovers over the page: the floating button, menus, the top bar's circles), `shadow-overlay` (over everything: dialogs, toasts, the bottom nav). Anything on the page itself has none.
  - **Motion in three durations and two curves**: `--motion-press` (80ms), `--motion-small` (150ms), `--motion-screen` (250ms); `--ease-enter` for what arrives or moves, `--ease-exit` for what leaves (`duration-(--motion-screen) ease-(--ease-enter)` in a class, `var(…)` in CSS).
  - **Icons in three sizes**: `size-4` (16px) beside text and in small controls, `size-5` (20px) in a button or row of its own and the top bar, `size-6` (24px) in the bottom nav and the floating button; `size-8` only for display (a square's glyph, the name game's play). Nothing smaller than 16px; a small glyph that needs more weight gets a heavier stroke instead.
  - **Tight tracking by size**: `tracking-display` for a title (a masthead, Home's greeting), `tracking-heading` for a card's or the top bar's name, `tracking-snug` for a name in a list; `tracking-tight` is older and in a few places.
  - **Two kinds of small caps**: `tracking-eyebrow` (an `Eyebrow`: a section's heading) and `tracking-caps` (every other uppercase label: a button, a chip, a tag, a badge, a field's label). Information is never set in caps: an occupation, a time, a pronoun read in sentence case. The small date tile keeps its own.
- Prefer a theme token over a raw value or one-off arbitrary class whenever one already covers it (e.g. `text-flame` over `text-[#e1530b]`, `text-eyebrow` over `text-xs` when it's actually an eyebrow) — the whole point of porting the tokens was to stop repeating the same hex codes and sizes across files. If a new value is genuinely needed in more than one place, add it to the `@theme` block rather than hardcoding it at each call site.
- **`clsx` for conditional/combined class names** (e.g. `components/shared/tag.tsx`'s filled/unfilled state) rather than hand-built template-literal string concatenation — chosen over `classnames` for being the smaller of the two with an equivalent API. Don't reach for `tailwind-merge` alongside it unless a real class-conflict-resolution need shows up (e.g. a component needing to override a token class a caller passed in); it solves a different problem than `clsx` and isn't installed.
- Comments are rare and rationale-only (explaining *why*, e.g. the note above `CANCEL_WINDOW_MS`) — the existing file is a good model for this; don't add comments narrating *what* the code does.
- **TypeScript (`.ts`/`.tsx`), not plain JavaScript.** This is a reversal of an earlier decision, the same way the Tailwind migration above reversed the inline-styles-while-splitting-the-file call: plain JS was fine for a prototype with no types worth enforcing yet, but the codebase outgrew that once real domain shapes (`Event`, `Circle`, `Member`, `Role`, ...) were being passed through a dozen layers by hand. `tsconfig.json` runs with `strict: true` and `noUncheckedIndexedAccess: true` from the start, not staged in later — the codebase's existing defensive style (guards everywhere already) made that low-friction. `lib/types.ts` is the single source of truth for the domain model (`Member`, `Circle`, `CircleRole`, `CircleResource`, `Event`, `Role`, `EventKindKey`, `NotificationKind`, ...) — import shapes from there rather than re-declaring a structurally-equivalent inline type at each call site. `Event` is one flat interface with the fields that only some events have (`kind`, `hostCircleId`, `proposed`, `votes`, `roles`) optional, not a discriminated union on `kind` — every real call site already guards these defensively, and a true union would force exhaustive narrowing rework across every existing `e.kind === "meeting"` check for no real safety gain here. Where governance logic reads several of those fields together, `lib/governance.util.ts`'s `isMeeting`/`isCircleHosted` type guards give real narrowing without touching call sites that don't need it. One known TS sharp edge worth knowing before you hit it: a `let` reassigned inside a `.map()`/`.filter()` callback does not narrow correctly when read afterward in the outer scope (TS keeps the pre-callback flow type there), and separately, narrowing a property (`e.hostCircleId &&`) does not survive into a nested closure (an `onClick`, a `db.transaction` callback, etc.) — both need the value hoisted into its own `const` at the point where the narrowing is actually valid (see `setVote` in `lib/db/events.ts`, which copies `row.hostCircleId` into a `const` before the transaction callback that uses it) rather than a bare `!` slapped on where the error surfaces.
- **All source filenames are kebab-case** (`circle-card.tsx`, `app-state-provider.tsx`, `date-tile.tsx`), including files that export a React component. This applies to the filename only — the exported component/function identifiers inside stay normal JS/React naming (`export function EventPage`, `PascalCase` for components, `camelCase` for everything else), since JSX requires a capitalized identifier to treat something as a component.
- **`.tsx` for anything under `app/` or `components/`, `.ts` for `lib/`.** The split is by location, not by whether a given file happens to contain a JSX tag — everything that's part of the component tree is `.tsx`; plain data/logic modules are `.ts`. Imports never include the extension, so this is purely a naming convention, not something Next.js's resolver depends on.
- **A file's *role* is encoded as a dotted suffix before that extension, for the two roles common enough to be worth marking:** `.page.tsx` for a component that's the full top-level view for exactly one route (`circle.page.tsx` exports `CirclePage`, one of two views `app/(app)/circles/[id]/page.tsx` can render — see Circles above; also `manage-circle.page.tsx`, `event.page.tsx`, `edit-myself.page.tsx`, `home.page.tsx`, `circles-root.page.tsx` and `neighborhood.page.tsx` (the Circles browser's other views, rendered at `/circles` and `/circles/[id]` for a neighborhood respectively), `event-form.page.tsx`, `name-game.page.tsx`, `events-list.page.tsx`, `welcome.page.tsx`), and `.util.ts` for a `lib/` module whose entire export surface is pure helper functions (`governance.util.ts`, `roles.util.ts`, `format.util.ts`, `circles.util.ts`, `events.util.ts`, `members.util.ts`). The suffix replaces an existing `-page`/`-form`-type word in the base name rather than stacking on top of it (`manage-circle-page.tsx` → `manage-circle.page.tsx`, not `manage-circle-page.page.tsx`). Not everything under `components/` or `lib/` gets a role suffix — only these two well-defined categories do: reusable/chrome components, providers, and one-off pieces (`circle-card.tsx`, `stat-card.tsx`, `app-state-provider.tsx`) stay plain kebab-case, and so do `lib/` modules that aren't collections of *pure* helper functions — `hooks.ts` is React hooks, `data.ts` is seed data, `types.ts` is the domain-model type module, and `lib/db/*.ts` / `lib/auth.ts` / `lib/session.ts` all have side effects (a database connection, cookies), which is exactly what disqualifies them despite being "helper functions" in a loose sense. When a new file clearly fits one of the two roles, name it that way from the start; don't invent additional suffixes (`.hook.ts`, `.provider.tsx`, etc.) without deciding that expansion explicitly first.
