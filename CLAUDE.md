# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Convene is a prototype for a federated, neighborhood-scale coordination tool — members, organizations (co-ops/collectives, nested under each neighborhood's own standing Neighborhood Council), events, and a lightweight direct-democracy governance layer (Neighborhood Council meetings and a federation council), on top of a design system carried over from "The Commons Institute" (ink-on-white, Helvetica/Georgia, zero border-radius, hairline rules).

It's a Next.js (App Router, JavaScript) app with no real backend yet — `lib/data.js` is the entire seed dataset, read through a data-access layer (`lib/db/`) designed to be swapped for a real database later without touching call sites, and all runtime state lives in `components/providers/app-state-provider.jsx`, mounted in `app/(app)/layout.jsx`. Auth is mock (email + one-time code, no real provider), gating everything except the welcome page at `/`. The app was originally prototyped as a single ~3900-line file, then split into `lib/` and `components/`, then moved off a single-component view-state switch onto real routes; none of the earlier single-file structure exists anymore, so treat the current tree as the spec.

## Setup & commands

- `npm run dev` — local dev server
- `npm run build` — production build (also the fastest way to catch broken imports/syntax across the app)
- `npm run lint` — ESLint

There is no test runner yet — deliberately deferred until the app grows past prototype stage.

## Architecture

### Routing and shared app state
`/` is the unauthenticated welcome page (email + one-time-code login — see Authentication below); every other route lives under the `app/(app)/` route group (a URL-invisible folder — `app/(app)/home/page.jsx` still serves `/home`), which requires a session: `/home`, `/federation`, `/directory`, `/directory/[id]`, `/organizations/[id]`, `/organizations/[id]/manage`, `/events`, `/events/new`, `/events/[id]`, `/events/[id]/propose`, `/profile/edit`, `/game`. `/people` and `/organizations` (the old flat list routes) still exist as server-side `redirect("/directory")` routes for old links/bookmarks — see Organization hierarchy below. Routes can't share React state via props the way a single root component could — `components/providers/app-state-provider.jsx` holds everything that used to be `useState` in that root component (`events`, `orgs`, `councilProposals`, `rsvpState`, `voteState`, `profile`, and their mutators) and is mounted once in `app/(app)/layout.jsx`, seeded from props that layout fetches server-side via `lib/db/`; every route beneath it reads the state via `useAppState()`.

Mutators on `AppStateProvider` are pure state + toast now — they never navigate. Where the old single-view app followed a mutation with a view change (e.g. jump to the newly created event), that's the calling route's job, since only the route has the router; `createEvent` and `proposeEndorsingAssembly` return the created event so the caller can `router.push` its URL. Each mutator also calls the matching `lib/db/` write, alongside (not instead of) its own `setState` — see Data access layer below. `lib/hooks.js`'s `useAppNav()` centralizes the small set of "go somewhere" helpers (`openEvent`, `openOrg`, and a legacy-key `setView` for components still written against the old view-name API) so the URL shapes live in one place instead of being hand-typed across components. `openOrg` branches on whether the target org is a Neighborhood Council (`org.neighborhood` set) — see Organization hierarchy below.

Back/cancel buttons use whichever is actually correct for that button: `router.back()` where the point is literally "return to wherever I came from" (e.g. the organization page), or an explicit `router.push()` to a known parent route where the destination is fixed regardless of entry point (e.g. a cancelled event form always returns to `/events`). Real routing made some of these more correct than the original: opening an event from Home's dashboard now returns to Home instead of always dumping into the full Events list.

The member-profile modal is deliberately not a route — it's opened identically from a dozen different pages (directory, attendee lists, member lists, role slots) and looks the same regardless of source. `components/providers/profile-modal-provider.jsx` holds it, mounted once in `app/(app)/layout.jsx`, and closes itself whenever the pathname changes (adjusted during render, not a `useEffect` — see the comment in that file) so it can't linger over content after a browser back/forward that bypasses its own close button.

`/events/[id]/propose` is one route serving two governance flows — a confirmed meeting proposing a federation council, or a council getting an endorsing meeting proposed in the viewer's neighborhood. Which applies is fully determined by the event's own `kind`, so the mode isn't part of the URL.

### Data access layer
`lib/db/` (`members.js`, `orgs.js`, `events.js`) is the seam between the app and its data source, added specifically so a real backend can later replace the mock implementation without touching call sites: every function is `async` (`getMembers`, `getMemberById`, `getMemberByEmail`, `getOrgs`, `getOrgsByMember`, `updateOrg`, `getEvents`, `createEvent`, `updateEvent`, `getCouncilProposals`, `createCouncilProposal`, `updateCouncilProposal`, `updateMember`, ...) even though the current implementation is just an in-memory array. Each file keeps its own module-level mutable copy, shallow-cloned from `lib/data.js`'s exports at load — deliberately a separate copy, not the same object reference `lib/data.js` still exports (see the caveat below). These files stay plain kebab-case, not `.util.js` — they have side effects (mutable state), which is outside that suffix's definition (see Coding style).

`app/(app)/layout.jsx` is the one place a Server Component fetches through the DAL and hands the result to a Client Component as props: it calls `getEvents()`/`getOrgs()`/`getMemberById(currentUserId)` and passes them into `AppStateProvider` as `initialEvents`/`initialOrgs`/`initialProfile`, which seed its `useState` calls. `AppStateProvider`'s mutators (`toggleRsvp`, `saveOrg`, `createEvent`, etc.) call the matching `lib/db/` write fire-and-forget, alongside their existing optimistic `setState` — there's no rollback/error-handling yet, since the mock DAL can't actually fail; that's real work for whenever a real backend can.

**Known, deliberate gap:** not every read goes through the DAL. A number of components (`org.page.jsx`, `event.page.jsx`, `browse.page.jsx`'s route pages, `profile-modal.jsx`, and others) still call `memberById`/`orgById`/`avatarFor`/`hostInfo`/`ORGS_BY_MEMBER`/`MEMBERS` directly against `lib/data.js`'s original static arrays, not through `AppStateProvider` or `lib/db/`. This predates the DAL and is out of scope for now — migrate a call site to the DAL when you're already touching it for other work, the same incremental approach used for the Tailwind migration, rather than converting everything at once.

### Organization hierarchy and the unified Directory
Orgs nest: every org has a `parentId` (another org's id, or `null` for root-level) instead of the flat `level` string this used to be. Each neighborhood has its own **Neighborhood Council** org (`the-903-council`, `ona-council`, `college-hill-council`, all root-level) — its `neighborhood` field (unique to Council-type orgs) marks it as a place every resident is automatically a member of, no explicit roster needed. `lib/orgs.util.js`'s pure helpers are the seam everything else reads the hierarchy through: `orgChildren` (direct children), `orgMembers` (a Council's derived resident roster, or a normal org's literal `members` array — always call this instead of reading `.members` directly, since a Council's own array is unused/empty), `orgScope` (walks `parentId` up to the nearest Council — `null` means federation-wide, replacing the old `level` field everywhere), `orgAncestors` (root-to-leaf chain, for breadcrumbs), `orgDescendantIds` (whole subtree, for search). Nesting is general-purpose (any org could someday have children — e.g. a large workplace's internal committees), but only Neighborhood Councils are populated with children today (The 903's: Finance/Grounds/Community Council, Coalition for the Unhoused).

Browsing is one unified **Directory** (`components/directory/browse.page.jsx`'s `BrowsePage`) replacing the old separate People and Organizations pages: given an org (or none, for the true root), it shows that org's direct children as folders (orgs, which nest — reuses `OrgCard`) and its own direct members as files (people, which never nest — `components/directory/member-card.jsx`'s `MemberCard`), with breadcrumbs and a search that flattens the *current* org's whole subtree (not a global search — see `orgDescendantIds`). **Routing splits by org type**: a Neighborhood Council browses at `/directory/[id]` (its "page" *is* the folder view — no dedicated org page yet); every other org still gets its own page at `/organizations/[id]` (`org.page.jsx`'s `OrgPage`, which also gained a "Sub-organizations" section reusing `OrgCard`, for whenever a non-Council org has children). `useAppNav()`'s `openOrg` is what decides which route a given org goes to — always route through it rather than constructing either path by hand. Each route also redirects a mismatched id to the other route (e.g. `/organizations/the-903-council` bounces to `/directory/the-903-council`), so a stray link never 404s just for guessing wrong.

Folders split into two grids by `kind`, general (any org's folder view does this, not just Neighborhood Councils): a **Councils** grid (`kind === "Council"`) above the **Organizations** grid (everything else) — The 903's page shows Finance/Grounds/Community Council here. (The org being browsed doesn't show itself in its own Councils grid — that was tried and deliberately pulled for now, may come back later.) A Neighborhood Council also displays differently from a normal org wherever its name is shown as a title (`orgDisplayName()` in `lib/orgs.util.js`, used by `OrgCard` and `BrowsePage`'s breadcrumbs/title): its bare neighborhood name ("The 903") instead of its full org name ("The 903 Neighborhood Council"), no kind eyebrow, and no scope chip — it *is* the scope, so showing either would be redundant. Finance/Grounds/Community Council are Council-kind too but aren't neighborhood-rooted (no `.neighborhood`), so they keep the normal chip/kind/name treatment.

### Authentication
Mock, passwordless: the welcome page (`app/page.jsx`, outside the `(app)` group, no session required) collects an email, matches it against a seed member's `email` field via `getMemberByEmail`, and — since there's no real email provider — hands a generated one-time code straight back to the page instead of sending it, which shows it inline as an explicit "dev mode" hint. `lib/auth.js` holds the three Server Actions this drives (`requestLoginCode`, `verifyLoginCode`, `logout`; the whole file is `"use server"` since every export is one) — they set/clear a plain, unsigned `session` cookie holding the logged-in member's id and, matching this app's existing convention that mutators never navigate, return a plain result and let the calling Client Component `router.push()` on success rather than redirecting from inside the action. `lib/session.js`'s `getCurrentUserId()` reads that cookie; it's a separate file from `lib/auth.js` on purpose — mixing a plain `next/headers`-using helper into a Server Actions file broke importing those actions from the Client Component welcome page, since Next tried to bundle the whole module (including `next/headers`) for the client.

`proxy.js` at the project root (not `middleware.js` — Next 16 renamed the convention, and the exported function must be named `proxy`) is the primary route gate: no `session` cookie redirects to `/`, with `/` itself explicitly excluded in the function body to avoid a redirect loop. `app/(app)/layout.jsx` also checks `getCurrentUserId()` and redirects defensively — not because proxy is unreliable in the happy path, but because the Next.js docs warn that Server Actions are only gated by whatever route called them, so a future matcher change could silently lose coverage; the layout check is what a real backend's authorization would also need regardless.

This whole file is intentionally throwaway: the cookie isn't cryptographically signed, the pending-code store is an in-memory `Map` that won't survive a restart, and there's no real email delivery. The email + one-time-code shape was chosen because it maps closely onto Supabase Auth's `signInWithOtp`/`verifyOtp` (the most likely real provider — see Data access layer), so swapping it later should mean replacing this file's internals, not redesigning the login flow.

### Data model
Three flat arrays in `lib/data.js` — `MEMBERS`, `ORGS`, `EVENTS` — are the seed dataset (read through `lib/db/`, not directly, for anything that should survive a future backend swap — see Data access layer). `ORGS_BY_MEMBER` is a derived lookup built once at module load. `HOME_HOOD` fixes which neighborhood the whole UI is viewed as. `CURRENT_USER_ID` is what an unauthenticated fallback would default to, but in practice `currentUserId` is now a real, dynamic value resolved at login (see Authentication) and threaded through as a prop, not read as a constant, from `AppStateProvider` downward. Components treat `lib/data.js` as read-only and go through `AppStateProvider`'s state (`events`, `orgs`, `rsvpState`, `voteState`, `profile`, via `useAppState()`) for anything that changes at runtime.

### Governance is the trickiest business logic
Events are either ordinary or "governance" (`meeting` or `council`, see `EVENT_KINDS` in `lib/data.js` — `meeting` was `assembly` before Neighborhood Councils existed as real orgs, see Organization hierarchy above). A meeting is hosted by a Neighborhood Council org via `orgId` (not the old `scope` neighborhood-name string, which `council`-kind events still use for `"federation"`, so don't conflate the two fields) and confirms once resident votes reach a majority of that council's own derived membership — `lib/governance.util.js`'s `meetingThreshold(e)` computes this live (`Math.floor(orgMembers(org, MEMBERS).length / 2) + 1`; the exact fraction is still a placeholder pending a real decision, isolated to this one function on purpose). Councils are federation-wide and confirm once a majority of neighborhoods *endorse* them (each neighborhood endorses by passing its own meeting vote) — this flow (`councilProposals` state, `proposeCouncilDraft`/`ratifyCouncilProposal`/`proposeEndorsingAssembly` on `AppStateProvider`, gated by `FEDERATION_COUNCIL_ENABLED`) is deliberately **not** rebuilt against the Council-org model yet (deprioritized — the MVP targets a single neighborhood); its data shape was kept consistent with the rename so it won't silently break if the flag is ever enabled, but expect it to need real work before federation launches. `lib/governance.util.js` (`kindOf`, `isConfirmed`, `councilConfirmed`, `canVote`, `canReadDetails`, `neighborhoodMajority`, `meetingThreshold`, `isExclusive`, `isHostOrgMember`) encodes these rules as pure functions shared between the event list and detail views — extend that module rather than duplicating logic per component. Only a Neighborhood Council can host a meeting today; any org hosting one is explicit future work, not yet built. Note the org kind `"Council"` (Finance/Grounds/Community Council, and every Neighborhood Council) and the event kind `"council"` (federation council meetings) are unrelated fields on unrelated data types that happen to share a word — a known, accepted naming overlap, not a bug.

### RSVP/vote state is duplicated by design
`rsvpState`/`voteState` (`{ [eventId]: true }`, current user only) exist alongside each event's own `rsvps`/`votes` arrays and are updated together in lockstep (see `toggleRsvp`, `toggleVote` in `AppStateProvider`). This lets "am I going?" render without scanning arrays while keeping counts/rosters correct everywhere else. Keep both updates atomic if these handlers change.

### Role-slotted events and time-based cancellation
Some events define `roles` (shift lead, librarian, etc.) with `min`/`max` instead of a plain RSVP list. Whether the shift is cancelled is *derived from the clock*, not stored: `lib/roles.util.js`'s `shiftNeedsSlots` (neutral, more than an hour out) flips to `shiftCancelled` inside the one-hour cancellation window (`inCancelWindow`) if a required role is still unfilled, and to `shiftEnded` after the end time. Don't cache these values — they must be recomputed on render.

### Members-only ("exclusive") events
An event hosted by an org with `membersOnly: true` is invisible to anyone outside that org, not just un-RSVP-able — `AppStateProvider`'s `visibleEvents` filter (the single choke point every route reads events through, alongside the `FEDERATION_COUNCIL_ENABLED` feature-flag filter) drops it from the array entirely for a non-member viewer, so it's absent from every list/dashboard and its `/events/[id]` route 404s. `isExclusive` / `isHostOrgMember` in `lib/governance.util.js` compute this, independently of the governance rules above.

### Neighborhood-scoped organization visibility
An org is visible to a viewer only if its effective scope (`orgScope(org, orgsById)`, from `lib/orgs.util.js` — set via the Scope field on its manage page, which now picks a parent Council rather than a raw neighborhood string) is their own neighborhood, `null` (federation-wide, i.e. root-level with no Council ancestor), or they're already one of its `orgMembers()` — membership always wins over scope, specifically so reparenting an org can never lock its own members out of it (including the ability to change the scope back). `AppStateProvider`'s `visibleOrgs` filter (the same choke-point pattern as `visibleEvents`) drops a non-matching org from the array entirely, so it's absent from the directory and Home's "Local organizations"/"My organizations" cards, and its `/organizations/[id]` and `/organizations/[id]/manage` routes 404. This is a different axis from members-only events above: it's about the org's home neighborhood vs. the viewer's, not org membership vs. non-membership.

### Shared design tokens and components
The design system exists in two parallel representations that must be kept in sync by hand: `lib/theme.js` (JS constants — `INK`, `PAPER`, `SOFT`, `FAINT`, `FLAME`, `LEAF`, `TEAL`, `PLUM`, `sans`, `serif`, the `TYPE` scale) for components still using inline `style={{...}}`, and the `@theme` block in `app/globals.css` (Tailwind v4 CSS-first config) for components written with Tailwind utility classes. Both must list the exact same colors/fonts/sizes — see Coding style below for which one a given component should use. `components/shared/` holds the generic pieces reused across pages (`Eyebrow`, `PageHeader`, `TabbedPanel`, `SearchWithFilter`, `Tag`, `Chip`, `form-fields`); `components/events/` has the event-specific reusable pieces (`DateTile`, `VoteButton`, `RsvpButton`) — reuse these rather than re-implementing per page. `components/shared/index.jsx` is a barrel re-exporting everything in the folder, so `import { Button, Label } from "@/components/shared"` works alongside (not instead of) importing a single file directly (`@/components/shared/button`) — both are valid, existing call sites weren't migrated to the barrel.

Toasts go through a `ToastProvider`/`useToast()` context (`components/shared/toast.jsx`) mounted in the true root `app/layout.jsx` — outside and above `app/(app)/layout.jsx`'s `AppStateProvider`, on purpose: it's the one provider both the unauthenticated welcome page and the authenticated app need, so the welcome page's login form gets `useToast()` for free. Components fire toasts via the hook rather than managing their own transient UI state.

## Code organization

Files are grouped by domain, not by component type: `components/shared/`, `components/directory/`, `components/orgs/`, `components/events/`, `components/home/`, `components/profile/`, `components/game/` — one component per file, with the file's kebab-case name matching its PascalCase export (`event.page.jsx` exports `EventPage`; see Coding style below for the `.page.jsx` suffix). `components/providers/` holds the two app-wide context providers (`app-state-provider.jsx`, `profile-modal-provider.jsx`) — they're components (they render JSX), just not ones any single domain owns. `components/shared/app-shell.jsx` is the nav wrapper (`TopBar` + `BottomNav`) rendered once in `app/(app)/layout.jsx` around every authenticated route; the button-press interaction CSS it used to carry in an inline `<style>` tag now lives in `app/globals.css` instead, since the unauthenticated welcome page needs those same classes and sits outside the tree `AppShell` wraps. `lib/` holds everything that isn't a component: `theme.js` (design tokens), `data.js` (seed data + lookups), `governance.util.js` / `roles.util.js` / `format.util.js` (pure helper functions), `hooks.js` (`useIsMobile`, `useAppNav`), `feature-flags.js`, `auth.js` / `session.js` (mock auth — see Authentication), and the `lib/db/` subfolder (the data access layer — see that section) — these stay `.js` since they hold no JSX. When adding a new component, put it in the folder for the domain it belongs to; when adding cross-domain UI (used by 2+ domains), it belongs in `components/shared/`.

`app/` has three things at its root: `layout.jsx` (minimal — just `ToastProvider`), `page.jsx` (the unauthenticated welcome/login page), and the `(app)/` route group holding everything else plus its own `layout.jsx`. Within `(app)/`, each route mirrors the route list above one-to-one — each `page.jsx` is a thin client component that pulls data from `useAppState()`/`useProfileModal()` and wires navigation via `useAppNav()`/`useRouter()`, then hands everything to the actual UI component from `components/`. Keep that split: route pages own data-fetching-and-wiring, `components/` own rendering, so a component never has to know whether it's reached via routing or (hypothetically) something else. `proxy.js` sits at the project root, a sibling of `app/`, not inside it — that's a Next.js convention, not a choice.

## Coding style

- **Tailwind (v4) for styling, using the theme tokens — not inline `style={{...}}` objects, and not CSS Modules.** This is a reversal of an earlier decision: inline styles were deliberate while the app was a single 3900-line file being split apart (adding a build step then would have widened that migration's scope), but now that the split is done, Tailwind is in. Most existing components still use inline styles + `lib/theme.js` and haven't been migrated yet — that's expected, not a bug to "fix" as a drive-by. `components/shared/eyebrow.jsx` and `components/shared/tag.jsx` are the reference examples of the converted style (utility classes, `bg-ink`/`text-soft`/`font-sans`/`text-eyebrow`/`tracking-wide` etc. from the `@theme` tokens in `app/globals.css`, arbitrary-value or fractional-spacing classes like `px-2.75`/`tracking-[0.04em]` where a design value doesn't land on a named Tailwind step). When writing a new component, use Tailwind. **This is how the migration actually happens, element by element**: whenever you touch an existing element for some other reason (adding an icon, fixing a style, anything), convert that specific element to Tailwind classes and remove its `style` object as part of the edit, rather than adding to the inline style just because the rest of the file still is. Elements in the same file you didn't otherwise need to touch stay as they are — that's still not a drive-by fix, only what you actually edited is.
- **Prefer a shared component over re-declaring the same style/behavior inline at each call site, once a pattern is genuinely established across the app.** `components/shared/button.jsx`'s `Button` is the reference example: before it existed, every "Save"/"Cancel"/"+ Add X" button in the app re-typed its own `style={{...}}` object for the same filled/invert-on-press or outlined/`ink-press` look (see the button-pattern inventory this replaced — filled primary, outlined secondary, outlined danger, a compact size). `Button` takes `variant` (`primary`/`secondary`/`danger`), `accent` (`ink`/`flame`/`teal`, primary only), `size` (`default`/`compact`), and passes through `disabled`/`onClick`/etc. — a leading icon is just a child rendered before the label text (`<Button><PlusIcon .../>Add hours</Button>`), not a separate prop, since the underlying markup already puts children in that order. It is deliberately **not** used for icon-only controls (a row's `✕` remove button, a modal's dismiss `✕`) — those stay bespoke, since `Button` always renders a visible text label. This doesn't override the general "don't add abstractions beyond what's needed" rule — a one-off control specific to a single page still stays inline — but when you notice yourself copying the same button (or similar repeated UI) styling into a third or fourth file, that's the signal to extract it into `components/shared/` rather than keep duplicating it, the same way `Eyebrow`/`Tag`/`Chip` already work.
- **Inline text links get an underline** — this is what distinguishes "this bold text is clickable" from plain emphasis (e.g. `components/orgs/org.page.jsx`'s website link, or the "Last edited by {name}" button in the same file). This applies specifically to bare text sitting inline in body content, not to nav chrome (top bar tabs, the "Providence" brand mark, `BottomNav`) or anything already boxed/bordered as a button, pill, or card (e.g. the mailto pill in `profile-modal.jsx`) — those already read as clickable from their shape and position, so underlining them too would be redundant.
- Prefer a theme token over a raw value or one-off arbitrary class whenever one already covers it (e.g. `text-flame` over `text-[#e1530b]`, `text-eyebrow` over `text-xs` when it's actually an eyebrow) — the whole point of porting the tokens was to stop repeating the same hex codes and sizes across files. If a new value is genuinely needed in more than one place, add it to the `@theme` block (and to `lib/theme.js` if inline-style code still needs it too) rather than hardcoding it at each call site.
- **`clsx` for conditional/combined class names** (e.g. `components/shared/tag.jsx`'s filled/unfilled state) rather than hand-built template-literal string concatenation — chosen over `classnames` for being the smaller of the two with an equivalent API. Don't reach for `tailwind-merge` alongside it unless a real class-conflict-resolution need shows up (e.g. a component needing to override a token class a caller passed in); it solves a different problem than `clsx` and isn't installed.
- Comments are rare and rationale-only (explaining *why*, e.g. the note above `CANCEL_WINDOW_MS`) — the existing file is a good model for this; don't add comments narrating *what* the code does.
- Plain JavaScript, not TypeScript.
- **All source filenames are kebab-case** (`org-card.jsx`, `app-state-provider.jsx`, `form-fields.jsx`), including files that export a React component. This applies to the filename only — the exported component/function identifiers inside stay normal JS/React naming (`export function EventPage`, `PascalCase` for components, `camelCase` for everything else), since JSX requires a capitalized identifier to treat something as a component.
- **`.jsx` for anything under `app/` or `components/`, `.js` for `lib/`.** The split is by location, not by whether a given file happens to contain a JSX tag — everything that's part of the component tree is `.jsx`; plain data/logic modules are `.js`. Imports never include the extension, so this is purely a naming convention, not something Next.js's resolver depends on.
- **A file's *role* is encoded as a dotted suffix before that extension, for the two roles common enough to be worth marking:** `.page.jsx` for a component that's the full top-level view for exactly one route (`org.page.jsx` exports `OrgPage`, rendered by `app/organizations/[id]/page.jsx`; also `manage-org.page.jsx`, `event.page.jsx`, `edit-myself.page.jsx`, `home.page.jsx`, `browse.page.jsx` (the unified Directory, rendered at both `/directory` and `/directory/[id]`), `new-event-form.page.jsx`, `governance-proposal-form.page.jsx`, `name-game.page.jsx`, `events-list.page.jsx`, `federation-home.page.jsx`), and `.util.js` for a `lib/` module whose entire export surface is pure helper functions (`governance.util.js`, `roles.util.js`, `format.util.js`, `orgs.util.js`). The suffix replaces an existing `-page`/`-form`-type word in the base name rather than stacking on top of it (`manage-org-page.jsx` → `manage-org.page.jsx`, not `manage-org-page.page.jsx`). Not everything under `components/` or `lib/` gets a role suffix — only these two well-defined categories do: reusable/chrome components, providers, and one-off pieces (`org-card.jsx`, `stat-card.jsx`, `app-state-provider.jsx`) stay plain kebab-case, and so do `lib/` modules that aren't collections of *pure* helper functions — `hooks.js` is React hooks, `data.js` is seed data, `theme.js` is design tokens, `feature-flags.js` is a flag constant, and `lib/db/*.js` / `lib/auth.js` / `lib/session.js` all have side effects (mutable in-memory state, cookies), which is exactly what disqualifies them despite being "helper functions" in a loose sense. When a new file clearly fits one of the two roles, name it that way from the start; don't invent additional suffixes (`.hook.js`, `.provider.jsx`, etc.) without deciding that expansion explicitly first.
