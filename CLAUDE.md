# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Circles is a prototype for a federated, neighborhood-scale coordination tool — members, circles (the city, its neighborhoods, and the councils, collectives, and co-ops inside them — one universal, nestable concept), events, and a lightweight direct-democracy governance layer (any circle's meetings, approved by a majority of its members), on top of a design system carried over from "The Commons Institute" (ink-on-white, Helvetica/Georgia, zero border-radius, hairline rules).

It's a Next.js (App Router, TypeScript) app backed by a real, self-hosted Postgres database (via a data-access layer, `lib/db/`, using Drizzle ORM — see Data access layer) — `lib/data.ts` is now seed-script input rather than something any app code reads directly, and all runtime state lives in `components/providers/app-state-provider.tsx`, mounted in `app/(app)/layout.tsx`. Auth is real too (Better Auth's email-otp plugin, no password — see Authentication), gating everything except the welcome page at `/`; login codes are emailed through `lib/email/` (SMTP — see Email). The app was originally prototyped as a single ~3900-line file, then split into `lib/` and `components/`, then moved off a single-component view-state switch onto real routes; none of the earlier single-file structure exists anymore, so treat the current tree as the spec.

## Setup & commands

- `npm run dev` — local dev server
- `npm run build` — production build (also the fastest way to catch broken imports/syntax across the app)
- `npm run lint` — ESLint

There is no test runner yet — deliberately deferred until the app grows past prototype stage.

## Architecture

### Routing and shared app state
`/` is the unauthenticated welcome page (email + one-time-code login — see Authentication below); every other route lives under the `app/(app)/` route group (a URL-invisible folder — `app/(app)/home/page.tsx` still serves `/home`), which requires a session: `/home`, `/circles`, `/circles/[id]`, `/circles/[id]/manage`, `/events`, `/events/new`, `/events/[id]`, `/events/[id]/edit`, `/profile/edit`, `/game`. Every circle — neighborhood or not, however deep it sits in the tree — lives under `/circles/[id]`, keyed by its own stable id rather than its position in the hierarchy (see Circles below). Routes can't share React state via props the way a single root component could — `components/providers/app-state-provider.tsx` holds everything that used to be `useState` in that root component (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, and their mutators) and is mounted once in `app/(app)/layout.tsx`, seeded from props that layout fetches server-side via `lib/db/`; every route beneath it reads the state via `useAppState()`.

Mutators on `AppStateProvider` are pure state + toast now — they never navigate. Where the old single-view app followed a mutation with a view change (e.g. jump to the newly created event), that's the calling route's job, since only the route has the router; `createEvent` returns the created event so the caller can `router.push` its URL. Each mutator also calls the matching `lib/db/` write, alongside (not instead of) its own `setState` — see Data access layer below. Compute the value a mutator writes to the DAL synchronously from the state already in scope, never by reading a `let` that a `setState` updater assigned: React doesn't run a functional updater inline, so that value is still its initial one on the next line (this silently dropped every DB write from `toggleRsvp`/`toggleVote`/`toggleRoleSlot` once). `lib/hooks.ts`'s `useAppNav()` centralizes the small set of "go somewhere" helpers (`openEvent`, `openCircle`, and a legacy-key `setView` for components still written against the old view-name API) so the URL shapes live in one place instead of being hand-typed across components. `openCircle` always routes to `/circles/[id]` — which of two views renders there is decided inside that route by the circle's `type` (a neighborhood renders as a folder view), not by the URL — see Circles below.

**Back lives in the top bar, not on the page.** Like Flutter's automatic app-bar back button, `TopBar` (`components/shared/top-bar.tsx`) shows a ghost arrow button on every route except the three tab roots (`/home`, `/circles`, `/events`); pages don't render their own. Its title is always the current page's (`pageTitle`: the tab name at a root, a circle's or event's own name on its page, "New event", "Manage circle" and so on), on desktop as well as mobile, so the Circles root, neighborhood folders and the Events list carry no title of their own. The bar is laid out the same on every screen size: the title on the left and the page's action on the right. On desktop the tabs sit in the centre, centred on the bar itself, with the title stopping short of them; on mobile they're in `BottomNav` instead. The action is an icon button, the icon in a filled circle (`IconButtonCircle` in `top-bar.tsx`). A primary one, the page's main job such as Save, is blue (`--color-action`); a secondary one, such as Create Event, Manage or Edit, is ink. A link-style action comes from `TopBar`'s `pageAction()`: the Events list's Create Event (a +), a circle's Manage for its members (a cog), and an event's Edit for its organizer (a pencil). A page can instead put an action of its own there, one that runs its code rather than linking somewhere, with `useTopBarAction` (`components/providers/top-bar-action-provider.tsx`, mounted in `app/(app)/layout.tsx`), which takes precedence over `pageAction()`. Each form's Save is one: Manage circle's and Edit profile's checks stay disabled until something changes, and the event form's submit (Create, Propose or Save changes) until the event is valid, with a validation error, at the foot of the form, scrolled into view. The action lives only in the top bar, never also on the page: there are no masthead Manage or Edit buttons and no Save or Cancel buttons at the foot of a form, and leaving a form is the top bar's Back. Pages don't render their own floating action buttons either. It goes back through `useGoBack()` (`components/providers/back-handler-provider.tsx`). That calls `router.back()` when there's an in-app page to go back to, and otherwise (the page was opened directly, from a link or a reload) pushes one URL segment up (`parentRoute`), so it never leaves the app for whatever site linked here. A page that goes back once it's done uses the same hook rather than `router.back()`, as Manage circle does after Save or Cancel. A page that needs to intercept leaving — the event form, Manage circle and Edit myself, which ask before discarding unsaved changes — registers a handler with `useBackHandler` (`components/providers/back-handler-provider.tsx`, mounted in `app/(app)/layout.tsx`), passing `null` while there's nothing to lose so Back behaves normally. Where a form is left once its changes are discarded (its route's `onCancel`/`onBack`) is still each route's own choice: `router.back()` where the point is "return to wherever I came from", or an explicit `router.push()` to a known parent (a discarded new-event form always returns to `/events`).

The member-profile modal is deliberately not a route — it's opened identically from a dozen different pages (circles, attendee lists, member lists, role slots) and looks the same regardless of source. `components/providers/profile-modal-provider.tsx` holds it, mounted once in `app/(app)/layout.tsx`, and closes itself whenever the pathname changes (adjusted during render, not a `useEffect` — see the comment in that file) so it can't linger over content after a browser back/forward that bypasses its own close button.

### Data access layer
`lib/db/` (`members.ts`, `circles.ts`, `circle-roles.ts`, `events.ts`, `resources.ts`, `notifications.ts`) is the seam between the app and its data source — every function is `async` (`getMembers`, `getMemberById`, `getMemberByEmail`, `updateMember`, `getCircles`, `getCircleById`, `getCirclesByMember`, `updateCircle`, `getEventsForMember`, `createEvent`, `setRsvp`, ...) and is backed by a real, self-hosted Postgres database via Drizzle ORM. `lib/db/schema.ts` holds every Drizzle table definition (`members`/`member_photos`, `circles`/`circle_members`/`circle_roles`/`circle_resources`, `events`/`event_series`/`event_rsvps`/`event_votes`/`roles`/`role_members`, `event_notifications`, plus Better Auth's own `user`/`session`/`account`/`verification` tables — see Authentication) and `lib/db/client.ts` opens the one real connection (`drizzle(process.env.DATABASE_URL)`). **Wrapping rule:** no file outside `lib/db/` (and `lib/better-auth.ts`, for the auth tables) may import `drizzle-orm` or `lib/db/schema.ts` directly — every other file reaches data through the plain async functions these files export, so the app is never tightly coupled to Drizzle itself. The DAL reassembles join tables into the arrays the app types expect (`Circle.members`, `Event.rsvps`/`votes`/`roles`) and normalizes Postgres's `HH:MM:SS` `time` back to the app's `HH:MM`.

Local dev runs Postgres, plus Mailpit for outgoing email (see Email), via `docker-compose.yml` (`docker compose up -d`); schema changes go through `drizzle-kit` (`npm run db:generate` to diff `lib/db/schema.ts` into a new SQL file under `drizzle/`, `npm run db:migrate` to apply it). `scripts/seed.ts` (`npm run db:seed`) inserts `lib/data.ts`'s fixtures into a freshly-migrated database — `lib/data.ts` is seed-script input only; no app code imports it. The live beta is seeded separately: `npm run db:seed:beta` (`scripts/seed-beta.ts`) reads a **gitignored** `seed/beta.json` — one city, one neighborhood, one council inside it (a `circle`-type circle; the file's keys still say `council`), and the people (all residents; those marked `inCouncil` are on the council) — because it holds real names and emails and must never be committed; `seed/beta.example.json` documents the shape with fake data. It also creates each person's login (a Better Auth user for their email — sign-up is off, so this is the only way to sign in) and refuses to run against a database that already has members. Both scripts share `scripts/seed-core.ts`.

`app/(app)/layout.tsx` is the one place a Server Component fetches through the DAL and hands the result to a Client Component as props: it calls `getEventsForMember(currentUserId)`/`getCircles()`/`getMembers()` and passes them into `AppStateProvider` as `initialEvents`/`initialCircles`/`initialMembers` (plus the signed-in member as `initialProfile`), which seed its `useState` calls. Components read the live roster and circles through `lib/hooks.ts` (`useMembers()`, `useMemberById()`, `useCircles()`, `useCirclesById()`), never from static data. `AppStateProvider` is a Client Component, though, and a real Postgres driver can't run in a browser bundle — so its mutators don't call `lib/db/` directly. They call `lib/db/actions.ts` instead: thin `"use server"` wrappers around the same DAL writes. Event and resource writes are authorized against the session and return `{ ok, value | error }` (Next sanitizes thrown messages in production, so a `UserFacingError` — the base of `EventError`/`ResourceError`, in `lib/db/errors.ts` — is caught in `asMember` and returned as data); the event actions are intent-specific (`createEventAction`, `updateEventDetailsAction`, `setRsvpAction`, `setVoteAction` — for meetings and proposals alike — `toggleRoleSlotAction`), never a general patch, because the server computes `rsvps`/`votes`/`roles` from the session member rather than trusting client-supplied arrays. `updateCircleAction`/`updateMemberAction` are authorized too, each the narrowest rule that closes it: `updateCircleAction` requires the session member to belong to the circle (`updateCircle` in `lib/db/circles.ts`, throwing a `CircleError`; it also silently drops a `members`/`roles` key from the patch, since neither is editable through this generic path — `roles` has its own action, and there's no membership-editing UI yet) — `/circles/[id]/manage` itself 404s for a non-member, the same way `/events/[id]/edit` 404s for a non-organizer, so the button that's already hidden for them isn't reachable by URL either. `updateMemberAction` takes no id from the client at all — it always writes the session member's own row, so there's no id to check. Both stay fire-and-forget (`.then((r) => { if (!r.ok) console.error(r.error); })`, no rollback) — retry/rollback handling for these two is still future work, but a refusal is no longer silent. The event mutators are optimistic like the rest, but reconcile through `syncEvent` in `AppStateProvider`: they adopt the server's event on success and roll back with an error toast on refusal; `createEvent`/`updateEventDetails` instead await the server and return a result so the form can show a refusal inline.

### Circles and the Circles browser
Everything that scopes something is a **circle**. The city ("Providence") is the root circle; neighborhoods, councils, collectives, and co-ops are circles inside it, and circles nest. Every circle has a `parentId` (the root's is `null` — exactly one row, enforced by a unique partial index) and a `type`: `neighborhood | circle | collective | cooperative | other`. A council (the Finance Council, a beta neighborhood's council) is a plain `circle`: there used to be a `council` type, and migration `0015` renamed that enum value to `circle`, converting every existing council. Only `neighborhood` has behavior (a member's *home* circle; see below); the rest are display/filter labels (`CIRCLE_TYPE_LABEL` in `lib/circles.util.ts`). Membership is always explicit — a `circle_members` row — for every type, neighborhoods included; there are no derived rosters. `circle_members` carries its circle's `type` through a composite FK to `circles(id, type)`, which lets a partial unique index limit each member to **one neighborhood circle** (their `Member.homeCircleId`) with no trigger. Membership in a sub-circle is independent of its parent.

`lib/circles.util.ts`'s pure helpers are the seam everything else reads the tree through: `indexCircles` (id → circle lookup, `CirclesById`), `isCircleMember`, `circleChildren`, `circleNeighborhood` (the circle itself if it's a neighborhood, else its nearest neighborhood ancestor — `null` means citywide; used for the place chip and "local to my neighborhood" checks), `circleDescendantIds` (whole subtree, for search), `circlesForMember`, `sharesCircleWith` (gates avatar photos), and the event-audience trio `isCircleAudience`/`circlesForAudience`/`audienceLabel` (see Events belong to a circle below) — `isCircleMember` stays *explicit* membership on purpose, so everyone isn't implicitly in the root for rosters, resources or `sharesCircleWith`. Circles are **public**: any signed-in member can see any circle's page and roster (only an event's visibility is restricted — see Events belong to a circle below). A member may belong to no neighborhood (`homeCircleId` is nullable), so the UI tolerates that.

Browsing is one **Circles** browser at `/circles`, split across views since the city root and a neighborhood folder show meaningfully different things: `components/circles/circles-root.page.tsx`'s `CirclesRootPage` (`/circles` with no id) shows every circle directly under the root — neighborhoods and citywide groups — as folders, with no people grid; `components/circles/neighborhood.page.tsx`'s `NeighborhoodPage` (`/circles/[id]` for a `neighborhood`-type circle) shows its direct children as folders (`CircleCard`) and its members as files (`components/circles/member-card.tsx`'s `MemberCard`) and a search that flattens its whole subtree; every other circle renders `circle.page.tsx`'s `CirclePage` (which also has a "Sub-circles" section), with its manage form one level deeper at `/circles/[id]/manage` (`manage-circle.page.tsx`'s `ManageCirclePage`). Both browse views share `components/shared/folder-grid.tsx`'s `FolderGrid` (also reused by Home's "My circles" speed dial). Keying by the circle's own stable id means reparenting one (its Parent Circle field on the manage page — neighborhoods or the city root are the offered parents for now) never changes its URL. `useAppNav()`'s `openCircle` constructs the URL — always route through it rather than hand-typing `/circles/${id}`. Folders split into a **Circles** grid (`type === "circle"`) above an **Organizations** grid (collectives, cooperatives and everything else) inside a neighborhood, and the Type filter's options are Circles, Organizations and People. Both `NeighborhoodPage` and `CirclePage` open with a **Part of** grid holding one card, the circle's parent (`components/circles/parent-circle.tsx`'s `ParentCircle`), so where a circle sits in the tree reads the same way from either view; the neighborhood view hides it while searching or filtering. The city root has no `/circles/[id]` page of its own — `openCircle` sends it to `/circles`.

`CircleCard`'s type eyebrow is controlled separately from its neighborhood chip via `showKindEyebrow` (default: on for everything but a neighborhood), and its neighborhood chip via `showNeighborhoodChip` (default on): both hide on every card while browsing *inside* a folder (`NeighborhoodPage`, `CirclePage`'s Sub-circles), since every card there structurally shares the folder's own neighborhood; they show at the Circles root and in Home's speed dial, which are flat lists that mix neighborhoods. `MemberCard`'s neighborhood chip follows the same `showNeighborhoodChip` reasoning. The top bar shows a small teal home icon next to the title when the page is the viewer's own home neighborhood (`/circles/${profile.homeCircleId}`).

### Circle roles
Members can hold **roles** inside a circle — Secretary, Leader, Facilitator, or any the circle adds — in every circle *except* a neighborhood or the city root (`circleHasRoles` in `lib/circle-roles.util.ts`, the module that holds every rule below as pure functions). They're optional throughout. The three **built-in** roles (`BUILTIN_CIRCLE_ROLES`) are always listed for an eligible circle, empty until someone is chosen, and can be assigned and cleared but never removed or renamed; a circle may add its own (up to 20, names up to 40 characters, unique case-insensitively). A role has **at most one holder, and a member can hold several roles** — one row per role, one member picker each. Circles are public, so `Circle.roles` (every built-in first, then the circle's own, each with its `memberId` or null) travels with the circle to every signed-in member, and the roles show on the circle page for anyone.

**Where they show:** on a member's card in that circle's Members grid, as an outlined badge (one per role, in the circle's own order) under their occupation. The card always shows their occupation (`Member.role`) and never their neighborhood — everyone in the grid belongs to this circle, so the chip would be redundant (the same reasoning as `MemberCard`'s `showNeighborhoodChip`); a member with no role simply has no badge. Nowhere else — a role belongs to one circle, so the profile modal, the neighborhood folder view and event pages don't show them.

**Managing them:** the **Manage circle** page (`manage-circle.page.tsx`) has a Roles table, one row per role with a member picker over that circle's members, plus "Add role" for the circle's own (which can be renamed or removed). It's shown only to members of the circle, and saved by the same Save button as the rest of the form — but through its own action: `saveCircleRolesAction` → `setCircleRoles` in `lib/db/circle-roles.ts`, which acts as the session member, requires them to belong to the circle, validates (`validateCircleRoles`, shared with the form for instant feedback), and *replaces* the circle's rows as a whole, returning the list as saved (`AppStateProvider.saveCircleRoles` adopts it; await-then-update, no optimistic write). The client only sends each role's name and holder, in order: whether a role is built-in is decided by its name on the server, a built-in left out is just kept empty, and a holder must be a member of the circle. `updateCircle` (still unauthenticated) explicitly ignores a `roles` key so this can't be bypassed, and a holder who's no longer a member of the circle reads as unassigned. Saving roles alone doesn't touch "last edited by". The demo Finance Council has Priya as Secretary, Felix as Leader and Mira as Facilitator; the beta seed takes an optional `councilRoles` list per person.

### Circle resources
A circle can attach **resources** — links (a shared drive, a doc), each shown with the icon of the kind the person adding it picks: a folder (yellow), a file (blue), a video (purple) or an announcement (red, a megaphone) — that only that circle's **members** can see. They render on `CirclePage`'s Bulletin tab (`components/circles/bulletin-section.tsx`), the first of its two tabs and the one a member lands on, before Wiki (About, events, sub-circles, members). The tabs only appear for a member; a non-member sees only the wiki, with no hint a Bulletin exists. They apply to circles that have a detail page, so **not** neighborhoods (whose folder view has no such section, and the server refuses to add one). Adding an item is a ghost + (like the top bar's Back) at the right end of the tab row itself, on the labels' line, shown only while the Bulletin tab is active — `SimpleTabs`' `actions` slot — so `CirclePage` owns whether the add dialog is open and passes it to `BulletinSection` (`adding`/`onAdd`/`onAddingDone`). An empty board also offers it as a dashed blank card, with a line on what to post; once anything is pinned only the + remains. The bulletin shows them as a board of cards (`BulletinCard` in `bulletin-section.tsx`), as many columns as fit: each card is ruled along its top in its kind's color, a link card is a link all over (its title's link stretched across it, inverting while pressed), and an announcement spans more of the board with its whole message. Any member of the circle can add, edit, or remove one, each saving immediately in its own modal rather than as part of the Manage form. A card's only control is its edit pencil; removing lives in the edit dialog, behind a confirmation. A control inside a pressable card is marked `data-press-ignore`, so pressing it doesn't press the card (see `PressFeedback`). A resource is `{ title, icon: "folder" | "file" | "video" | "announcement", url?, message? }`: a folder, file or video is a link (`url`), and an announcement is a message typed out for members (`message`) with no link, shown in full in the list rather than opened, and signed with who posted it and the date ("— Name on 2/24/2026"). The poster is `created_by`, set by `createResource` from the session and never changed by an edit; items from before it was recorded (or whose poster was deleted) have none and show just the date. Each has exactly one of the two, which the form (it asks what you're adding first, then for a link or a message), `validateResourceInput`, `lib/db/resources.ts` (which saves only the field the kind uses and clears the other) and the table's own `circle_resources_link_or_message` check all hold to, shown newest first (editing one doesn't move it); links must be `http(s)` and open in a new tab (`lib/resources.util.ts`'s `validateResourceInput` is shared by the form for instant feedback and by the server as the real check).

Because circles themselves are public — the whole `circles` array is sent to every signed-in member — resources are deliberately **not** a field on `Circle`: they live in their own table and their own AppState slice, and the privacy boundary is enforced on the server, not in the UI. `lib/db/resources.ts` is the only place it lives: `getResourcesForMember(memberId)` returns only resources of circles that member belongs to (`app/(app)/layout.tsx` calls it with the session's member, so a non-member's browser never receives a circle's resources), and every write there re-checks membership and re-validates input, throwing a `ResourceError`. It takes the member id as an argument and never touches the session itself, so it can be exercised directly; `lib/db/actions.ts`'s `createResourceAction`/`updateResourceAction`/`deleteResourceAction` supply that id from `getCurrentUserId()` (never a client-supplied one) and return `{ ok, value | error }` result objects rather than throwing, since Next sanitizes a thrown error's message in production. Resources were the app's first server-side authorization; the event actions and `updateCircleAction`/`updateMemberAction` (see above) now all check the caller too. Unlike every other mutator, `AppStateProvider`'s `addResource`/`updateResource`/`removeResource` are **await-then-update**, not optimistic: the server can refuse and generates the id, so state changes only after it accepts. New circle types or "wiki"-style pages that want resources should render `BulletinSection` the same way (members only) rather than reading `resources` for non-members.

### Profile photos
A member can **replace** their photo on Edit myself (`components/profile/photo-picker.tsx`) but never remove it — no UI, action or DAL function deletes one. The browser crops it to a square and shrinks it to a 512px JPEG before upload. Save uploads it first, waiting for the result (`AppStateProvider.savePhoto` → `updateMemberPhotoAction` → `setMemberPhoto`, which checks the file's actual bytes are JPEG/PNG/WebP and that it's under 1 MB), so a refused photo keeps the form open. Photos sit in Postgres (`member_photos`, bytea) in their own table, so `getMembers` reads only the upload time (`Member.photoVersion`), never the image data. `avatarFor` turns that into `/api/members/[id]/photo?v=…` and falls back to the pravatar placeholder until someone uploads one. That route serves the photo only to the member or to someone sharing a circle with them (`getMemberPhoto`), which is the same rule `Avatar` applies in the UI, so it can't be bypassed by URL. It's cached `private, immutable`, since each new upload gets a new URL.

### Installable app (PWA)
Circles can be installed from the browser as a standalone app. `app/manifest.ts` is the manifest. Its `start_url` is `/home`, so someone not signed in lands on the welcome page. `app/layout.tsx`'s `viewport` and `appleWebApp` cover iOS, which still reads its own meta tags rather than the manifest. Every icon (`public/icons/`, `app/apple-icon.png`, `app/icon.svg`) is generated from one SVG mark by `npm run icons` (`scripts/generate-icons.tsx`) and committed, so change the mark there, not the PNGs. `proxy.ts`'s matcher skips the manifest and icons, because browsers fetch them without cookies. Because of `viewportFit: "cover"`, the page draws under the home indicator and a landscape notch, so anything pinned to an edge pads itself with `env(safe-area-inset-*)`: `AppShell`, `TopBar`, `BottomNav`, toasts, and `FloatingActionButton`, which adds the inset to its `bottom` itself. A new fixed or sticky element needs the same, and full-height layouts use `min-h-dvh`, not `min-h-screen`. There's no service worker yet. Offline support and push notifications would come with one. iOS's swipe-from-the-edge Back is turned off in the installed app (`useBlockEdgeSwipe` in `AppShell`), because it slides the whole screen, bars included. Bringing it back properly would need a gesture of our own that moves only the page.

Everything in `AppStateProvider` is loaded once, when the `(app)` layout renders, and pages render from it without fetching, so `refresh` in `AppStateProvider` reloads it all through `loadAppStateAction`. That happens on every return to the app, every 60 seconds while it's on screen, and when the connection comes back, with refreshes at least 15 seconds apart. So what someone else did shows up within about a minute, and at once on coming back. Coming back after at least a minute away also checks first whether the server has been deployed since this copy loaded: `lib/app-version.ts` compares the commit built into the browser code (`NEXT_PUBLIC_APP_VERSION`, set by `next.config.mjs`) with `/api/version`, and on a mismatch reloads the page, because the old copy's Server Actions no longer exist on the new server. It's only checked then, not on the timer, because a reload would throw away a form someone is partway through. Next's `deploymentId` is no help here, since nothing on a self-hosted server reads it. That's the same `getAppStateForMember` (`lib/db/app-state.ts`) the `(app)` layout seeds from, so keep the two using it. A refresh that starts within 10 seconds of a change made in this session is dropped, in case it read the database before that change landed. That's what the `tracked` wrapper around every mutator records, so a new mutator needs wrapping too.

### Authentication
Real auth now — Better Auth's email-otp plugin, still passwordless: the welcome page (`app/page.tsx`, outside the `(app)` group, no session required) collects an email and a one-time code. Its "Demo accounts" button lists members' emails, fetched by that server component (the page sits outside `AppStateProvider`) and dropped entirely in a production build so real addresses never ship to an unauthenticated visitor. `lib/better-auth.ts` is the only file that imports `better-auth` itself (matching the DAL's wrapping rule above) — it builds the `betterAuth({...})` instance with the Drizzle adapter (pointed at `lib/db/schema.ts`'s `user`/`session`/`account`/`verification` tables), `emailAndPassword: { enabled: false }` (this app has never had a password), and the `emailOTP` plugin configured with `disableSignUp: true` — a member without a matching seeded email should get the same "we don't recognize that email yet" rejection the old mock gave, not a new account. Better Auth's own `sendVerificationOTP` hook is deliberately a no-op, because Better Auth runs it as a background task and swallows its errors (a failed send would look like success): `requestLoginCode()` (`lib/auth.ts`) creates the code, reads it back out via `auth.api.getVerificationOTP()` (a Better Auth endpoint marked server-only — never exposed over HTTP), and emails it itself, so a failed send is reported to the person. **The code is returned to the browser only when `NODE_ENV !== "production"`** (the welcome page's inline "dev mode" hint) — in production the email is the only proof of owning the address, so leaking it would let anyone sign in as any member. `requestLoginCode()` also allows one code per address per minute (an in-memory cooldown, per server process — move it to the database if this ever runs on more than one instance), since the address is a member's real inbox; a failed send doesn't start it. Wrong-code attempts are limited by Better Auth's own default (3 per code).

`lib/auth.ts` still holds the three Server Actions the welcome page calls (`requestLoginCode`, `verifyLoginCode`, `logout` — same names/signatures as the mock version, so no call site changed), now calling `auth.api.sendVerificationOTP`/`getVerificationOTP`/`signInEmailOTP`/`signOut` instead of an in-memory pending-code `Map` and a plain cookie. Session cookies are Better Auth's own (`better-auth.session_token`), written via the `nextCookies()` plugin (must be last in the plugins array) — it forwards `Set-Cookie` headers from an `auth.api.*` call made inside a Server Action through `next/headers`'s `cookies()` automatically, which is what lets `lib/auth.ts` call `auth.api.*` directly with no client-side `authClient` and no mounted catch-all route handler. `lib/session.ts`'s `getCurrentUserId()` calls `auth.api.getSession()`, then looks the session's user back up by email via `getMemberByEmail()` to get this app's own `Member.id` — Better Auth's own user id is deliberately not linked to a member by foreign key (see `lib/db/schema.ts`'s comment on the `user` table); email is the one field both systems already agree on. `getCurrentUserId()` stays a separate file from `lib/auth.ts` on purpose — mixing a plain `next/headers`-using helper into a Server Actions file broke importing those actions from the Client Component welcome page, since Next tried to bundle the whole module for the client.

`proxy.ts` at the project root (not `middleware.ts` — Next 16 renamed the convention, and the exported function must be named `proxy`) is the primary route gate, and can't hold a real DB connection itself (middleware runs on the Edge runtime, incompatible with Drizzle's Node-only Postgres driver) — so it uses `better-auth/cookies`' `getSessionCookie()`, a presence-only check (decodes the cookie, doesn't hit the DB) that's safe there. `/` is explicitly excluded in the function body to avoid a redirect loop. `app/(app)/layout.tsx` calls `getCurrentUserId()` (a real, DB-validated check) and redirects defensively on top of proxy's cheap one — same division of labor the mock auth already had, not new.

The email + one-time-code shape maps closely onto how Better Auth's own `email-otp` plugin works, which is exactly why swapping to it didn't require redesigning the login flow — `requestLoginCode`/`verifyLoginCode`/`logout`'s signatures never changed.

### Email
`lib/email/index.ts` is the only file that imports `nodemailer` (the same wrapping rule as the DAL and Better Auth): everything sends through `sendEmail({ to, subject, text, html? })`. It speaks plain SMTP, so any provider (Postmark, Resend, SES, ...) or a self-hosted server is a change of `SMTP_URL`, not of code — prefer an SMTP relay over self-hosting the outbound server, since deliverability (SPF/DKIM/DMARC, IP reputation) is the hard part, not the protocol. Config is `SMTP_URL` (e.g. `smtps://user:password@host:465`) and `EMAIL_FROM` (an address on a domain the relay is set up to send as); in development `.env.example` points at **Mailpit**, a mail catcher in `docker-compose.yml` that shows every message at http://localhost:8025 and delivers none. With them unset, development just logs the message, and production throws instead of silently dropping a login code. `lib/email/templates.util.ts` holds the messages as pure functions (`loginCodeEmail(code)`), plain text first with matching inline-styled HTML. Emails so far: login codes, and new-event notifications (see Event notifications below). Digests are planned and will reuse `sendEmail` and the same queue. Anything member-typed goes through the template's `esc()` before it reaches HTML.

### Event notifications
Members are told about an event when it's created, when a proposal is approved, and when a meeting is approved (reaches its vote threshold). Two things vary independently, and the queue records both (`event_notifications.kind` and `.digest`):

**What happened** (`kind`), and who's told, in `lib/db/notifications.ts`:
- **`new`** — an event or meeting hosted by a person: the members of the circle it's shown to (`circleId`). A meeting's email says who *proposed* it and how many votes it needs (voting is also the RSVP), like the in-app banner.
- **`proposed`** — a circle-hosted proposal: the members of the **host** circle, the only ones who can see and vote on it. The circle it will eventually be shown to hears nothing yet.
- **`approved`** — something was approved, and its circle is told. Two ways to get here, which can't both apply to one event: **a circle-hosted proposal** reaches a majority of its host circle — **everyone in the event's circle** (for the city root, every member) is told, announced as an approved event (green rule; "Hosted by" the host circle, "Proposed by" the organizer), queued in the same transaction as the approving vote (`enqueueProposalApprovalNotifications`, from `setVote`), and also when a circle-hosted event is approved the moment it's created (a one-member host circle), with anyone whose *proposal* notice hadn't gone out yet dropped, since it's decided; or **a meeting** reaches its vote threshold — every member of its circle is told. A meeting's approval is recomputed from its live votes, not latched, so it's announced by the one vote that lands *exactly* on the majority (`enqueueMeetingApprovalNotifications`; `setVote` locks the meeting's row so concurrent votes can't each miss it), and the one-row-per-member-and-kind rule means a member is never told twice if votes are withdrawn and it's approved again. Not sent for a meeting that's already over.
- **`cancelled`** — the organizer cancelled an event others were going to (see Cancelling an event under Events belong to a circle). Everyone going, meaning its RSVPs (a meeting's voters among them) and slot holders, is told, always by an email of its own straight away (`enqueueCancellationNotifications`, in the cancelling transaction). Anything not yet sent about the event is withdrawn first (`withdrawEventNotifications`), so no one hears "new event" after "cancelled".

**How it's delivered** (`digest`) depends on the size of the circle being told (`queueFor`): a circle with **no sub-circles** gets an email of its own, right away; one **with sub-circles** — a neighborhood, the city — gets a line in its members' **daily digest** instead, since an email per event would be too much for a big audience. This applies to `new`, `proposed`, and a *meeting's* `approved`. A circle-hosted event's `approved` is the exception: it's always its own email (`immediate`), because it's what opens the event to that audience at all.

In every case the person whose own action caused it (the creator; the member whose vote tipped an approval) is skipped, as is anyone without an email address, and nothing goes out for an event already in the past. Edits don't notify, and there are no per-member preferences or unsubscribe yet, which the beta will want before it emails real people at any volume.

**The daily digest.** `lib/notify.ts`'s `deliverDigests` sends one email per member listing what's been queued for them since the last send, grouped by the circle they belong to (a proposal by its host circle) and soonest first: new events and meetings, proposals to vote on (orange "Proposal · vote to approve"), and approved meetings (green). A meeting that was proposed and then approved since the last digest is listed once, as approved. The heading says "N new events" while that's all it is, and "N updates" once it mixes in the rest. It goes out once a day at `DIGEST_HOUR` (0–23, default 8, in the server's local time — set `TZ` on a server that isn't in the community's timezone): rows are *due* once queued at or before the most recent send time, so something that happened after this morning's send waits for tomorrow's, and there's no "did today's run happen" record — due rows are marked sent as they go, so the next poll finds none, and a server that was down at send time simply sends when it comes back. Events already over by then are left out, and a digest with nothing left to say isn't sent. One caveat: the digest claims each member's rows together, so two servers draining at once could split a member's rows across two emails; a single instance can't.

It's a Postgres-backed queue: `event_notifications` has one row per (event, member, kind) — a member can be owed a proposal email and later an approval email for the same event — inserted **in the same transaction as the change that earns it** (`insertEvent(event, { notifyMembers: true })`, which only `createEvent` passes — seeding never emails anyone — and `setVote`'s approval), so an event is never created without its emails queued or the reverse. `lib/notify.ts`'s `deliverEventNotifications()` drains it: `createEventAction` and an approving `setVoteAction` schedule it with Next's `after()` so it runs right after the response is sent (members hear about it within a second or two), and `instrumentation.ts` starts a 15-second poller at server boot — which also drives the digest — as the safety net for failures, leftovers from a restart, and other server instances. The database is what prevents double sends: rows are claimed with `FOR UPDATE SKIP LOCKED` and a row can't be claimed again until 5 minutes after its last attempt (which is also the retry backoff), up to 5 attempts, with the last error kept on the row. Each email is rendered at send time from the event's current data, so a proposal approved in the seconds before its email goes out (and not already dropped) is sent as an ordinary event rather than as a request for votes. The poller is started once at boot by `instrumentation.ts` and **doesn't hot-reload**: restart `npm run dev` after changing notification code, or the running server keeps sending with the old one. `lib/db/notifications.ts` decides *who* and never touches SMTP; `lib/notify.ts` sends and never decides who.

### Data model
Three concepts, all in `lib/types.ts`: `Member`, `Circle`, and `Event`. `lib/data.ts`'s `MEMBERS`/`CIRCLES`/`EVENTS` are the seed dataset only (read through `lib/db/` at runtime). Every event belongs to exactly one circle (`circleId`) and always has an `organizerId` — the member who created it and the only person who can edit it (`isEventOrganizer`). `circleId` is who the event is shown to (and who would be notified of it); it is *not* the host. An event is hosted either by its organizer or, when `hostCircleId` is set, by a circle — which need not be the one it's shown to (the Finance Council can host an event shown to The 903). A circle-hosted event starts as a proposal (`proposed`) — see Events belong to a circle below. `currentUserId` is a real, dynamic value resolved at login (see Authentication) and threaded through as a prop from `AppStateProvider` downward. Components go through `AppStateProvider`'s state (`events`, `circles`, `members`, `rsvpState`, `voteState`, `profile`, via `useAppState()` or the `lib/hooks.ts` wrappers) for everything, static or not.

### Governance is the trickiest business logic
Two things put an event to a vote, and in both a circle's own members are the voters: a **meeting** (`kind: "meeting"`, see `EVENT_KINDS` in `lib/governance.util.ts`) and a **circle-hosted proposal** (see Events belong to a circle below). Any circle can hold a meeting: it's an event whose circle is the one being asked to decide, proposed by a member, and approved once its votes reach a majority of that circle's own members — `voteThreshold(e, circlesById)` computes this live (`majority(members.length)`, i.e. `Math.floor(n / 2) + 1`, shared with the server's approval check; the exact fraction is still a placeholder pending a real decision, isolated to this one function on purpose). Anyone who can see a meeting is by construction in its circle's audience, so there's no separate eligibility gating on voting or the agenda. A meeting can't be held in the root circle (its roster is implicit, so there's no majority to compute), carry signup slots, or be circle-hosted (its circle *is* the voter). **Wording:** "approve" is the one word for both meetings and circle-hosted events, in what people read ("Vote to Approve", "N more to approve", the "Approved" status and filter) and in the code (`isApproved`, the `approved` notification kind) — don't reintroduce "confirm" for either. (The generic `ConfirmModal` is unrelated: it's a confirmation dialog.) A meeting's approval is recomputed from its live votes; a proposal's approval is **latched** by the server (`events.approved_at`) and stays even if votes are later withdrawn. `lib/governance.util.ts` (`kindOf`, `isApproved`, `voteCount`, `voteThreshold`, `majority`, `votingCircleName`, `votingMemberNoun`, `isEventOrganizer`, `isMeeting`, `isCircleHosted`, `isProposal`, `isVoting` — a vote is what the event is waiting on right now, so it gets the orange row/banner — `isGoverned` — it has been through a vote at all, for the Status filter — and `eventTypeLabel`) encodes these rules as pure functions shared between the event list and detail views — extend that module rather than duplicating logic per component. They take the live `circlesById` lookup (`useCirclesById()`) as an explicit argument rather than reading static data, so they always reflect the current circle rosters. A federation-wide council flow (event kind `council`, proposals, ratification, neighborhood endorsements) existed and was removed as unused; it would return as a meeting hosted by the root circle with its child circles' endorsements.


### RSVP/vote state is duplicated by design
`rsvpState`/`voteState` (`{ [eventId]: true }`, current user only) exist alongside each event's own `rsvps`/`votes` arrays and are updated together in lockstep (see `toggleRsvp`, `toggleVote` in `AppStateProvider`). This lets "am I going?" render without scanning arrays while keeping counts/rosters correct everywhere else. Keep both updates atomic if these handlers change.

### Repeating events
When creating an event (circle-hosted or not — **not a meeting**, for now: `validateEventDraft` refuses one, and the form hides "Repeats" on the Meeting tab), the form's "Repeats" can make it **weekly** or **monthly**, with an optional last date ("Until"). The pattern is read from the first date (`lib/recurrence.util.ts`, pure). Weekly repeats that weekday. Monthly repeats its place in the month ("the 2nd Tuesday"), not the day number; a first date on the 29th–31st means "the last" such weekday. Editing can't turn a one-off into a series or change the pattern.

**Storage: a series plus materialized dates.** `event_series` holds the pattern and a template (title, times, location, description, slot definitions, circle, host, organizer). Each date is an ordinary `events` row with `series_id` set, so RSVPs, votes, slots, visibility, cancelling and notifications all work per date with no special cases, and `Event.repeat` just says which series a date belongs to. Dates exist only `REPEAT_HORIZON_DAYS` ahead (4 weeks weekly, about 2 months monthly), so a weekly event doesn't flood the list. `extendSeries` in `lib/db/events.ts` adds them: when the series is created, when a circle-hosted one is approved, and from a 10-minute poller (`lib/series.ts`, started by `instrumentation.ts`, which also doesn't hot-reload). `generated_through` is how far a series has got, so a date that was deleted is never made again, and the series row is locked while it's extended. A new date starts like a created event: the organizer attends, with empty slots.

**Governance.** A circle-hosted series is voted on **once**: only its first date exists until that's approved, and the approving vote (`setVote`) approves the series (`event_series.approved_at`) and adds the rest, already approved. While it's waiting, editing its one date is editing the series, the day included. Meetings don't repeat yet. If they come back, the open question is whether a series is voted on once or date by date, since a meeting's vote is also its RSVP.

**Notifications.** The circle is told **once**, by the first date's usual `new`/`proposed`/`approved` notice, whose email and digest line say how it repeats. Later dates are added silently.

**This date or this and later.** The organizer's edit form offers either scope for a date of a live series (`SeriesScope` in `lib/events.util.ts`). "This and later" applies to every later date not already cancelled and to the template, and keeps each date's slot signups by slot name, but the day itself only moves one date at a time. Cancelling "this and later" runs the usual cancel on each date (deleted if no one else is going, otherwise marked cancelled) and ends the series the day before (`until`), so nothing more is added. Someone going to several of those dates gets **one** cancellation email, about the soonest, saying the rest are off too (`endedBefore`). Both return every event they changed, and `AppStateProvider` merges them in.

### Role-slotted events and time-based cancellation
Some events define `roles` (shift lead, librarian, etc.) with `min`/`max` instead of a plain RSVP list. Whether the shift is cancelled is *derived from the clock*, not stored: `lib/roles.util.ts`'s `shiftNeedsSlots` (neutral, more than an hour out) flips to `shiftCancelled` inside the one-hour cancellation window (`inCancelWindow`) if a required role is still unfilled, and to `shiftEnded` after the end time. Don't cache these values — they must be recomputed on render.

### Events belong to a circle
An event's circle decides who can see it: only that circle's own members — not its parent or child circles — plus, for the root (city) circle, everyone, since everyone is implicitly in the city (`isCircleAudience` in `lib/circles.util.ts`; the implicit-root rule applies to events only). Enforcement is server-side: `getEventsForMember` in `lib/db/events.ts` only ever returns events in the member's circles or the root, so anything else is never sent to their browser (its `/events/[id]` 404s and it's absent from every list), and every write goes through a DAL function that takes the session's `memberId`: `createEvent` (requires the circle's audience, forces the organizer, generates the id and the starting rsvps/votes itself), `updateEventDetails` (organizer only; never changes circle, kind or organizer, and keeps signed-up slot members by role key), `setRsvp`, `setVote` and `toggleRoleSlot` (audience only; slot max and one-slot-per-person enforced). A member outside an event's audience gets the same "doesn't exist" error as for a missing event. An event's circle and host circle are locked after creation.

**Cancelling an event.** Its organizer can cancel it from the edit form (`cancelEvent` in `lib/db/events.ts`, through `cancelEventAction`), but not once it's over. What happens depends on whether anyone else is going to it, meaning an RSVP (a meeting's vote is one) or a slot. If someone is, the event is marked cancelled (`events.cancelled_at`, `Event.cancelled`), stays visible where it was with a Cancelled banner and badge, and each person going is emailed. If no one is, it's deleted, along with its RSVPs, votes, slots and notification rows. An unapproved proposal's votes are approvals, not RSVPs, so one is deleted. It's decided under a row lock, and it's final: every event write (`updateEventDetails`, `setRsvp`, `setVote`, `toggleRoleSlot`) refuses a cancelled event, its edit page 404s, and `isVoting` is false for it.

**Circle-hosted events.** The event form's "Hosted by" is a dropdown of the person and the (non-root) circles they belong to that are the chosen Circle itself or inside it (`isWithinCircle` in `lib/circles.util.ts`, re-checked by `createEvent` on the server) — so PVD Things can't host an event shown to The 903, while the Finance Council can — and changing the Circle drops a host that no longer fits; choosing a circle turns the form orange ("Propose event") and creates a proposal: only the host circle's members can see it (`getEventsForMember` and `canSee` in `lib/db/events.ts` are the SQL and per-row forms of the same rule — keep them in step) and only they can vote, each vote an approval only (not an RSVP, unlike a meeting). RSVPs and slot signups are refused until it's approved. The vote that reaches `majority(host circle size)` — decided on the server, under a row lock so concurrent votes can't each miss the others — sets `approved_at`; the proposer's own vote counts, so a one-member circle approves immediately. Once approved it becomes visible to `circleId`'s audience as well as staying visible to the host circle's members, reads as an ordinary event again (host shown as the circle, its organizer named), and can no longer be voted on. A proposal that's never approved just lapses after its date. The organizer alone edits it, including while it's a proposal; editing deliberately does **not** reset votes already cast — they stand. A meeting is unaffected: it stays a separate kind hosted by its own circle for its own members. `insertEvent` is the raw trusted insert only the seed scripts use. In the event form a "Circle" dropdown (the member's circles plus the city, home neighborhood first; meetings exclude the city) is who it's shown to, and slots are available on any ordinary event. `validateEventDraft` in `lib/events.util.ts` is the one pure check shared by the form and the DAL.


### Shared design tokens and components
The design system lives in one place now: the `@theme` block in `app/globals.css` (Tailwind v4 CSS-first config) — colors, fonts, and the type scale as CSS custom properties Tailwind utility classes read from. This used to be duplicated in a parallel `lib/theme.js` of JS constants for components still using inline `style={{...}}`; once the last such component was converted, `lib/theme.js` was deleted rather than left as dead weight — see Coding style below for how that migration worked. `components/shared/` holds the generic pieces reused across pages (`Eyebrow`, `TabbedPanel`, `SearchWithFilter`, `Tag`, `Chip`); `components/events/` has the event-specific reusable pieces (`DateTile`, `VoteButton`, `RsvpButton`) — reuse these rather than re-implementing per page. `components/shared/index.tsx` is a barrel re-exporting everything in the folder, so `import { Button, Label } from "@/components/shared"` works alongside (not instead of) importing a single file directly (`@/components/shared/button`) — both are valid, existing call sites weren't migrated to the barrel.

Toasts go through a `ToastProvider`/`useToast()` context (`components/shared/toast.tsx`) mounted in the true root `app/layout.tsx` — outside and above `app/(app)/layout.tsx`'s `AppStateProvider`, on purpose: it's the one provider both the unauthenticated welcome page and the authenticated app need, so the welcome page's login form gets `useToast()` for free. Components fire toasts via the hook rather than managing their own transient UI state.

## Code organization

Files are grouped by domain, not by component type: `components/shared/`, `components/circles/`, `components/events/`, `components/home/`, `components/profile/`, `components/game/`, `components/welcome/` — one component per file, with the file's kebab-case name matching its PascalCase export (`event.page.tsx` exports `EventPage`; see Coding style below for the `.page.tsx` suffix). `components/providers/` holds the two app-wide context providers (`app-state-provider.tsx`, `profile-modal-provider.tsx`) — they're components (they render JSX), just not ones any single domain owns. `components/shared/app-shell.tsx` is the nav wrapper (`TopBar` + `BottomNav`) rendered once in `app/(app)/layout.tsx` around every authenticated route; the button-press interaction CSS it used to carry in an inline `<style>` tag now lives in `app/globals.css` instead, since the unauthenticated welcome page needs those same classes and sits outside the tree `AppShell` wraps. `lib/` holds everything that isn't a component: `data.ts` (seed data, not imported by app code), `governance.util.ts` / `roles.util.ts` (an event's signup slots) / `recurrence.util.ts` (a repeating event's dates) / `format.util.ts` / `circles.util.ts` / `circle-roles.util.ts` (a member's roles in a circle) / `events.util.ts` / `members.util.ts` (pure helper functions), `hooks.ts` (`useMembers`, `useCircles`, `useAppNav`, ...), `auth.ts` / `session.ts` / `better-auth.ts` (auth — see Authentication), `email/` and `notify.ts` (outgoing email and the notification sender — see Email), `series.ts` (the poller that adds repeating events' dates), and the `lib/db/` subfolder (the data access layer — see that section) — these are `.ts` since they hold no JSX. When adding a new component, put it in the folder for the domain it belongs to; when adding cross-domain UI (used by 2+ domains), it belongs in `components/shared/`.

`app/` has three things at its root: `layout.tsx` (minimal — just `ToastProvider`), `page.tsx` (the unauthenticated welcome/login route — a thin wrapper rendering `components/welcome/welcome.page.tsx`'s `WelcomePage`, the same route-pages-wire/`components/`-render split used everywhere else), and the `(app)/` route group holding everything else plus its own `layout.tsx`. Within `(app)/`, each route mirrors the route list above one-to-one — each `page.tsx` is a thin client component that pulls data from `useAppState()`/`useProfileModal()` and wires navigation via `useAppNav()`/`useRouter()`, then hands everything to the actual UI component from `components/`. Keep that split: route pages own data-fetching-and-wiring, `components/` own rendering, so a component never has to know whether it's reached via routing or (hypothetically) something else. `proxy.ts` sits at the project root, a sibling of `app/`, not inside it — that's a Next.js convention, not a choice.

## Coding style

- **Tailwind (v4) for styling, using the theme tokens — not inline `style={{...}}` objects, and not CSS Modules.** This is a reversal of an earlier decision: inline styles were deliberate while the app was a single 3900-line file being split apart (adding a build step then would have widened that migration's scope), but now that the split is done, Tailwind is in. The migration off inline styles + `lib/theme.js` is complete — `lib/theme.js` itself has been deleted now that nothing imports it, and no component still uses a static inline `style`. `components/shared/eyebrow.tsx` and `components/shared/tag.tsx` are reference examples of the converted style (utility classes, `bg-ink`/`text-soft`/`font-sans`/`text-eyebrow`/`tracking-wide` etc. from the `@theme` tokens in `app/globals.css`, arbitrary-value or fractional-spacing classes like `px-2.75`/`tracking-[0.04em]` where a design value doesn't land on a named Tailwind step). When writing a new component, use Tailwind. Don't add an inline `style` object for anything Tailwind can express. A handful of components still keep one genuinely dynamic per-instance inline `style` (e.g. a computed progress-bar `width`, `FloatingActionButton`'s `bottom` offset, `FolderGrid`'s `gridTemplateColumns`) — Tailwind can't express a runtime-computed value as a static class, so these are deliberate, not leftovers.
- **Prefer a shared component over re-declaring the same style/behavior inline at each call site, once a pattern is genuinely established across the app.** `components/shared/button.tsx`'s `Button` is the reference example: before it existed, every "Save"/"Cancel"/"+ Add X" button in the app re-typed its own `style={{...}}` object for the same filled/invert-on-press or outlined/`ink-press` look (see the button-pattern inventory this replaced — filled primary, outlined secondary, outlined danger, a compact size). `Button` takes `variant` (`primary`/`secondary`/`danger`), `accent` (`ink`/`flame`/`teal`, primary only), `size` (`default`/`compact`), and passes through `disabled`/`onClick`/etc. — a leading icon is just a child rendered before the label text (`<Button><PlusIcon .../>Add hours</Button>`), not a separate prop, since the underlying markup already puts children in that order. It is deliberately **not** used for icon-only controls (a row's `✕` remove button, a modal's dismiss `✕`) — those stay bespoke, since `Button` always renders a visible text label. This doesn't override the general "don't add abstractions beyond what's needed" rule — a one-off control specific to a single page still stays inline — but when you notice yourself copying the same button (or similar repeated UI) styling into a third or fourth file, that's the signal to extract it into `components/shared/` rather than keep duplicating it, the same way `Eyebrow`/`Tag`/`Chip` already work.
- **Inline text links get an underline** — this is what distinguishes "this bold text is clickable" from plain emphasis (e.g. `components/circles/circle.page.tsx`'s website link, or the "Last edited by {name}" button in the same file). This applies specifically to bare text sitting inline in body content, not to nav chrome (top bar tabs, `BottomNav`) or anything already boxed/bordered as a button, pill, or card (e.g. the mailto pill in `profile-modal.tsx`) — those already read as clickable from their shape and position, so underlining them too would be redundant.
- Prefer a theme token over a raw value or one-off arbitrary class whenever one already covers it (e.g. `text-flame` over `text-[#e1530b]`, `text-eyebrow` over `text-xs` when it's actually an eyebrow) — the whole point of porting the tokens was to stop repeating the same hex codes and sizes across files. If a new value is genuinely needed in more than one place, add it to the `@theme` block rather than hardcoding it at each call site.
- **`clsx` for conditional/combined class names** (e.g. `components/shared/tag.tsx`'s filled/unfilled state) rather than hand-built template-literal string concatenation — chosen over `classnames` for being the smaller of the two with an equivalent API. Don't reach for `tailwind-merge` alongside it unless a real class-conflict-resolution need shows up (e.g. a component needing to override a token class a caller passed in); it solves a different problem than `clsx` and isn't installed.
- Comments are rare and rationale-only (explaining *why*, e.g. the note above `CANCEL_WINDOW_MS`) — the existing file is a good model for this; don't add comments narrating *what* the code does.
- **TypeScript (`.ts`/`.tsx`), not plain JavaScript.** This is a reversal of an earlier decision, the same way the Tailwind migration above reversed the inline-styles-while-splitting-the-file call: plain JS was fine for a prototype with no types worth enforcing yet, but the codebase outgrew that once real domain shapes (`Event`, `Circle`, `Member`, `Role`, ...) were being passed through a dozen layers by hand. `tsconfig.json` runs with `strict: true` and `noUncheckedIndexedAccess: true` from the start, not staged in later — the codebase's existing defensive style (guards everywhere already) made that low-friction. `lib/types.ts` is the single source of truth for the domain model (`Member`, `Circle`, `CircleRole`, `CircleResource`, `Event`, `Role`, `EventKindKey`, `NotificationKind`, ...) — import shapes from there rather than re-declaring a structurally-equivalent inline type at each call site. `Event` is one flat interface with the fields that only some events have (`kind`, `hostCircleId`, `proposed`, `votes`, `roles`) optional, not a discriminated union on `kind` — every real call site already guards these defensively, and a true union would force exhaustive narrowing rework across every existing `e.kind === "meeting"` check for no real safety gain here. Where governance logic reads several of those fields together, `lib/governance.util.ts`'s `isMeeting`/`isCircleHosted` type guards give real narrowing without touching call sites that don't need it. One known TS sharp edge worth knowing before you hit it: a `let` reassigned inside a `.map()`/`.filter()` callback does not narrow correctly when read afterward in the outer scope (TS keeps the pre-callback flow type there), and separately, narrowing a property (`e.hostCircleId &&`) does not survive into a nested closure (an `onClick`, a `db.transaction` callback, etc.) — both need the value hoisted into its own `const` at the point where the narrowing is actually valid (see `setVote` in `lib/db/events.ts`, which copies `row.hostCircleId` into a `const` before the transaction callback that uses it) rather than a bare `!` slapped on where the error surfaces.
- **All source filenames are kebab-case** (`circle-card.tsx`, `app-state-provider.tsx`, `date-tile.tsx`), including files that export a React component. This applies to the filename only — the exported component/function identifiers inside stay normal JS/React naming (`export function EventPage`, `PascalCase` for components, `camelCase` for everything else), since JSX requires a capitalized identifier to treat something as a component.
- **`.tsx` for anything under `app/` or `components/`, `.ts` for `lib/`.** The split is by location, not by whether a given file happens to contain a JSX tag — everything that's part of the component tree is `.tsx`; plain data/logic modules are `.ts`. Imports never include the extension, so this is purely a naming convention, not something Next.js's resolver depends on.
- **A file's *role* is encoded as a dotted suffix before that extension, for the two roles common enough to be worth marking:** `.page.tsx` for a component that's the full top-level view for exactly one route (`circle.page.tsx` exports `CirclePage`, one of two views `app/(app)/circles/[id]/page.tsx` can render — see Circles above; also `manage-circle.page.tsx`, `event.page.tsx`, `edit-myself.page.tsx`, `home.page.tsx`, `circles-root.page.tsx` and `neighborhood.page.tsx` (the Circles browser's other views, rendered at `/circles` and `/circles/[id]` for a neighborhood respectively), `event-form.page.tsx`, `name-game.page.tsx`, `events-list.page.tsx`, `welcome.page.tsx`), and `.util.ts` for a `lib/` module whose entire export surface is pure helper functions (`governance.util.ts`, `roles.util.ts`, `format.util.ts`, `circles.util.ts`, `events.util.ts`, `members.util.ts`). The suffix replaces an existing `-page`/`-form`-type word in the base name rather than stacking on top of it (`manage-circle-page.tsx` → `manage-circle.page.tsx`, not `manage-circle-page.page.tsx`). Not everything under `components/` or `lib/` gets a role suffix — only these two well-defined categories do: reusable/chrome components, providers, and one-off pieces (`circle-card.tsx`, `stat-card.tsx`, `app-state-provider.tsx`) stay plain kebab-case, and so do `lib/` modules that aren't collections of *pure* helper functions — `hooks.ts` is React hooks, `data.ts` is seed data, `types.ts` is the domain-model type module, and `lib/db/*.ts` / `lib/auth.ts` / `lib/session.ts` all have side effects (a database connection, cookies), which is exactly what disqualifies them despite being "helper functions" in a loose sense. When a new file clearly fits one of the two roles, name it that way from the start; don't invent additional suffixes (`.hook.ts`, `.provider.tsx`, etc.) without deciding that expansion explicitly first.
